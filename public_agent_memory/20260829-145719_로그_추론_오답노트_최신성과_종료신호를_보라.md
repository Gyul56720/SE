# 로그 추론 오답노트 -- 키워드 매칭 말고 최신성·종료신호를 보라

## 무슨 일이 있었나 (실측, 2026-08-29 14:51)

"admin-agent가 쿼터 소진으로 답변을 못 하는지, 답변 중인지 로그로 확인하라"는 질문에
public-agent가 이렇게 답했다: "쿼터 소진이 맞다. 근거는 09:15:40의 `candidate=key-29ca714b
:gemini-3.5-flash quota exhausted`다." 검증 결과 이 답은 근거가 틀렸다.

1. 인용한 09:15:40 사건은 **실패가 아니라 성공한 요청**이었다. 그 요청은 후보를 갈아타다가
   09:25:08에 `Model have changed` + 정상 `reply=`로 끝났다. 5시간 반 전의, 이미 성공으로
   끝난 무관한 줄을 "지금 답변 불가"의 증거로 인용했다.
2. 질문 시점에 실제로 봐야 할 건 가장 최근 admin 요청('시작.' 14:35:13)이었고, 그건
   14:42:20 이후 응답도 최종오류도 없이 멈춰 있었다 -- 진짜 근거는 여기 있었는데 안 봤다.

## 왜 틀렸나 (추론 실패의 뿌리)

- **키워드 최초 매칭 = 결론, 으로 점프했다.** "quota exhausted"라는 문자열을 로그에서
  처음 만난 자리에서 멈추고 그걸 근거로 삼았다. 질문은 "지금" 상태인데, 시간 순서상
  가장 최근의 관련 이벤트를 고르는 절차가 없었다.
- **전환 로그를 종료 로그로 오독했다.** `quota exhausted, 다음 후보로 전환`은 설계상
  "이 후보만 소진, 다음으로 넘어간다"는 진행 로그다(run_with_fallback_pool). 이 봇은 그
  줄 뒤에 `Model have changed` + reply로 여러 번 복구했다(05:20, 09:25, 14:30 실측).
  한 후보의 소진은 결코 "답변 불가"의 증거가 아니다.
- **질문의 전제에 편향됐다.** 질문이 "쿼터 소진인가?"라고 먼저 물으니, 반박 증거를 찾지
  않고 전제를 확증하는 줄만 골랐다(확증 편향).

## 다음부터 지킬 규칙 (오답노트)

1. **"지금" 상태를 묻는 질문엔, 로그를 시간 역순으로 훑어 가장 최근의 관련 이벤트부터
   본다.** 처음 만난 키워드 줄이 아니라, 질문 대상(여기선 admin thread)의 *마지막* 줄이
   근거다.
2. **종료 신호를 확인하기 전엔 실패로 단정하지 않는다.** fallback 루프의 진짜 종료 신호는
   둘뿐이다: (a) `reply=`가 찍혔다(=성공), (b) `(에이전트 오류, 사용 가능한 API 키/모델
   조합 모두 실패)`가 찍혔다(=완전 소진). 둘 다 없으면 "아직 진행/대기 중"이지 "소진 확정"이
   아니다.
3. **전환 로그(`다음 후보로 전환`)와 종료 로그를 구분한다.** 전환은 정상 동작이다. 소진
   줄의 개수가 아니라 그 뒤에 성공 reply가 왔는지를 본다.
4. **근거로 인용하는 로그 줄의 timestamp를 질문 시각과 대조한다.** 몇 시간 전 줄을 현재
   근거로 쓰지 않는다. 인용 전에 "이 줄이 지금 질문과 같은 요청·같은 시간대인가?"를 자문한다.
5. **질문의 전제를 그대로 믿지 말고 반증을 먼저 찾는다.** "X 때문인가?"라고 물으면, X를
   확증하는 줄뿐 아니라 X를 반증하는 줄(성공 reply 등)도 같이 찾은 뒤 판단한다.

## 한 줄 요약

로그로 "지금" 상태를 판정할 땐 -- 최초 키워드 매칭이 아니라 **가장 최근 관련 줄**을 보고,
**종료 신호(reply 또는 전체 실패 오류)**가 찍히기 전엔 성공도 실패도 단정하지 마라.
