## 1. 스펙을 읽는다는 것 = **아직 정의되지 않은 행동을 찾는 것**

`[사용자가져옴:안읽음]` 사용자가 준 핵심 문장: *"스펙을 읽는다는 것은 숫자를
읽는 것이 아니라 '아직 정의되지 않은 행동을 찾아내는 것'에 가깝습니다."*

예로 든 FIR 요구사항(signed 16-bit · 64 tap · 100 MHz · AXI4-Stream)에서
뽑아내야 하는 미정 항목:

    Input        sample rate? · valid/ready? · backpressure 허용?
    Coefficient  programmable? · **갱신 중 필터 동작 허용?**
    MAC          accumulator width? · saturation? · rounding? · overflow 행동?
    Performance  throughput? · latency? · initiation interval?
    Reset        sync/async? · reset value? · **리셋 중 출력 행동?**
    Interface    TLAST? · TKEEP? · **READY 가 LOW 일 때 내부 state 유지?**

**우리가 이미 하는 것.** `house/spec.py` 의 `모른다` 목록과 제안서 §2 "아직
모르는 것 — 사람이 정해야 하는 칸" 이 정확히 이 일이다. MERA 제안서가 그 칸을
5개 냈고, 관문 S027/S028 이 **읽은 칸을 모른다고 적는 것**과 **같은 것을 여러 줄로
적어 수를 부풀리는 것**을 잡는다.

**우리가 안 하는 것.** 위 목록은 **인터페이스 종류에서 기계적으로 따라 나온다** —
`valid/ready` 가 있으면 backpressure 질문이 따라오고, 누산기가 있으면 overflow
질문이 따라온다. 우리 `모른다` 는 **모델이 채우는 칸**이라 회로마다 들쭉날쭉하다.
`house/dv/plan.py` 가 시나리오를 인터페이스에서 뽑듯이, **미정 항목도 그렇게 뽑을
수 있다.** 이것이 가장 값싼 다음 한 걸음이다.

## 3. 실제 공개 IP 문서는 어떻게 생겼나 — **여기만 내가 읽었다**

`[내가읽음:목록]` **Caliptra Integration Specification** (chipsalliance/caliptra-rtl)
의 최상위 절, 순서대로:

    Scope · Overview · Caliptra Core · SoC interface definition ·
    SoC interface operation · SoC SHA acceleration block · TRNG REQ HW API ·
    Internal TRNG · SRAM implementation · **SoC integration requirements**

`[내가읽음:목록]` **Caliptra Hardware Specification** 의 최상위 절:

    Scope · Overview · Caliptra Core · Cryptographic subsystem architecture

그 안에 레지스터 맵 · Boot FSM(리셋 행동) · 워치독/치명 오류(오류 처리) ·
clock gating 절 · FSM 그림들이 있고, **정식 acceptance criteria 절은 옅다**.

**여기서 배울 두 가지.**

1. **상위 Integration Spec 과 개별 IP Spec 이 갈려 있다.** 통합하는 사람이 볼
   것(신호·스트랩·SRAM export·통합 요구)과 IP 속을 볼 것이 다른 문서다.
   → 우리 제안서는 **한 장에 다 넣는다.** 고객 SoC 팀이 볼 "통합 문서" 가 없다
   (`house/flow.py` 의 `없음` 칸 "고객 SoC 에 전달" 이 이것이다).
2. **`SoC integration requirements` 가 따로 한 절이다** — 보안 · DFT · 퓨즈 ·
   리셋/클럭 · 엔트로피 · SRAM 을 **통합하는 쪽이 지켜야 할 조건**으로 적는다.
   → 우리에게 그런 절이 없다. IP 를 넘길 때 "이 조건을 지켜야 동작한다" 를 못 적는다.

## 4. 요구사항은 **검증 가능해야** 한다 `[사용자가져옴:안읽음]`

나쁜 예: *"The filter shall provide high performance."*
좋은 예: **`REQ-FIR-003`: The filter shall process one input sample per clock
cycle when `TREADY=1`.**

그러면 곧바로 시험이 나온다:

    REQ-FIR-003 → TVALID/TREADY handshake → 1 sample/cycle → PASS/FAIL

**이것이 우리에게 정확히 빠진 고리다.** 우리는 아래 셋을 이미 가지고 있다.

    house/dv/plan.py   시나리오마다 **출처**(어느 포트/스캔 결과에서 나왔나)
    관문 4b            커버 빈이 커버리지의 **분모**
    관문 5c            테스트벤치가 정말 무는지(변이 점수)

**빠진 것은 맨 위 한 칸이다** — 요구사항에 **ID** 가 없다. 지금 사슬은

    포트/스캔 → 시나리오 → 커버 빈 → 커버리지 %

인데, 업계의 사슬은 한 칸 더 위에서 시작한다.

    **요구사항(REQ-ID)** → 시나리오 → 커버 빈 → PASS/FAIL → 요구사항으로 되짚기

우리 `speccheck` 는 스펙을 **자기 자신**과 대조하고(S016~S022), **요청 글**과
대조하지만(S023~S032), **요구사항 하나하나에 번호를 붙여 추적하지는 않는다.**

## 5. 문서 계층 `[사용자가져옴:안읽음]`

    고객 요구사항 → Product Requirements → Hardware Requirements Specification
    → **Hardware Architecture Specification (HAS)** → Microarchitecture
    → RTL → Verification → Synthesis/PPA

그리고 HAS 에 대한 구분이 쓸모 있다:

- *"MAC array 를 사용한다"* — 아키텍처 **설명**
- *"16-bit signed × 16-bit signed, accumulator 40-bit signed, overflow 는
  saturation"* — **구현 가능한 수준의 specification**

우리 제안서는 둘째 쪽에 가깝다(포트 폭·클럭·파라미터가 수로 박혀 있다). 다만
**REQ-ID 가 없어서 그 수를 시험으로 되짚을 수 없다.**

## 6. 책 `[사용자가져옴:안읽음]` — **한 권도 안 읽었다**

| 책 | 무엇을 배우는가 (사용자의 말) |
|---|---|
| Wiegers & Beatty, *Software Requirements* | 검증 가능한 요구사항 쓰기 · 모호성 제거 · acceptance criteria · traceability |
| Rabaey 계열 / Cambridge *Digital Integrated Circuit Design* | 요구사항 → 하드웨어 구조 (top-down) |
| Mehler, *Digital IC Design Using Verilog and SystemVerilog* | 스펙 → RTL 구조 |
| Chu, *RTL Hardware Design Using VHDL* | 합성 가능한 하드웨어로 내리는 법 |
| Yang, *Integrated Circuit Design: IC Design Flow and PBL* | 전체 흐름을 과제로 잇기 |

사용자의 추천 순서: **Wiegers → IC Design Flow → Mehler**.
한 권만 고른다면 *Software Requirements*.

**나는 이 중 어느 것도 안 읽었다.** 책 제목과 요약은 사용자가 준 것이다.

## 그래서 우리 코드에 무엇이 빠졌나 — 정리

| 업계가 하는 것 | 우리 | 어디에 있어야 하나 |
|---|---|---|
| 미정 행동을 **인터페이스에서 기계적으로** 뽑기 | 모델이 `모른다` 를 채운다 | `house/spec.py` + `dv/plan.py` 와 같은 꼴 |
| 요구사항에 **REQ-ID** | 없음 | `house/spec.py` |
| REQ → 시나리오 → 시험 **역추적** | 시나리오→빈까지만 | `dv/plan.py` 가 REQ 를 받게 |
| **Acceptance criteria** 절 | 없음 | 제안서 |
| **통합 요구(Integration requirements)** 절 | 없음 | 제안서 / 인도 문서 |
| 상위 Integration Spec 과 IP Spec 을 **가르기** | 한 장에 다 | `house/flow.py` 의 "고객 SoC 에 전달" 칸 |

**가장 값싼 순서**(내 판단):

1. **미정 항목을 인터페이스에서 뽑는다.** `dv/plan.py` 와 같은 방식이고, 이미 있는
   `rtlscan` 을 쓴다. 모델 없이 돌고, 회로를 안 가린다
2. **REQ-ID 를 붙인다.** 스펙의 못박힌 수마다 `REQ-<IP>-NNN` 을 매기면
   `표에서읽기()` 가 이미 그 수를 들고 있으므로 기계적이다
3. **시나리오에 REQ-ID 를 건다.** `dv/plan.py` 의 `출처` 칸이 이미 그 자리다
4. 그러면 **Acceptance criteria 절이 저절로 나온다** — REQ 마다 어느 시나리오가
   덮었고 어느 커버 빈이 찼는지

## 이 정리가 못 한 것

- **NASA Product Specification Document Standard 를 못 읽었다** (`ntrs.nasa.gov`
  차단). 요구사항/아키텍처/상세설계를 어떻게 가르고 traceability 를 어떻게
  명시하라는지는 **사용자가 전해 준 말**뿐이다
- **책 다섯 권 중 한 권도 안 읽었다**
- Caliptra 는 **절 제목 수준**까지만 봤다. 각 절이 실제로 어떻게 쓰였는지는 못 봤다
- DIDfinder(DI-IPSC-82259) 와 VUT 의 flash controller 논문은 **링크만 봤다**
