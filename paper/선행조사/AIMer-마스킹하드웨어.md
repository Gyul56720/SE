# 선행조사 -- AIMer / AIM 의 마스킹 하드웨어

**방침이 바뀌었다.** 빈 밭을 찾지 않는다. **붐비는 밭(PQC 마스킹 하드웨어, 2024~2026)에서
아직 아무도 안 디딘 한 걸음**을 고른다. 방법을 새로 만들지 않고 이미 있는 가젯 위에 선다.

**읽은 수준**: 전부 검색 요약이다. **이 주제의 1차 출처가 전부 망에서 막혔다**(아래 참조).

---

## 고른 걸음

**AIMer 의 일방향 함수 AIM 을 FPGA 로 짓고, 그 비선형부를 기존 합성 가능 가젯으로 마스킹하고,
형식도구로 검증한다.**

왜 이 걸음인가: **AIM/AIMer 의 FPGA 하드웨어 구현이 검색 범위에서 보이지 않는다.**
마스킹 이전에 구현 자체가 없다. 그런데 AIMer 는 KpqC 전자서명 표준(2025-01 확정)이고,
2026 에 국방 포함 5개 분야 시범전환이 걸려 있다.

## 우리가 그것과 다른 점

1. **AIM 의 FPGA 구현이 없다.** 소프트웨어 최적화(2023/1151, 2026/1417)와 양자회로(2023/337)
   뿐이다. 하드웨어는 첫 걸음이다.
2. **비선형부의 성격이 다르다.** AIM 의 비선형은 **Mersenne 거듭제곱** `x^(2^e - 1)` 이다.
   AES 의 GF(2^8) 역원(x^254)과 달리 **체가 훨씬 크고 지수가 파라미터**다. 체 분해 전략,
   곱 깊이, **랜덤성 비용**이 전부 달라질 수밖에 없다.
   -- **주의: 규격서를 못 읽어 n 과 e 를 확인하지 못했다. 아래 참조.**
3. **2026 형식검증 물결이 안 닿는 자리일 수 있다.** Prime-Field PINI, 마스킹 Barrett 축약,
   NTT 파이프라인 합성성 -- 전부 **격자의 소수체·NTT** 를 겨눈다. AIM 은 GF(2^n) 과 해시가
   본체다. -- **이것은 추론이다. 재지 않았다.**
4. **마스킹 비용이 해시에 몰린다**(소프트웨어 실측 1.8~5.5배). 하드웨어에서 이 분포가
   어떻게 되는지는 소프트웨어 결과로 예측되지 않는다.

# Phase 0 첫 실측 (2026-09-24) -- 레퍼런스를 세션에 붙여서 쟀다

`kpqc-cryptocraft/kpqclean_ver2` 를 붙여 **AIMer 레퍼런스 C 6종을 전부 읽었다.**
그래서 추정이 아니라 코드에서 구조를 꺼냈다.

## AIM2 의 실제 데이터흐름 (`aim2.c`)

    matrix_L, matrix_U, vector_b  <-  SHAKE(iv)          아핀층을 IV 에서 매번 생성
    for i in 0..L-1:
        state[i] = pt (+) const[i]                       const = pi 의 자릿수
        state[i] = state[i]^e_i                          역 Mersenne S-box (지수가 n비트 통짜)
        state[i] = L[i] * (U[i] * state[i])              아핀 (선형)
    s  = XOR(state[*]) (+) b
    s  = s^e_final                                       Mersenne S-box (e=7 / 31 / 7)
    ct = s (+) pt                                        feed-forward

**비밀은 `pt`(비밀키)이고, 비선형은 `gf_exp` 뿐이다.** 선형층(아핀·XOR·제곱)은 몫별로
따로 하면 되므로 **마스킹이 공짜다.** 그래서 마스킹 비용은 전부 **곱**에 몰린다.

## 잰 것 1 -- 지수에서 정적으로 센 곱 (제곱은 공짜로 친다)

| | 체 | 입력 S-box | 곱(이진법) | 슬라이딩창 최선 | 줄어듦 |
|---|---|---|---|---|---|
| AIMer-128 | GF(2^128) | 2 | 164 | **77** (w=4) | 2.13x |
| AIMer-192 | GF(2^192) | 2 | 258 | **108** (w=4) | 2.39x |
| AIMer-256 | GF(2^256) | 3 | 414 | **188** (w=5) | 2.20x |

**이 2배는 기여가 아니다 -- 슬라이딩 창은 교과서다.** 예산을 정하는 수일 뿐이다.
(그리고 eprint 2023/1151 의 "Mer 연산 최적화" 가 소프트웨어에서 이미 이걸 했을 수 있다.
**그 논문을 못 읽었다** -- eprint 이 망에서 막힌다.)

## 잰 것 2 -- 레퍼런스를 실제로 돌려 센 곱 (`aim/곱세기.sh`)

| aimer-128f | gf_mul | gf_mul_add | gf_sqr | 곱 합계 |
|---|---|---|---|---|
| keypair | **167** | 0 | 384 | **167** |
| sign | 164 | 5313 | 75760 | **5477** |
| verify | 0 | 4950 | 70785 | 4950 |

| aimer-192f | gf_mul | gf_mul_add | gf_sqr | 곱 합계 |
|---|---|---|---|---|
| keypair | **261** | 0 | 576 | **261** |
| sign | 256 | 7889 | 54480 | **8145** |

**독립 대조 통과**: keypair 의 `gf_mul` = **167 / 261**. 지수 popcount 로 **정적으로** 센 값과
**같다**. 완전히 다른 두 경로가 같은 수를 냈다.

**계측을 한 번 틀렸고 잡았다**: 처음에 `ld --wrap` 으로 쟀더니 keypair 가 **곱 0개**로 나왔다.
`--wrap` 은 **같은 파일 안의 호출을 못 잡는다** -- `gf_exp` 와 `gf_mul` 이 둘 다 `field128.c`
안이라 곱이 통째로 빠졌다. 소스에 직접 계수기를 넣어 다시 쟀다. (keypair 가 0 이 아니었으면
못 잡았을 것이다.)

## 그래서 나온 수 -- 랜덤성 예산

1차 마스킹에서 곱마다 신선한 랜덤 n비트를 쓴다는 **모형**을 쓰면:

    aimer-128f  서명 1회에 곱 5477 개 ->  85.6 KB 의 신선한 랜덤
    aimer-192f  서명 1회에 곱 8145 개 -> 190.9 KB 의 신선한 랜덤

**TRNG 처리량이 설계를 지배한다.** 이것이 소프트웨어 마스킹(Picnic 에서 비용이 **해시**에
몰렸다)과 다른 자리다.

## 이 수를 아직 못 믿는 이유 -- 사소한 설명을 다 못 죽였다

1. **어느 곱이 비밀에 닿는지 안 갈랐다.** MPCitH 의 곱 중 공개값끼리의 곱이 있으면 마스킹
   대상이 아니고, 그만큼 예산이 준다. **세어 보기 전에는 5477 이 상한이다.**
2. "곱마다 랜덤 n비트" 는 **모형이지 실측이 아니다.** 1차 DOM/HPC 체 곱의 표준 비용으로
   잡았을 뿐, 가젯을 실제로 짓고 세야 한다.
3. 제곱이 "공짜" 인 것은 **랜덤성 기준**이다. 면적과 지연은 공짜가 아니다.
4. 슬라이딩 창 수는 내가 짠 계수기가 낸 것이다. 내부 일관성(w=1 열 = popcount - S-box 수)은
   맞았으나 **독립 구현과 대조하지 않았다.**

# Phase 0-c 끝 (2026-09-24) -- 첫 RTL 이 돈다

`aim/rtl/` 에 GF(2^128) 곱·제곱과 AIM2 의 **최종 Mersenne S-box `x^7`** 을 지었다.
축약 다항식은 레퍼런스 `field128.c` 에서 읽었다: **f(x) = x^128 + x^7 + x^2 + x + 1**
(코드의 `<< 7`, `<< 2`, `<< 1` 과 `^ t` 가 곧 g(x) = x^7+x^2+x+1 이다).

`x^7` 은 가수로 펴면 **곱 2회**다 (레퍼런스 `gf_exp` 는 3회를 쓴다 -- 첫 곱이 out=1 에 낭비된다):

    x -> x^2 -> x^3 = x^2 * x -> x^6 = (x^3)^2 -> x^7 = x^6 * x
         제곱     곱              제곱             곱

## 잰 것 3 -- 레퍼런스 벡터 대조 (`aim/rtl검사.sh`)

    벡터 256 개  sqr 틀림 0 · mul 틀림 0 · mer7 틀림 0   -> 통과

정답은 **레퍼런스가 낸다**(`aim/dv/gen_vectors.c` 가 `gf_sqr`·`gf_mul`·`gf_exp(e=7)` 를
그대로 돌린다). 내가 짓지 않는다.

## 잰 것 4 -- **검사가 무는지** 변이로 확인 (네 개 전부 문다)

| 변이 | sqr | mul | mer7 | 이 꼴이어야 하는 까닭 |
|---|---|---|---|---|
| 축약 다항식 x^7 -> x^6 | 254 틀림 | 254 | 254 | 셋 다 `reduce` 를 쓴다 |
| clmul 자리이동 i -> i+1 | **0** | 255 | 255 | `sqr` 는 clmul 을 안 쓴다 |
| 제곱 비트벌리기 한 칸 | 255 | **0** | 255 | `mul` 은 spread 를 안 쓴다 |
| 벡터 파일 비우기 | - | - | - | 초록이 아니라 **무효**로 낸다 |

**어느 것이 깨지고 어느 것이 안 깨지는지가 의존 구조와 맞는다.** 이것이 테스트벤치가
제대로 물려 있다는 증거다.

**변이 하나를 처음에 놓쳤다**: `sed` 로 `<< 7)` 을 바꿨는데 **주석 안의 `(temp[3] << 7)`**
을 먼저 맞춰서 **코드가 하나도 안 바뀐 채 통과**했다. 하마터면 "이 변이는 검사가 못 잡는다"
고 잘못 보고할 뻔했다. 지금은 코드 줄을 정확히 노리고, 대상을 못 찾으면 죽는다.

## 잰 것 5 -- 면적 (yosys, 기술 비의존)

| 모듈 | 셀 | AND | XOR | MUX |
|---|---|---|---|---|
| `gf128_sqr` | **204** | **0** | 204 | 0 |
| `gf128_mul` | **33,038** | **16,384** | 16,654 | 0 |
| `mer7` (제곱2+곱2) | 66,484 | 32,768 | 33,716 | 0 |

**이 표가 마스킹 이야기를 게이트로 보여준다.**

- 제곱은 **AND 가 0개** -- 순수 XOR, 곧 **선형**이다. 마스킹에서 몫마다 복제만 하면 되고
  **신선한 랜덤이 0비트**다.
- 곱은 **AND 가 16,384개**. 1차 마스킹이면 이 AND 하나하나가 가젯이 된다.
- **곱이 제곱보다 셀 기준 162배다.** 앞서 센 "서명 1회에 곱 5477개" 가 왜 설계를 지배하는지가
  여기서 보인다.

**합성 꼴이 결과를 바꾼 것도 쟀다**: `if (b[i]) acc ^= a << i` 로 쓰면 비트마다 **MUX**가
나고(실측 MUX 32,768개), `acc ^= (a & {255{b[i]}}) << i` 로 쓰면 **AND**가 난다. 같은 식인데
합성 결과가 다르다. 셀 **개수**는 같지만 AND2 가 MUX2 보다 싸므로 실제 면적은 준다
-- **다만 GE 는 라이브러리에 매핑해야 말할 수 있다. 아직 안 했다.**

## 아직 못 믿는 것

1. 교과서 곱이다. **카라추바를 안 썼다.** 33,038 셀은 상한이지 좋은 수가 아니다.
2. **조합회로 한 판**이다. 파이프라인도 지연 측정도 없다.
3. GE·전력은 **라이브러리 매핑을 안 해서 말할 수 없다**(`house/lib/` 에 라이브러리가 있다).
4. 아직 **마스킹을 안 했다.** 여기까지는 평문 RTL 이다.

# 잰 것 6 -- **역 Mersenne S-box 의 곱이 9~16배 줄어든다** (`aim/mer역_가수.py`)

규격서의 정의에서 구조를 세우고 **계산으로 확인했다.**

    d = e^-1 mod n  이라 하면   e~ = sum_{j=0}^{d-1} 2^(e*j mod n)
    따라서  x^e~ = x * s(x) * s^2(x) * ... * s^(d-1)(x),   s(x) = x^(2^e)

**두 가지로 확인했다.** (1) 구조 검증 `(2^e-1) * e~ = 1 mod (2^n-1)` 이 7개 전부 통과.
(2) `d = popcount(e~)` 가 **레퍼런스 상수에서 실측한 81 · 83 · 113 · 143 · 163 · 69 · 183
과 정확히 일치**한다. 그리고 계산으로 (3) 가수 결과 = 이진법 결과, (4) `Mer[e](x^e~) = x`
왕복까지 맞췄다.

| | n | e | d | 레퍼런스(이진법) 곱 | **가수 곱** | 배수 |
|---|---|---|---|---|---|---|
| AIM2-I | 128 | 49 | 81 | 81 | **8** | 10.1x |
| | 128 | 91 | 83 | 83 | **9** | 9.2x |
| AIM2-III | 192 | 17 | 113 | 113 | **9** | 12.6x |
| | 192 | 47 | 143 | 143 | **11** | 13.0x |
| AIM2-V | 256 | 11 | 163 | 163 | **10** | 16.3x |
| | 256 | 141 | 69 | 69 | **8** | 8.6x |
| | 256 | 7 | 183 | 183 | **12** | 15.2x |

**AIM2-I 한 판: 164 곱 -> 19 곱 (8.6배).**

## 왜 **하드웨어**에서만 값어치가 큰가

`s^k(x) = x^(2^(e*k))` 는 Frobenius 거듭제곱이라 **선형**이다.

- **하드웨어**: 상수 GF(2) 행렬 하나. 마스킹에서 몫별로 따로 하면 되고 **신선한 랜덤 0비트**.
- **소프트웨어**: 제곱을 `e*k` 번 도는 것이라 **전혀 공짜가 아니다.**

앞서 게이트로 잰 것이 이걸 뒷받침한다: `gf128_sqr` 은 **AND 0개**(순수 XOR, 선형),
`gf128_mul` 은 **AND 16,384개**. 곱만 랜덤을 먹는다.

**그래서 최적화의 목적함수가 다르다.** 소프트웨어는 총 시간을 줄이고, 마스킹 하드웨어는
**곱의 개수가 곧 랜덤 비트 수**다.

## 이 수를 아직 못 믿는 이유

1. **면적 대가를 안 쟀다.** 곱은 9~16배 줄지만 **서로 다른 Frobenius 지수마다 선형 회로가
   하나씩 는다.** 128x128 GF(2) 행렬 하나가 수천 XOR 이므로, 2*log2(d) 개쯤이면 곱 하나와
   맞먹을 수 있다. **랜덤성은 분명히 이득이고 면적은 아직 모른다.**
2. **서명 전체로 보면 작다.** 앞서 실측한 서명 1회의 곱 5477 개 중 역 Mersenne 이 쓰는 것은
   **164 개뿐**이고 나머지 5313 개는 MPC 곱셈검사다. 164 -> 19 는 전체의 **2.6%** 다.
   **키생성과 AIM2 평가기 자체에서는 전부다.**
3. **신규성을 확인하지 못했다.** eprint **2023/1151** 이 "**Mer 연산 최적화**" 로 최대 97.9%
   개선을 보고하는데, **그게 바로 이것일 수 있다.** eprint 이 망에서 막혀 못 읽었다.
   **이 칸을 닫기 전에는 새롭다고 말하지 않는다.**
4. 가수는 반복제곱법이다. **최단 가수가 아니다** -- 더 줄 수 있다.

# 잰 것 7 -- 가수의 **면적 대가**를 게이트로 쟀다 (`aim/rtl/aim_mer_inv.v`)

앞서 "곱은 9~16배 줄지만 선형 회로가 는다 -- **랜덤성은 이득이고 면적은 모른다**" 고 적었다.
이제 잰다.

**같은 RTL 안에 두 셈법을 넣고 파라미터로 갈랐다.** 그래야 합성이 둘을 직접 견준다.

    MODE=0  이진법 -- 레퍼런스 gf_exp 와 같은 셈법. 제곱기만 쓴다
    MODE=1  Frobenius 가수 -- 배럴(7단, sigma^(2^j) 를 지나거나 건너뛴다)

둘 다 **곱셈기 하나를 재사용**한다. 그래야 비교가 정직하다.

## 대조 -- 레퍼런스 벡터 32개, 두 모드 다 통과

    vectors=32  MODE0(binary) bad=0  MODE1(chain) bad=0
    cycles: MODE0=128  MODE1=8

정답은 레퍼런스 `gf_exp(x, aim2_sbox_exponents[0])` 이 낸다.

## 면적 (yosys, 기술 비의존)

| | 셀 | **AND** | XOR | MUX | DFF | 사이클 | 곱 |
|---|---|---|---|---|---|---|---|
| MODE=0 이진법 | 34,215 | **16,394** | 16,865 | 544 | 394 | 128 | 81 |
| MODE=1 가수 | 60,675 | **16,394** | 42,569 | 1,299 | 394 | **8** | **8** |

**AND 가 정확히 같다**(16,394). 곱셈기 하나를 공유하니 당연하고, 그것이 요점이다 --
**늘어난 것은 전부 XOR 25,704 개**이고 그것은 Frobenius 배럴이다.

    평문 하드웨어에서의 맞바꿈:  면적 1.77배  <->  사이클 16배 · 곱 10.1배

## 왜 이것이 **마스킹에서** 유리한 맞바꿈인가

- **AND = 비선형.** 1차 마스킹에서 가젯이 되고 **신선한 랜덤을 먹는다.** 두 모드가 **같다.**
- **XOR = 선형.** 마스킹에서 **몫마다 복제**될 뿐 랜덤을 안 먹는다.
- **랜덤 비트는 곱 횟수에 비례한다**: 곱마다 n비트라는 모형이면
  **S-box 한 번에 81x128 = 10,368 비트 -> 8x128 = 1,024 비트.**

즉 가수는 **랜덤을 안 먹는 쪽(XOR)으로 면적을 늘려서, 랜덤을 먹는 쪽(곱 횟수)을 10배 줄인다.**
TRNG 처리량이 설계를 지배한다는 앞의 실측과 맞물린다.

## 아직 못 믿는 것

1. **아직 마스킹을 안 했다.** 위 랜덤 비트 수는 **모형에서 온 투영이지 실측이 아니다.**
   실제로 HPC 가젯을 붙이고 PROLEAD 로 검증해야 한다.
2. **GE 가 아니다.** 기술 비의존 셀 수다. XOR2 와 AND2 의 면적비가 1 이 아니므로
   "1.77배" 는 라이브러리에 매핑해야 확정된다 -- **그것이 Nowon Silicon 의 SYN 일이다.**
3. 곱셈기가 **교과서 꼴**이다(카라추바 아님). 곱셈기가 작아지면 배럴의 상대 비중이 커진다.
4. 사이클 128 대 8 은 **곱셈기가 1사이클**일 때다. 파이프라인하면 달라진다.

걸렸다. 레지스터가 X 로 남고 `busy` 가 X 가 되어 `start` 를 영영 못 받아 **시간초과**가 났다.
1 에서 시작해 내려찍도록 고쳤다. (앞서 `--wrap` 이 같은 파일 안의 호출을 못 잡던 것,
