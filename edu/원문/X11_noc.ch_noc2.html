X11. Interconnect: Arbitration, Flow Control and Deadlock

An IP block that talks to anything talks through an interconnect, and the interconnect's properties leak into the block's specification whether or not the specification mentions them. The three that leak hardest are how bandwidth is shared, how back-pressure propagates, and whether the system can lock up. All three are computable and the third is provable.

X11.1 Credit-based flow control: sizing the buffer

Why the buffer must cover the round trip
StepJustification
1The sender may transmit only while it holds credits; each transmission consumes one.Definition of credit-based flow control.
2A credit is returned when the receiver frees a buffer entry; the return takes tret to arrive.Physical delay: the return path is wires and pipeline stages like any other.
3For the sender never to stall while the receiver is draining, credits must outlast the round trip.Otherwise there is an interval in which the sender has no credit and the receiver has space.
4Nbuf ≥ B · RTT, where B is the peak rate and RTT is forward latency plus return latency.The bandwidth–delay product. It is the same formula as a TCP window and for exactly the same reason.
5Any shortfall shows up as a throughput loss of Nbuf/(B·RTT), not as a functional failure.Which is why an undersized buffer is found in performance bring-up rather than in verification — late, and by the customer.

Worked example 3. A block on a pipelined AXI interconnect
Given. A DMA engine issues read bursts across an interconnect with 6 cycles of forward latency and 6 of response, at 500 MHz, 128-bit data, and must sustain 6 GB/s.
Method. Convert the required bandwidth into outstanding transactions via the bandwidth–delay product, then check it against the interface's ID width, which is what actually limits outstanding transactions on AXI.

How this is got wrong. By sizing the buffer for the burst and not for the round trip. A common specification says ‘one burst of read data’, which permits exactly one outstanding burst and throttles the engine to burst-length divided by round-trip — here about a quarter of the wire rate. The second frequent error is to size for the average latency: the interconnect's latency has a tail whenever another master is active, and a buffer sized for the mean stalls whenever the tail occurs. Size for the latency at the load you will actually run at, and state that load in the datasheet, because a customer whose system is busier than your bench will not reach your quoted bandwidth.

Quality of service is not a policy, it is two different requirements that must be separated before a policy can be chosen. A display controller needs guaranteed bandwidth and tolerates latency, because it has a line buffer; a CPU fetching a cache miss needs low latency and consumes little bandwidth. One arbiter cannot serve both well with a single knob, which is why real interconnects separate them: a bandwidth regulator (a token bucket or a deficit counter) enforces the first, and a priority class enforces the second, with the regulator demoting a requester that exceeds its allocation so that its priority cannot starve anyone. When writing an IP block's requirements, state which of the two you need; ‘high performance’ is not an interconnect requirement and cannot be designed against.

X11.3 Deadlock: a property of the dependency graph

The four conditions, and which one hardware removes
StepJustification
1Mutual exclusion: a resource is held by one holder at a time.True of every buffer; not removable.
2Hold and wait: a holder may request another resource while holding one.True of any pipelined request; removing it means allocating everything at once, which wastes buffers.
3No pre-emption: a buffer cannot be taken back.Removable — by dropping and retrying, which is what a network does and what an on-chip fabric usually cannot afford.
4Circular wait: the wait-for graph contains a cycle.This is the one hardware removes. Break every cycle and deadlock is impossible regardless of the other three.
5Virtual channels break cycles by splitting one physical buffer into several logically independent ones with an ordering between them.A message may only move from a lower-numbered channel to a higher one, so the dependency graph becomes acyclic by construction.
6Dimension-ordered routing breaks cycles in a mesh by forbidding a turn.X then Y: the turns that would close a cycle are simply not permitted. Cheap, and it costs path diversity, which costs throughput under adversarial traffic.
The most common on-chip deadlock has nothing to do with routing. It is a read response that cannot make progress because the response buffer is full of responses waiting behind a write that cannot complete because the write channel is blocked by a request from the same master. Protocol specifications address this with ordering rules — AXI's requirement that read and write channels be independent, and that a slave must not make a read response depend on a future write — and those rules are routinely broken by IP blocks that share one internal queue between the two channels. If your block merges AXI's read and write paths into a single ordered structure anywhere, you have created this deadlock, and it will appear in a customer's system and not in yours.
Problem. A bridge accepts an AXI write and must issue a read to fetch the rest of a partially written cache line, then complete the write. Why is this a deadlock hazard, and what are the fixes?
Solution. It creates a dependency from the write channel to the read channel. If the read travels through the same interconnect and that interconnect is congested with writes — including this one, which is holding a slot — the read cannot be issued and the write cannot retire. The wait-for graph has a cycle. Three fixes, in increasing order of cost and decreasing order of fragility. Reserve resources before accepting: do not accept the write until a read slot and a line buffer are already allocated, so the bridge never holds and waits. Use a separate virtual or physical channel for the fetch, so the read's path cannot be blocked by writes. Buffer the entire write and acknowledge it immediately, converting the dependency into a local one — which costs a full line of storage per outstanding write and changes the coherence behaviour. Whichever is chosen, the argument must be written down as an acyclicity claim about the dependency graph, because it is not something a simulation will refute reliably: deadlocks appear only under specific congestion, and the bench that would produce it is rarely the bench that is written.

Worked example 4. Bisection bandwidth decides, not link count
Given. A 16-node system, 128-bit links at 1 GHz. Compare a ring, a 4×4 mesh and a full crossbar under uniform random traffic, where on average half the traffic crosses the bisection.
Method. Compute the bisection bandwidth — the bandwidth across the worst cut that divides the network in half — and compare with the offered load. Bisection, not aggregate link bandwidth, is what limits uniform traffic.

How this is got wrong. By quoting aggregate bandwidth. The ring in this example has 16 links and 256 GB/s of aggregate link bandwidth, which sounds ample and is irrelevant: uniform traffic is limited by the two links at the cut. The corollary is that topology should be chosen from the traffic pattern. If the real traffic is nearest-neighbour, the ring's bisection never binds and it is the right answer; if it is all-to-all, only the bisection matters. An interconnect specified without a traffic model has not been specified.
