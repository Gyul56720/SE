X5. Reed–Solomon Decoding, Traced and Measured

Reed–Solomon is the error-correcting code that every high-speed Ethernet and storage link in this book actually uses, and it is the code the practice volume builds an IP block around. It is also a code whose decoder is usually presented as four opaque stages. This part opens each stage on a small field where the numbers can be printed in full, then measures the large field that ships.

X5.1 The field is a choice, and an unverified choice is a risk

A Reed–Solomon code lives over a finite field GF(2m ), and the field is fixed by a primitive polynomial. Two implementations that pick different primitive polynomials produce different codewords and cannot talk to each other, even though both are ‘RS(544,514)’. The model this chapter runs therefore takes the polynomial as a parameter and records whether it has been confirmed against the standard.

Worked example 45. Verifying a small field before using it
Given. GF(24) generated by x4 + x + 1 (0b10011).
Method. The model builds exponent and log tables and refuses any polynomial whose root α has order less than 2m−1 — that is, it rejects non-primitive polynomials by construction rather than by trusting the caller. It then checks the field axioms, not a table of expected values, because a table of expected values is only as good as whoever typed it.

How this is got wrong. By declaring success when the syndromes go to zero and stopping there. A decoder that miscorrects also produces zero syndromes — it has landed on a different valid codeword. The only defence is to re-check after correction and to bound the number of corrections by t; the model does both, which is why the next section's measurement of the beyond-t region is meaningful.
Why the syndromes are what they are. The syndrome Sj is the received polynomial evaluated at αfcr+j . Every valid codeword is divisible by the generator, whose roots are exactly those powers, so a clean codeword gives all-zero syndromes. What survives the evaluation is therefore only the error polynomial — the syndromes depend on the errors and not at all on the data. That single fact is what makes bounded distance decoding possible, and it is worth verifying on the numbers above: change the message and re-run, and the syndromes do not move.

X5.3 Berlekamp–Massey as a hardware recurrence

What Berlekamp–Massey is actually doing
StepJustification
1The syndromes of an e-error pattern satisfy a linear recurrence of order e.Each error contributes a geometric sequence αji; a sum of e geometrics satisfies an order-e recurrence.
2The recurrence's characteristic polynomial is the error locator σ(x).Its roots are the inverses of the error positions, by construction.
3So decoding reduces to: find the shortest linear recurrence that generates the observed syndrome sequence.This restatement is the entire content of the algorithm.
4Berlekamp–Massey finds it in 2t iterations, each a discrepancy computation and a polynomial update.Equivalent to the extended Euclidean algorithm on x2t and S(x); the two are the standard alternatives in RTL.
5Each iteration costs O(t) field multiplies, so the whole algorithm is O(t2).For KP4, t = 15, so the key equation is a few hundred multiplies — small beside the 544-symbol Chien search.
6The iteration count is data independent.Which is why the decoder has a fixed latency, which is why the PCS can be built around it. A variable-latency decoder would need elastic buffering through the whole receive path.

X5.4 Beyond t: the region a careless test never visits

A bounded-distance decoder corrects up to t errors. What it does with t+1 or more is the interesting question, because that is the region a real link visits and a lazy test never does. Three outcomes are possible: detect the failure and flag it, miscorrect to a wrong codeword silently, or leave the word unchanged. The measurement below counts all three.

400 random trials per row, seeded. The first three rows must be 1.000 — that is the code's guarantee. The rows below must not be 1.000, and a test suite that only ever injects zero or one error cannot tell a working decoder from one that returns its input unchanged.
This is the false-green that RS test benches actually produce. Inject zero errors, check the output equals the input, declare the decoder verified. A decoder consisting of a wire passes. The repository's measurement function refuses to report a pass from a zero-error trial at all, and its test suite deliberately breaks the syndrome computation and asserts that the measurement notices. A verification plan for an FEC block must state, for every test, what broken implementation that test would catch.
Problem. Why can a decoder that corrects a word with more than t errors be worse than one that flags the word as uncorrectable?
Solution. Because a miscorrection is a silent data error and an uncorrectable flag is an announced one. Upper layers are built to handle the announcement: Ethernet marks the frame errored and it is discarded and retransmitted; storage returns a read failure and the host retries or reconstructs from parity. There is no layer that handles data that is wrong and claims to be right. In a system with an outer code — the concatenated structure of 802.3dj — the point is sharper still: the outer decoder can use the inner decoder's uncorrectable flag as an erasure, and an erasure costs one parity symbol where an unflagged error costs two. Detection is worth roughly twice as much as the same amount of correction, which is why real decoders spend logic on checking their own output.
Problem. KP4 is RS(544,514) over GF(210), yet 544 > 210−1 is false — 544 is comfortably below 1023. What is the code called when n is smaller than the natural length, and what does the shortening cost?
Solution. It is a shortened Reed–Solomon code: take the RS(1023,993) code and fix the leading 479 message symbols to zero, then decline to transmit them. Both ends know they are zero, so the decoder simply treats the received word as having 479 leading zeros. Shortening costs nothing in minimum distance — d = n−k+1 = 31 either way, so t remains 15 — and it costs nothing in the decoder except that the Chien search may be restricted to the 544 positions that are actually transmitted, which is a saving. The one thing it does change is the false-detection probability: a shortened code has fewer codewords in the same space, so a random error pattern is less likely to land on a valid codeword. Shortening therefore improves miscorrection statistics slightly, for free.

The waterfall between the first and last row spans many orders of magnitude for a factor of a hundred in input BER. That steepness is what FEC buys and it is why link margin is measured in fractions of a dB.
The dangerous assumption, named. Every number in that table assumes bit errors are independent. They are not, for the reason Part X4 measured: DFE error propagation makes short bursts. Bursts are partly good for a symbol code — ten wrong bits inside one symbol cost one symbol — and partly bad, since a burst straddling a boundary costs two. The net effect depends on the burst-length distribution, which is a property of the receiver, not of the channel. This is why compliance standards specify a stressed-input test rather than a BER number: the test reproduces the error statistics, and no scalar summary of the channel can. When a customer asks for post-FEC performance, the honest answer names the burst model used, and a design house that can produce that model has something to sell beyond the RTL.
