X35. Hardware Data Structures: CAM, Hashing and Bloom Filters

Networking, storage and security IP spend most of their logic looking things up. The structures that do it are a small, well-understood family with sharply different cost profiles, and choosing among them is one of the clearest cases in this book where an architectural decision is settled by arithmetic rather than by preference.

TCAM is the structure that decides the cost of a router, and it is worth knowing why it is so expensive. A ternary cell stores three states — 0, 1 and don't-care — which needs two storage bits plus comparison logic, roughly sixteen transistors against six for SRAM. Worse, every cell compares on every lookup, so power is proportional to the whole table rather than to the entry found: a large TCAM can dissipate tens of watts doing nothing but matching. The architectural responses all reduce the number of cells that must compare — partition the table by prefix length and activate only relevant banks, put a small filter in front, or replace TCAM with an algorithmic trie in SRAM and accept multiple accesses. Every high-end switch datasheet's power figure is substantially a statement about this one structure.

X35.2 Hashing: the birthday problem decides your table size

Why a hash table needs to be much larger than its contents
StepJustification
1With n items in m buckets, the probability that a particular pair collides is 1/m.Uniform hashing assumption.
2There are n(n−1)/2 pairs, so the expected number of colliding pairs is about n2/(2m).Linearity of expectation.
3Collisions start appearing when n ≈ √m, not when n ≈ m.The birthday paradox. This is the fact that surprises people sizing tables.
4The longest chain with n = m is Θ(log n/log log n) — about 5–8 for realistic sizes.So a single-probe hardware lookup fails often enough to matter.
5Two hash functions and a choice of the emptier bucket reduces the longest chain to log log n.The power of two choices: an exponential improvement from one extra probe. This is why hardware hash tables are multi-way.

How this is got wrong. By choosing the average-case structure for a worst-case requirement. Chained hashing has a superb average and an unbounded tail, and a networking datapath is judged on the tail: a lookup that occasionally takes eight accesses either stalls the pipeline or drops the packet. Cuckoo hashing buys a bounded query at the cost of a potentially long insertion, which is the right trade because insertions are rare and can be handled by a slow path. Recognising which operation must be bounded is the whole of the design decision.

X35.3 Bloom filters: paying memory for certainty in one direction

The false-positive rate, and the optimal number of hashes
StepJustification
1A Bloom filter is m bits; inserting an item sets k bits chosen by k hashes.No item is stored — only its fingerprint in the bit array.
2After n insertions, the probability a given bit is still zero is (1−1/m)kn ≈ e−kn/m.Independent settings.
3A query gives a false positive when all k bits happen to be set: p = (1−e−kn/m)k.Never a false negative — that asymmetry is the whole value.
4Minimising over k gives k = (m/n)ln 2.And then p = 2−k.
5So about 1.44 log2(1/p) bits per item, regardless of how large the items are.A 1 % filter costs about 10 bits per item whether the items are 32-bit or 1500-byte. That independence from key size is why it is used in front of expensive lookups.

Problem. Where does a Bloom filter belong in an IP block, and where does it not?
Solution. It belongs wherever a negative answer is common and an expensive lookup can be skipped, and where a false positive costs only wasted work rather than a wrong result. Concretely: in front of a TCAM or an off-chip table, to avoid the access entirely for the majority of keys that are absent; in a cache to avoid probing a way; in a coherence directory to avoid a snoop. In each case the filter is an optimisation and the real structure still answers. It does not belong anywhere the answer is used directly, because a false positive is then a wrong answer — and it does not belong where deletions are needed, because a plain Bloom filter cannot delete (clearing a bit may un-insert another item); that needs a counting Bloom filter at four times the memory, and at that point a small hash table is often better. The design question to ask is: what is the measured fraction of negative queries? A filter in front of a table that is usually hit is pure cost, and that fraction is a property of the customer's traffic, which means it belongs in the datasheet as an assumption.
