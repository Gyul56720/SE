Z22. 8b/10b — One Block, Two Markets

Of everything a one-person design house could build first, an 8b/10b encoder is unusually well chosen, for a reason that has nothing to do with the technology: the same block sells into PCIe and into Ethernet. PCIe Gen1 and Gen2 use it as the physical-layer line code; so does 1000BASE-X, the gigabit Ethernet PCS. So do SATA, DisplayPort, Fibre Channel and USB 3 Gen1. One verification effort, one datasheet, several customers who do not compete with each other.

Z22.1 Where it sits

Read that diagram as a list of obligations rather than a picture. The CDR cannot recover a clock from a long run of identical bits, so the code must bound run length. The AC coupling capacitors in the channel cannot pass DC, so the code must bound the imbalance between ones and zeros. The deserialiser has no idea where a byte starts, so the code must provide a pattern that means ‘here’ and cannot be forged by data. Each of those is one of the four properties Part Z21 proved.

Z22.2 What the code does, in one worked byte

Encoding 0x00 with running disparity −1
StepJustification
1Split the byte into low 5 bits and high 3 bits: 0x00 → x = 0, y = 0. This is written D0.0.The code is built from a 5b/6b stage and a 3b/4b stage. The naming Dx.y is universal in the literature.
2Look up x = 0 in the 5b/6b table for RD = −1: 100111.Four ones and two zeros, so its disparity is +2.
3Running disparity was −1; adding +2 gives +1.This is why the table for RD = −1 holds the codeword with positive disparity: it pulls the imbalance back toward zero.
4Now look up y = 0 in the 3b/4b table, using the updated disparity RD = +1: 0100.One one and three zeros, disparity −2. The 3b/4b stage sees the disparity after the 6-bit stage, not the disparity the byte started with — a detail that is easy to get wrong and that the property check catches immediately.
5RD becomes +1 − 2 = −1, and the codeword is 100111 0100.Back where we started, which is exactly what bounded running disparity means.
6Check the result: 1001110100 has five ones and five zeros, and its longest run is two.Verified against the published value for D0.0 as one of the seven corroboration vectors.

The third row is worth dwelling on, because it is the one that cannot be checked by looking at a codeword. A run of six can straddle a boundary: each codeword is individually fine and the pair is not. That is why the checker enumerates pairs, filtered by which disparity each one can follow — and it is why the two table-compression defects of Part Z21 were invisible until it ran.

Worked example 86. Why the longest run is exactly 5 and not 4
Given. P3 reports a longest run of 5, and that is a pass rather than a failure.
Method. Ask what produces the run of 5 and whether it is avoidable.
Numbers. The comma itself. K.28.5 is 0011111010 — five ones in a row, by construction. Any code that also bounded data runs at 5 without exception would have no pattern left that data cannot produce.
This is the general shape of the run-length/alignment trade. The comma must be distinguishable from data, so it must do something data cannot. Making the bound tighter for data is what buys the comma its distinctiveness.
How this is got wrong. The tempting reading of ‘longest run = 5’ is that the design only just passes and a small change might push it to 6. The opposite is true: the 5 is designed in, it occurs only in K codes, and the data codewords are strictly better behaved. Reporting the maximum without saying where it comes from would leave a reader with the wrong impression of the margin.

Z22.4 The circuit

The encoder is almost entirely combinational. There is exactly one bit of state in the whole block.

Why the running disparity register is one bit wide
StepJustification
1Running disparity is conventionally described as a signed accumulator.That is how the literature explains it, and it invites an implementation with a width and a saturation question.
2But P2 proves it only ever takes the values −1 and +1.Every codeword has disparity −2, 0 or +2, and the table selection always moves it back toward zero.
3Two possible values need exactly one bit: 0 means −1, 1 means +1.The accumulator, its width, and its saturation logic all disappear.
4So the entire sequential state of an 8b/10b encoder is one flip-flop.Measured: the synthesised block has 13 flip-flops — code 10 + rd 1 + code_valid 1 + err 1. Exactly one of them is the protocol state.
5Knowing an invariant is what bought that.The proof did not just check the design; it simplified it. This is the usual return on proving a property rather than assuming it.

Z22.5 The one-bit-state rule, in code

// 6비트 코드워드의 불균형만큼 RD 가 움직인다.  -2 / 0 / +2 뿐이다.
// $countones 대신 손으로 더한다 -- iverilog 가 -g2012 에서도 그것을
// 안 받는 판이 있다.  **도구에 안 기대는 쪽을 고른다.**
wire [2:0] six_ones = {2'b0, six[5]} + {2'b0, six[4]} + {2'b0, six[3]}
                    + {2'b0, six[2]} + {2'b0, six[1]} + {2'b0, six[0]};

// 1의 개수가 4 면 +2, 3 이면 0, 2 면 -2.  rd 는 1비트다.
wire rd_mid = (six_ones == 3'd4) ? 1'b1 :
              (six_ones == 3'd2) ? 1'b0 : rd;

Two details in six lines. The manual popcount avoids $countones, which some simulator builds reject even in -g2012 mode — when a construct buys you nothing but a dependency, do not take the dependency. And the rd fall-through in the last line is the disparity-zero case: the codeword does not move the imbalance, so the register holds. Writing that as an explicit else rather than letting it fall out of an incomplete assignment is what keeps always_comb from inferring a latch (Part Z18.5).

The stream matters more than the count. The golden generator threads running disparity from one vector to the next, so the expected value on line 2000 depends on every line before it. A single disagreement anywhere makes everything after it wrong — the regression cannot quietly pass with a broken state machine, which is the failure mode a per-codeword test would have.

Worked example 87. What the mutation score found that 3000 passing vectors did not
Given. The regression passed 3000 streamed vectors with 0 mismatches. Mutation scoring then reported 71.4 % with six escapes.
Method. Look at each surviving mutant and ask why the tests cannot see it.
Numbers. Five were provably equivalent — OR replaced by XOR in a condition whose terms are mutually exclusive, verified over all 32×2 = 64 inputs with zero differences. The sixth was real: code_valid <= valid & ~bad_k mutated to | survived.
The fix was to observe code_valid during a deliberate idle beat after each transaction, which took four lines and moved the score to 100 %. This is the same lesson as the throughput mutant in Part Z1: a regression measures what you told it to look at, and mutation scoring is how you find out what you forgot.
How this is got wrong. The real one is not a subtle bug — the mutant asserts code_valid on every idle cycle, which would break any downstream consumer immediately. It survived because the testbench never looked at an idle cycle. The stimulus drove a transaction every beat, so the entire idle path was unexercised. No amount of additional random data would have found it.

74 LUTs and 13 flip-flops for a block that sits in the datapath of every PCIe Gen2 lane in the world. But the frequency is the number that decides what this block is actually good for, and it is worth doing that arithmetic rather than assuming.

Worked example 88. Is this fast enough to sell?
Given. The encoder reaches 84.9 MHz on iCE40 HX8K at one byte per clock. 1000BASE-X carries 1 Gb/s of payload; PCIe Gen2 runs 5 GT/s per lane and 8b/10b passes 8 payload bits per 10 transmitted.
Method. Convert each protocol's payload rate into the byte rate the encoder must accept, then compare.
Numbers. 1000BASE-X needs 1 Gb/s ÷ 8 = 125 Mbyte/s. PCIe Gen2 needs 5 GT/s × 8/10 ÷ 8 = 500 Mbyte/s per lane. At one byte per clock this block delivers 84.9 Mbyte/s — 68 % of gigabit Ethernet and 17 % of one PCIe Gen2 lane. It meets neither.
The fix is architectural, not a matter of squeezing the timing. Encoding two bytes per clock gives 170 Mbyte/s, which clears 1000BASE-X with margin; the two encoders are independent except that the second must take the first's updated disparity, so the disparity path becomes the critical path. PCIe Gen2 needs six bytes per clock at this frequency, which on this fabric is not the right answer — that part belongs on a faster process.
How this is got wrong. The tempting sentence to write was ‘comfortably past gigabit Ethernet’ — it was in the first draft of this page, and it was wrong by a factor of 1.5. 84.9 MHz sounds fast, and a block being small and clean invites the assumption that it is also fast enough. Neither area nor cleanliness implies throughput; only the arithmetic does. The same draft also multiplied 84.88 by 8 and got 686 instead of 679.

So the honest positioning is: on this FPGA, at one byte per clock, the block is a demonstration rather than a shippable PHY. Widened to two bytes per clock it is a plausible 1000BASE-X part. PCIe Gen2 is a different process, not a different day of optimisation. A datasheet that says that is more useful than one that quotes 84.9 MHz and leaves the division to the reader.
