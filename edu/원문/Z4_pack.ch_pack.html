Generated at build time. Part Y10 computed that maintaining six copies by hand over a nine-month project has an expected nine missed edits; the generator is a day's work and removes all nine.
The map validates itself, and that is most of the value. The definition refuses overlapping bit ranges, offsets that are not word-aligned, reset values too wide for their field, unknown access types, duplicate offsets, and — the one that matters most — a hardware-written field declared RW, which is the read-modify-write race of Part Y10. Each of those is a defect that a hand-written map produces regularly and that nothing downstream detects: the RTL compiles, the header compiles, the documentation looks right, and the bug appears in the customer's driver.

Z4.4 Three generator bugs the gate found

The register-map generator was written from Part Y10's argument and looked correct. The agent and the gate found three defects in it, none of which any amount of reading would have found, and each is instructive about a different failure mode.

Table 509. What was found, and by which gate
BugFound byWhy reading would not have found it
An ID register could not hold a constant. Every RO field was wired to a hardware input, so a vendor code read as zeroThe regression, against an independent modelThe generator was internally consistent — it did exactly what its author intended, and the intention was incomplete
A read-clear register cleared during the APB setup phase. rd was psel & ~pwrite, missing penableThe regression, after the stimulus was extendedIt reads as correct; the defect is in the protocol's two-phase timing, which only a running comparison exposes
A software-set field had an unused hardware port. W1S defaulted to hardware-driven, which is wrong for the common caseverilator -Wall (UNUSEDSIGNAL)An unused port is harmless functionally and is a question the integrator has to ask you
And the mutation score found the stimulus hole that hid the second one. Before it ran, the register-file regression was green on 400 accesses and scored 58.3 %. Five escapes all pointed at the same place: the hardware-side inputs were tied to zero, so the W1C and RC paths had never executed. Driving them turned up two real failures within minutes. The green regression was not wrong — those 400 accesses did match — and it was nearly worthless. That distinction is the whole argument for measuring whether a suite bites rather than whether it passes.
Problem. You have one week before a customer evaluation. What do you build first?
Solution. Not more features. Build, in this order, the things the evaluation will actually test. First the gate, because everything else is easier to trust once one command produces the numbers; a day. Then the mutation score, because it is the single artefact that distinguishes you from a supplier who says ‘we tested it thoroughly’, and because it will find the stimulus holes you do not know about; half a day plus whatever it turns up. Then the known-issue list, which costs an afternoon and is read as competence rather than as weakness. Then the integration guide, written as if for someone you will never speak to. Only then the datasheet, because by that point every number in it exists and is reproducible — which means writing it takes an hour instead of a day and none of it is invented. A week spent this way produces a smaller block that can be bought; a week spent on features produces a larger one that cannot.
