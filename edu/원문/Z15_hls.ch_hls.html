Z15. HLS — What It Costs, and How to Make It Win

High-level synthesis has two well-known drawbacks. The first is that it does not always compile what you give it. The second is quality of results: the generated RTL can use noticeably more of the device than RTL a person would have written. Both are real, and both are measured in this part on a filter that exists in this repository.

But “generated RTL is worse than hand RTL” is not a law. It is what happens when the C++ is written as if it were software. If you understand the specification, the architecture you actually want, and what the HLS tool does with what you wrote, the generated RTL can beat hand-written RTL — and below it does, by 1.38× in clock frequency. The rest of this part is how.

Z15.1 Drawback one: what the tool refuses

Before any quality question there is a compile question. These are one-variable controls run against PandA Bambu 2024.10 in this container: each row changes exactly one thing from the row above, so the cause is not inferred.

Table 451. What Bambu accepts and refuses — one-variable controls
ControlWhat changedResult

Control 2 is the important one: the same file, one line added, a hard failure. The blocker is not C++ and not the algorithm — it is the pragma dialect. Every vendor has its own, and pragmas are exactly the part of an HLS source that does not port. Control 4a is the pleasant surprise: Xilinx's arbitrary-precision integer type compiles fine on a tool that has nothing to do with Xilinx, because it is ordinary C++ templates. Control 4b is the unpleasant one, and it has no workaround.

The design rule that falls out of this table, and the one edu/model/ipmodel.h follows: put the algorithm in portable C++ and keep every tool-specific thing out of it. No pragmas in the header, no vendor stream types, no heavy template arithmetic. Then the same header compiles under g++ as the golden model and under the HLS tool as the design, and retargeting to a different HLS tool is a build-script change rather than a rewrite.

Z15.2 Drawback two: quality of results, measured

The filter is four taps, 8-bit samples, constant symmetric coefficients. Written naturally in C++ — int parameters, int accumulator, the way anybody would write it — and handed to Bambu, it produces this:

Worked example 76. Where a 4-tap filter's 890 LUTs came from
Given. A 4-tap FIR with constant coefficients needs, by hand, about 200 LUT4 on this device. The naive HLS version used 890.
Method. Compare the two rows above. The algorithm is identical — the same header, the same arithmetic, verified bit-identical. Only the C parameter types differ.
Numbers. 3.60× reduction (1,218 cells to 338) from changing int to signed char in the function signature. Nothing else changed.
This is the single largest QoR lever in HLS and it costs one line. It is also the first thing to check when generated RTL comes back four times too big.
How this is got wrong. The tempting explanation is “HLS tools are bloated.” It is not that. C's integer promotion rules widen char and short operands to int before arithmetic, so a C++ source that says int is requesting a 32-bit datapath and 32-bit ports. The tool built what the source asked for. A person writing Verilog types [7:0] and cannot make this mistake — which is most of why naive HLS loses to hand RTL.

Z15.3 Making the comparison honest

Three things had to be fixed before any number in the next table meant anything. Each of them, left unfixed, produces a confident and wrong result.

Table 453. Three ways this comparison was wrong before it was right
ProblemSymptomFix
The two designs computed different functionsNone — area numbers looked fine and meant nothingVerify both against the same C++ golden vectors first. Every design in the next table passes 400 vectors with 0 mismatches.
Reset polarity differedThe generated RTL never asserted done; 400/400 “failed”Bambu defaults to active-low reset; the hand RTL used active-high. --reset-level=high --reset-type=sync.
Frequency was measured on the wrong pathAdding pipeline registers made Fmax fall (324 MHz → 74 MHz), and the hand RTL reported no frequency at allnextpnr reports register-to-register paths only. Wrap every design in an identical registered timing shell (fir_shell.v) so the path being measured is the datapath.

The third deserves emphasis because it is the kind of error that survives review. The numbers before the fix were not noise — they were stable across seeds and they were monotonic in the wrong direction. A stable, reproducible, completely meaningless measurement is the most dangerous kind, because every instinct says to trust it. What made it visible was not a tool warning; it was noticing that more registers cannot make a design slower, and refusing to write the number down until that contradiction was explained.

Worked example 77. Does the generated RTL beat the hand-written RTL?
Given. Hand-written 3-stage pipeline: 256 LC at 76.9 MHz, latency 3. Best HLS point (HLS clock=3ns): 386 LC at 105.9 MHz, latency 9.
Method. Compare each axis separately. There is no single QoR number; area, frequency and latency trade against each other.
Numbers. Frequency: 1.38× better. Area: 1.51× worse. Latency: 3.0× worse.
So the answer is: yes on frequency, no on area and latency, and only at one point in the sweep. Anyone quoting the 1.38× without the 1.51× area and 3× latency is selling, not measuring.
How this is got wrong. Two trivial explanations had to be killed. First, that the hand RTL was a straw man: the comparison is against a hand-written pipelined design, not the single-cycle one, precisely so the answer is not rigged. Second, that tightening the constraint always helps: it does not. At 2 ns and 1 ns the generated design is both larger and slower than at 3 ns. The knee is at 3 ns and you only find it by sweeping.

Z15.5 The method — how to get better QoR than hand RTL

The 1.38× did not come from the tool being clever. It came from four things, in this order. Each is a thing you do, not a thing the tool does.

Why the generated RTL could win at all
StepJustification
1Write the interface at the true width, not the C default.Measured above: 3.60× area from this alone. Until this is done, nothing else matters — the design is four times too big and every later measurement is taken on the wrong design.
2Express the architecture you want, not just the arithmetic you want.The folded form computes h0(x0+x3)+h1(x1+x2): two multipliers instead of four. The tool will not discover the symmetry; you state it, and equiv.cpp proves you stated it correctly.
3Let the tool re-schedule, and sweep the constraint.One number, --clock-period, produced five different microarchitectures with latencies 2, 4, 9, 12 and 18 cycles. In hand RTL each of those is a redesign; here each is a rebuild.
4Pick the knee from the sweep rather than the tightest point.The best frequency is at 3 ns, not at 1 ns. Constraining harder past the knee adds registers that the fabric cannot exploit, so area rises and frequency falls.

Step three is where the structural advantage lives, and it is worth being precise about what it is. The tool is not out-scheduling a human. A human given a week could hand-pipeline this filter to 3 ns and would probably land smaller than 386 LC. The advantage is that the sweep above cost four rebuilds and no design work, so five architectures were evaluated instead of one. Hand RTL usually gets pipelined once, for one target, because re-pipelining is expensive and risky; it then stays that way when the target moves. The generated design is re-derived from the specification every time.

That is the real claim, and it is narrower and more useful than “HLS beats hand RTL.” Hand RTL beats HLS at a point you have already designed for. HLS beats hand RTL at a point you have not. In a one-person design house, where nobody has a week to re-pipeline a block because a customer moved the clock from 75 to 100 MHz, the second case is the one that keeps happening.

Z15.6 Where this result stops being true

Stating the conditions under which a measurement flips is not a disclaimer; it is part of the measurement. This one flips under any of these:

Table 455. Invalidation conditions for Z15.4
ConditionWhy the result changes
A different fabriciCE40 has no DSP blocks usable here, so constant multiplies became LUT shift-adds. On a device with hard multipliers the area picture changes completely.
Wider data or more tapsAt 4 taps the hand design is small enough for one person to hold in mind. The argument for HLS gets stronger with size, but this table does not prove that — it was not measured here.
A hand design with more than 3 stagesThe comparison is against a 3-stage hand pipeline. A 6-stage hand pipeline would likely beat the 3 ns HLS point on both axes. What it would cost in engineer-days is not in the table.
A different HLS toolBambu's scheduler is not Vitis HLS's. The pragma dialect result in Z15.1 guarantees the sources are not portable unchanged.

The last row is the one to plan around commercially. An IP built on one HLS tool's pragmas is tied to that tool. An IP built the way edu/model/ipmodel.h is built — portable C++, tool-specific settings on the command line — is not, and that portability is worth more than the few percent a vendor pragma might buy.
