X37. Bus Protocols: Ordering, Outstanding Transactions and Exclusives

Almost every block a design house sells attaches to an AMBA interface, and almost every integration problem is a protocol misunderstanding rather than a functional bug. The protocol's subtle points are few and they recur; this part works through them.

X37.1 The handshake, and the one rule that is always broken

VALID/READY, and why VALID may not wait
StepJustification
1A transfer occurs on a rising edge when VALID and READY are both high.The basic handshake, shared by AXI, AXI-Stream, TileLink and CHI.
2Once VALID is asserted it must stay asserted until the transfer occurs, and the payload must not change.Otherwise the receiver cannot rely on what it sampled.
3VALID must not depend combinationally on READY.This is the rule that is broken. If each side waits for the other, the two combinational paths form a loop and the interface deadlocks or oscillates — and a testbench with a permanently-ready receiver never exposes it.
4READY may depend combinationally on VALID.The asymmetry is deliberate: it lets a receiver accept in the same cycle, which is where the throughput comes from.
5A registered-output, registered-ready skid buffer breaks any timing path across the interface at the cost of one cycle and two entries of storage.The standard remedy, and the right default for an IP boundary — Part X14's advice to register every boundary, in protocol form.
The testbench that hides this bug is the default one. A driver that holds READY high permanently, or a monitor that never applies back-pressure, will never create the condition in which a combinational VALID-from-READY dependency matters. Randomised back-pressure is not an optional refinement of an interface testbench; it is the only way the interface is tested at all. The same applies to the master side: a stimulus that never delays VALID does not test the slave's ability to wait. Both are one line of constrained randomisation and both routinely go missing.

How this is got wrong. By choosing one extreme. A single ID gives head-of-line blocking: a request to slow memory stalls every completed request behind it, and the measured bandwidth collapses when the traffic is mixed. Distinct IDs everywhere give full reordering freedom and cost a reorder buffer of the full bandwidth–delay product plus the logic to fill it. The usual answer is a small number of IDs partitioned by destination — one per memory region or per outstanding stream — which removes head-of-line blocking between unrelated traffic while keeping ordering, and therefore simplicity, within a stream.

X37.3 Exclusive access, and why it is harder than it looks

Load-linked / store-conditional in bus form
StepJustification
1An exclusive read records a monitor for that address and master.AXI's ARLOCK exclusive, or the processor's load-linked.
2An exclusive write succeeds only if the monitor is still set.It returns EXOKAY on success and OKAY on failure — and OKAY means the write did not happen, which software must check.
3Any intervening write to the address by anyone clears the monitor.That is what makes it atomic.
4The monitor is in the slave or the interconnect, not the master.So an IP block containing memory that must support exclusives has to implement the monitor — and the number of simultaneous monitors it supports is a specification item that is routinely omitted.
5Monitors may be granted at a granularity coarser than one address.Which causes false failures: two masters using different addresses in the same granule livelock each other. The granule size must be documented.
6Spurious failure is always permitted, so software must loop.Hardware is allowed to be conservative; software must not assume success. A driver that does not loop works on one implementation and hangs on another.
Atomics moved from the master to the interconnect, and an IP vendor should know which era their customer is in. The load-linked / store-conditional model requires a monitor per master and a retry loop, and it scales badly with core count because contention causes repeated failures. Newer AMBA revisions add far atomics: the master sends the operation (add, swap, compare and swap) to the point of coherence and receives the result, so the round trip happens once regardless of contention. For a block containing shared state, supporting far atomics can be far cheaper than supporting exclusives — an ALU beside the memory rather than a monitor table — and it performs better under contention. Asking the customer which their system uses is a scoping question worth raising early.
Problem. Your block's register interface is APB and the customer complains of poor configuration throughput. What do you say?
Solution. That APB is doing exactly what it is for, and then offer the two real options. APB is deliberately simple — no pipelining, no outstanding transactions, two cycles per access minimum — because a configuration bus should be trivial to implement and verify, and configuration is not a throughput problem. If the customer is writing thousands of registers at boot and it matters, the causes are usually not the bus: a slow bridge clock ratio, a synchroniser per access, or software doing read-modify-write where a write would do. Measure before changing the interface. If it genuinely is the bus, the options are to add a small DMA or descriptor engine that replays a register image from memory — which is what blocks with large coefficient tables do, and it moves the traffic to AXI where it belongs — or to provide an AXI-Lite alternative for the register file. Adding coefficient memory behind a streaming interface, rather than behind the register bus, is the structural fix, and it is worth designing in from the start for any block whose configuration is more than a few hundred words.
