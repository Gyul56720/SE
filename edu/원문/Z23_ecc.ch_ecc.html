Z23. The Packet Header ECC — Why Headers Get More Than Payloads

A MIPI CSI-2 short packet is four bytes: one Data Identifier, two Word Count, one ECC. A long packet adds a payload and a 16-bit CRC at the end. So the header gets an error-correcting code and the payload gets a merely error-detecting one, and the header's code costs a quarter of the header's own size.

That asymmetry looks wasteful until you ask what each failure costs. This part builds the header code, proves it, and puts it on silicon.

Z23.1 Why the header is worth more protection

Why a 1-bit header error is not a 1-bit problem
StepJustification
1The header's Word Count says how many payload bytes follow.The receiver has no other way to find the packet boundary; CSI-2 packets are not self-delimiting.
2A single bit flipped in Word Count changes that length — by 1, or by 32768 if it lands in the top bit.Binary weighting means the damage is not proportional to the number of bits flipped.
3The receiver then looks for the next packet header at the wrong offset.It reads payload bytes as a header, whose ECC will not check, whose Word Count is garbage.
4The error does not stop. Every subsequent packet in the frame is misaligned.One bit has cost an entire video frame, and possibly re-synchronisation time beyond it.
5Whereas a single bit flipped in the payload corrupts one pixel.The CRC flags the packet as bad; the frame is imperfect but its structure survives. An ISP can interpolate one pixel.
6Therefore: correct the header, merely detect on the payload.The cost asymmetry is thousands to one, so the protection asymmetry is justified. This is the same reasoning that puts ECC on DRAM address lines before data lines.

Z23.2 What SEC-DED means, precisely

Table 497. Three codes, three guarantees

Extended Hamming SEC-DED (6 bits)correcteddetected, not corrected6 bits

The middle row is the trap, and it is why the sixth bit is not optional. A plain Hamming code always produces a syndrome that names some bit, so given a 2-bit error it confidently flips a third one. You end up worse off than with no ECC at all. The extra overall-parity bit is what lets the decoder say “I do not know” — the same distinction this repository insists on everywhere else, here implemented in six wires.

Worked example 89. How one extra bit buys double-error detection
Given. 5 Hamming parity bits give each of the 30 bit positions a distinct 5-bit syndrome. Add a 6th bit that is the parity of the entire codeword.
Method. Work out what each error class does to the syndrome and to the overall parity, separately.
Numbers. A single error flips an odd number of bits, so overall parity becomes 1, and the syndrome is non-zero and names the bit. A double error flips an even number, so overall parity returns to 0, while the syndrome (the XOR of two distinct non-zero syndromes) is still non-zero. So syndrome non-zero with parity 0 is a signature no single error can produce.
That bug is instructive because it is conservative: it never corrupts data, it just declines to fix things it could have fixed. In the field it would look like an unexplained doubling of the dropped-frame rate, with no corrupted output to point at — the kind of defect that gets blamed on the cable for a year.
How this is got wrong. The decoder must compute overall parity directly from the received codeword, not by re-encoding the received data and comparing the 6th bit. Re-encoding folds the syndrome's own parity into the comparison: the result is 1 XOR parity(syndrome), which is 0 for every data bit whose syndrome has odd weight. Measured — the first version of ecc24_dec did exactly this and reported 90 of 180 single errors as double errors, i.e. refused to correct half of the correctable ones.

Z23.3 Constructing the code

Part Z21 explained why the remembered MIPI parity masks were discarded: counted before use, they produced 27 distinct syndromes out of the 30 required. So the code here is built from first principles instead, and is not byte-compatible with CSI-2. The construction is four lines:

# 24 데이터 비트에 신드롬을 배정한다.
# 무게 1 짜리 패턴은 **패리티 비트 자신의 오류**가 쓰므로 데이터에 주면 안 된다.
cand = [s for s in range(1, 32) if bin(s).count('1') >= 2]   # 26 개
syn  = cand[:24]                                             # 24 개만 쓴다

# 패리티 i 의 마스크 = 신드롬의 i 번째 비트가 1 인 데이터 비트들
masks = [[b for b in range(24) if (syn[b] >> i) & 1] for i in range(5)]
Why the syndromes must have weight ≥ 2
StepJustification
1Each parity bit can itself be corrupted in transit.The ECC field travels over the same lanes as the data.
2If parity bit i flips, the recomputed syndrome is 2i — a weight-1 pattern.Only that one parity check disagrees.
3So the five weight-1 patterns are already spoken for, and no data bit may be assigned one.Otherwise a flipped parity bit and a flipped data bit look identical, and the decoder corrupts good data trying to fix a parity bit that nothing depends on.
4Of the 31 non-zero 5-bit patterns, 26 have weight ≥ 2, and we need 24.It fits, with two spare. Had we needed 27 data bits, 5 parity bits would not have been enough.
5Verified rather than argued: all 29 syndromes distinct, none zero, no double-error syndrome colliding with a single-error syndrome.29/29, 0 인 것 없음

Six representative data values rather than all 224, because the code is linear: the syndrome of a corrupted codeword depends only on the error pattern, not on the data underneath it. That is a property worth stating rather than assuming, so the six values span all-zeros, all-ones and four irregular patterns, and they all agree — which is the evidence that linearity holds in the implementation and not merely in the theory.

Z23.5 The circuit is a pile of XOR trees

// `^(vector)` 는 리덕션 XOR -- 모든 비트를 XOR 한다.
// 이 한 글자가 14입력 XOR 나무 하나다.  C++ 에는 이런 연산자가 없다.
wire [4:0] p;
assign p[0] = ^(data_in & M0);
assign p[1] = ^(data_in & M1);
assign p[2] = ^(data_in & M2);
assign p[3] = ^(data_in & M3);
assign p[4] = ^(data_in & M4);
wire p5 = (^data_in) ^ (^p);

// 신드롬 -> 비트 자리.  각 데이터 비트의 신드롬은 그 비트가 어느 마스크에
// 들어 있는가로 정해진다.  전부 상수라 합성기가 통째로 푼다.
genvar g;
generate
    for (g = 0; g < 24; g = g + 1) begin : gen_fix
        wire [4:0] s_g = { M4[g], M3[g], M2[g], M1[g], M0[g] };
        assign fix[g] = (syn == s_g) & opar & (syn != 5'd0);
    end
endgenerate
assign data_fixed = data_in ^ fix;

Three things in that fragment are worth naming. The reduction XOR (^vector) has no C++ equivalent and collapses a 14-input parity tree into one character — Part Z18.6 lists the others. The generate loop builds 24 comparators whose right-hand sides are all compile-time constants, so synthesis evaluates s_g away entirely and what remains is 24 five-bit constant comparisons. And the block is named (gen_fix) because an unnamed generate block gets called genblk1, and every constraint and waveform that references it breaks the day somebody inserts another loop above it.

68 LUTs, zero flip-flops, and it corrects any single-bit error in a camera packet header. For comparison the 8b/10b encoder of Part Z22 is 74 LUTs. Both are small enough that the interesting engineering is entirely in the verification and the specification, not in the gates — which is the usual situation for protocol IP and the reason Parts Y and Z4 spend so much more time on deliverables than on RTL.

The stimulus mix in that table is the part most easily got wrong. A regression built from random headers contains no bit errors at all, so it exercises only the ECC_OK path — the correction logic, which is the entire point of the block, would never run. Errors have to be injected, and injected in the proportions you care about.

Z23.7 Swapping in the real masks

Because the construction is separated from the structure, making this block CSI-2 interoperable is a table change, not a redesign:

And the proofs are exactly what you re-run after the swap, because a transcription error in five hex constants is precisely the failure this part opened with. The value of having built the harness first is that checking somebody else's constants costs one command.
