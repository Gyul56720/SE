X41. DRAM: The Timing That Shapes Every Memory Controller

Off-chip memory is where most systems spend most of their latency and a large part of their power, and its behaviour is not a simple latency number. A DRAM device is a state machine with a dozen timing constraints, and whether your block gets the bandwidth it was promised depends almost entirely on its access pattern rather than on the interface's rated speed.

X41.1 The bank, the row and the reason access order matters

Why a DRAM read is three operations, not one
StepJustification
1A DRAM array stores each bit as charge on a capacitor, read by dumping it onto a bit line.The read is destructive — the charge is consumed.
2ACTIVATE opens a row: the whole row is sensed into the sense amplifiers, which form the row buffer.Thousands of bits at once. This takes tRCD.
3READ or WRITE then accesses columns within the open row.Fast — the data is already in the sense amplifiers. A second access to the same row is far cheaper than the first.
4PRECHARGE writes the row back and restores the bit lines.Takes tRP. Required before opening a different row in the same bank.
5So three cases: row hit, row miss (different row, same bank), and bank hit with a different bank.Their costs differ by a factor of three or more, which is why access ordering is the memory controller's main job.
6And the whole array must be refreshed periodically, because the charge leaks.Refresh steals bandwidth and blocks access to a bank while it runs.

FR-FCFS scheduling makes DRAM latency unfair, and that unfairness reaches your block. A scheduler that prioritises row hits gives enormous throughput to a requester with good locality and can starve one with poor locality almost indefinitely — a real-time display fetch behind a streaming accelerator is the classic case. Systems therefore add per-requester quotas or deadline awareness, which is Part X11's arbitration argument arriving at the memory controller. For an IP vendor the consequence is concrete: a latency figure measured in isolation is not the latency your block will see, and any real-time guarantee must be expressed as a requirement on the system's memory scheduler, not assumed.

X41.3 Refresh, and why it gets worse

Worked example 40. What refresh costs at each density
Given. DDR4 requires all rows refreshed every 64 ms (32 ms above 85 °C). Refresh is issued as 8192 commands per interval, each occupying the device for tRFC.

How this is got wrong. By assuming refresh is a rounding error. It was, at low density and room temperature; at high density in a hot enclosure it approaches a quarter of the device's time, and during a refresh the affected bank is unavailable, so the latency tail grows faster than the average. Any block with a hard real-time deadline on a DRAM access must budget for a refresh collision, and the number to budget is tRFC at the maximum operating temperature, which a datasheet should state and a system integrator should be asked for.
Problem. Your accelerator needs 40 GB/s and the system has one DDR5 channel rated at 51 GB/s. Is that enough?
Solution. Almost certainly not, and the calculation to show it is short. Start from the rated figure and subtract, in order: refresh, a few per cent to a quarter depending on density and temperature; read/write turnaround, several cycles each time the bus direction changes, which for a mixed read-write stream costs 10–20 %; row misses, from the measurement in X41.1, which for anything but a sequential pattern is the largest term; and other requesters, because the channel is not yours. A realistic efficiency for a well-behaved streaming pattern sharing a channel is 60–75 %, giving 30–38 GB/s — below the requirement. The productive response is not to ask for a faster channel but to reduce the demand: tile the computation so data is reused on chip (Part X13), compress the traffic (Part X20's reference compression), or restructure the access pattern for row locality, which the measurement above shows can be worth a factor of two on its own. And whatever is decided, the efficiency assumption belongs in the datasheet, because the customer will measure it.
