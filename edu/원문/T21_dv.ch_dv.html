T21. The Verification Environment — What It Proves

Coverage says you tried it. Only the checker says it worked. Confusing the two is the most expensive mistake in verification.

Everything after this chapter's stage in the flow assumes the RTL is right. Synthesis will faithfully implement a bug; place-and-route will close timing on it; signoff will certify that it is manufacturable. Verification is the only stage that can answer whether the design does what it was supposed to do, and it is the stage that consumes the most engineering effort on almost every project. This chapter is about the structure that effort takes, and about the one distinction that decides whether the effort was worth anything.

T21.1 The structure, and why it is split the way it is

표 54. Each component, and the one question it answers
ComponentAnswersWhy it is separate from its neighbour
SequenceWhat transactions should happen?It is written per test and knows nothing about pins — so the same sequence runs on a different bus protocol
SequencerIn what order, when several sequences compete?Arbitration is a policy, and policies change per test while drivers do not
DriverHow is one transaction expressed on the wires?It is the only component that knows the protocol's timing. Everything above it is protocol-agnostic
MonitorWhat actually happened on the wires?It must be independent of the driver. A monitor that trusts the driver's intent cannot detect a driver that drove the wrong thing
ScoreboardWas it correct?It holds the reference model. It is the only component whose failure means the DUT is wrong
Coverage collectorWhat did we try?It must not judge. Mixing coverage and checking produces a testbench that reports 100 % of nothing
Config objectWhich of the above exist, and how are they set up?So that one environment serves a block, a subsystem and the chip, with the agents that do not apply turned off rather than deleted
가상 인터페이스 (virtual interface) — the one construct with no software analogue

The testbench's driver and monitor are class objects: created at run time, garbage-collected, passed around by handle. The pins they must wiggle belong to a module instance, which is created at elaboration and exists for the whole simulation. A class cannot hold a reference to a static elaborated object directly, because at the time the class is written the instance does not exist.

A virtual interface is the bridge: a handle, held by the class, pointing at an interface instance that was elaborated. The testbench's configuration step sets it, and after that the driver can drive real pins from dynamic code.

The most common failure in a new environment is a null virtual interface — the driver was built before anything assigned it. It is not a subtle bug, but it is unfamiliar, because no ordinary software language has this split between two object lifetimes.

어디에 쓰나Every agent that touches the DUT.
언제 쓰나Set during the build/connect phase, before any sequence runs.
어떻게 쓰나Assign it from the top-level module into the configuration database, and have every driver and monitor fetch it during build — then assert that it is non-null rather than letting the first pin access fail with a null-handle error a thousand cycles later.
실제 코드는 이렇게 생겼다
// Top level, where both worlds meet:
my_if  dut_if (.clk(clk));                 // elaborated: exists for the run
my_dut u_dut  (.p(dut_if));

initial begin
  // Hand the elaborated thing to the dynamic world, by name:
  uvm_config_db#(virtual my_if)::set(null, "*", "vif", dut_if);
  run_test();
end

// In the driver's build phase -- and check it, do not assume it:
if (!uvm_config_db#(virtual my_if)::get(this, "", "vif", vif))
  `uvm_fatal("NOVIF", "virtual interface was never set")
여기서 틀린다. Clocking blocks matter here: driving a DUT input from the testbench without one races with the DUT's own evaluation at the clock edge, and the race is resolved differently by different simulators. A testbench that passes on one simulator and fails on another is almost always a missing clocking block, not a tool bug.

T21.2 Coverage is a measure of stimulus, not of correctness

기능 커버리지 (functional coverage) · 커버포인트 · 크로스 — A coverpoint samples a value and sorts it into bins; a covergroup collects coverpoints and is sampled at a defined event; a cross is the set of bin combinations of two or more coverpoints. Coverage is the fraction of bins that have been hit at least once. Note what that definition does not contain: any reference to whether the design behaved correctly when the bin was hit.
100 % functional coverage with a scoreboard that never fires is 100 % evidence of nothing. Coverage answers 'did the stimulus reach this situation'. Correctness is answered only by the scoreboard and the assertions. The two are reported side by side, they look similar, and they measure entirely different things — and a green coverage report is the most persuasive way to ship a bug, because it is a number, it is high, and nobody asks what it counted.
실제로 난 일
A block shipped with every covergroup at 100 %. The scoreboard's compare method had an early return added during debugging and never removed: it checked the first beat of each burst and silently passed the rest. Every bin was hit. Nothing was compared. The escape was found by a customer, and the testbench that missed it had a perfect coverage report throughout. The check that would have caught it is not more coverage — it is a mutation test: change one bit of the DUT's output and confirm the scoreboard goes red.
자해 검사 (mutation testing) for a testbench

A testbench is a program that is supposed to fail when the design is wrong. Nothing in a normal regression ever exercises that property — every run is against a design that is (by then) right, so the failure path is never taken.

The fix is to break the design on purpose: invert a bit in a response, drop a transaction, delay a handshake by one cycle, corrupt a byte in the middle of a burst. Then run the regression and confirm it goes red, and confirm which check caught it. A mutation nothing catches is a hole in the checking, located precisely.

This is the same discipline that this book applies to its own numbers: a measurement that cannot come out wrong has not measured anything.

어디에 쓰나Every environment, at least once per major block, and in CI if you can afford the runtime.
언제 쓰나Before believing a coverage report. A mutation campaign is the only evidence that the coverage number is attached to a checker at all.
어떻게 쓰나Keep a list of mutations as a file, each with the check that is expected to catch it. Run them; a mutation caught by no check, or caught only by a timeout, is a finding.
실제 코드는 이렇게 생겼다
# mutations.txt -- and the expected catcher, which is the real content
#   id  mutation                          expected catcher
#   m1  invert resp[0]                    scoreboard data compare
#   m2  drop every 8th write              scoreboard transaction count
#   m3  delay ready by 1 cycle            protocol assertion a_ready_stable
#   m4  return wrong burst length         scoreboard length compare
#   m5  corrupt byte 3 of burst           scoreboard data compare
#
# Result column after the run. Any row whose catcher is "none" or
# "test timeout" is a hole -- a timeout means nothing noticed, it just
# stopped.
여기서 틀린다. A mutation caught by every check is not a good result either — it means the mutation was too coarse to locate anything. The useful mutations are the ones caught by exactly one check, because those map a check to the failure it is responsible for.

T21.3 Why crosses explode: the arithmetic of random closure

유도 — How long random stimulus takes to fill K bins
이렇게 된다왜냐하면
1Assume each test lands in one of K bins, uniformly and independently.The assumption to argue with. Real constrained-random stimulus is neither uniform nor independent — but this case is the optimistic one, so what it computes is a lower bound on the effort.
2With j bins already hit, the chance a test hits a new one is (K−j)/K.Counting. The remaining bins are K−j of the K.
3So the expected number of tests to go from j to j+1 is K/(K−j).A geometric waiting time has mean 1/p.
4Summing over j = 0…K−1 gives K·(1 + 1/2 + … + 1/K) = K·HK.Expectation is additive even though the waits are not independent of each other's outcomes.
5HK ≈ ln K + 0.577, so the cost is about K·ln K.Slightly worse than linear in the number of bins — which is fine. The problem is not this factor; it is that K itself is a product when you cross.

The two columns are computed by different means — a summed series and an actual repeated drawing that uses none of it — and they agree to within a few per cent, with the residual being the Monte-Carlo sampling error at 300 trials for the largest case. That is what licenses the last row, which is the one that matters: crossing two 100-bin coverpoints makes K = 10,000 and turns a 518.7-test job into a 97,876.1-test one. A cross is not a small addition to a coverage model; it is a multiplication of the closure effort.

The uniform calculation understates the problem badly, because random closure is governed by the rarest bin, not the average. The last rows are the quantitative reason directed tests still exist in a constrained-random flow: a corner with probability 10⁻⁶ under the constraints will not be reached by adding machines. It is reached by changing the constraints for one test, or by writing that test by hand — and either way, by someone deciding it matters, which is a design decision and not a verification one.
예제 9. Should we add this cross?
주어진 것. A proposal to cross 'transfer size' (8 bins) with 'address alignment' (4 bins) with 'outstanding transactions' (16 bins).
푸는 법. K = 8 × 4 × 16 = 512. Under uniform random stimulus that is about 3,490.1 tests to fill. But check the legality first: a 1-byte transfer cannot be 8-byte-misaligned, so a good fraction of the 512 bins are unreachable by construction.
답. Add it, with the illegal combinations declared illegal_bins rather than left empty. The reachable count is what closure is measured against; leaving 512 as the denominator guarantees the report never reaches 100 % and trains everyone to ignore it.
Declaring illegal bins has a second benefit that is worth more than the first: an illegal_bins that fires is an immediate error. It turns a statement about what cannot happen into a check that it did not.
여기서 틀린다. The trap is the opposite of the obvious one. The danger is not that the cross is too expensive — it is that an un-pruned cross produces a coverage number that can never reach its target, and a target that is known to be unreachable stops being a target. An honest 100 % over reachable bins is worth more than an honest 87 % over a denominator nobody trusts.

T21.4 Knowing when to stop

Coverage closure is a necessary condition for stopping, not a sufficient one. The question a project actually has to answer is different: how many bugs are still in there? That cannot be measured directly, but the rate at which bugs are being found can be, and a decaying rate carries information.

유도 — Estimating the bugs you have not found yet
이렇게 된다왜냐하면
1Suppose the number of new bugs found per week falls by a constant factor q.An empirical observation in many projects, and the assumption this estimate rests on. It is not a law.
2Then the bugs still to come are n·q + n·q² + … = n·q/(1−q), where n is this week's count.Geometric series, the same one as T17's ECO convergence — and it fails the same way when q approaches 1.
3With n = 4 found this week and q = 0.7, that is 9.33 more.Substitution. The number is small enough to be encouraging and uncertain enough to be dangerous, which is why the next step is the important one.
4Now kill the trivial explanation. The rate can fall because bugs are running out, or because effort fell, or because the tests stopped changing.Three causes, one observable. Distinguishing them is not optional — two of the three mean the estimate is meaningless.
5Measure effort and new-stimulus rate alongside the bug count.Constant simulation hours and rising coverage with a falling bug rate is evidence. A falling bug rate with a falling regression count is a measurement of the team's schedule, not of the design.

An estimate whose value is dominated by an unverified assumption should be reported as an assumption, not as an estimate, which is the same rule this book applies to every number in it.

The numbers to carry: filling K bins with uniform random stimulus costs about K·ln K tests, so a cross of two 100-bin points costs 97,876.1 rather than 518.7 — crosses multiply the closure effort, and pruning illegal combinations is therefore engineering rather than tidiness. And a bin with probability 10⁻⁶ takes 1.00000×106 tests to reach once, which is the arithmetic that keeps directed tests alive.

Verification establishes that the design is right. It says nothing about whether a particular piece of silicon was manufactured correctly — that question is answered by a machine with the die in it, and answering it cheaply is the subject of the last chapter.

특허로 가는 길 — 이 주제에서 발명이 일어나는 자리
Verification methodology is published rather than patented — the methodology libraries are open source, which is the point of them. What is filed is around coverage-directed test generation: using the coverage result to steer the constraint solver towards the bins that are still empty, which is a direct attack on the coupon-collector arithmetic computed in this chapter.
