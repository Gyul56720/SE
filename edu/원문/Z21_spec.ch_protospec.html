Z21. Building Protocol IP When You Cannot Get the Spec

Every previous part of this volume built a block whose definition was ours to choose. A protocol block is different: its correctness is defined by a document somebody else wrote, and for the protocols a design house most wants to sell into — MIPI CSI-2, PCIe, Ethernet — that document is expensive, membership-gated, or both.

This part is about what to do then. It is not a workaround chapter. The discipline it describes — separate what you can prove from what you have assumed, and publish the boundary — is the same discipline you need with the spec in hand, because having the document does not mean you implemented it correctly.

Z21.1 The honest starting position

The container this book is built in has no outbound network: a CONNECT to ieee802.org returns 403. So the normative tables for 8b/10b and the MIPI packet-header ECC were not available while the blocks in Parts Z22 and Z23 were written. That is stated first, because everything else in those parts has to be read against it.

There are exactly three things you can do in that position, and only the third is defensible:

Table 489. Three responses to a missing specification
ResponseWhat it producesVerdict
Write the constants from memory and shipA block that looks finished and is wrong in ways nobody will notice until integration.No. This part demonstrates concretely why — three sets of remembered constants were wrong, and one was not even a valid code.
Refuse to build anythingNothing. The structure, the verification harness and the microarchitecture are all independent of the exact table values.No. It throws away the 90 % of the work that does not depend on the document.
Build it, prove everything provable, and publish the boundaryA block that is correct by construction on every property you can state, with a written list of what remains unverified and how to close it.Yes. This is what Parts Z22–Z23 do.

Z21.2 What “provable without the document” means

A protocol constant is not arbitrary. It was chosen to make the code satisfy properties — and those properties are usually stated in the open literature even when the tables are not. That gives you a check with real teeth: assert the properties the constants exist to provide, and test them exhaustively.

Table 490. The two blocks, and what each property buys

8b/10bBijective within each running disparityTwo data bytes encode to the same codeword → the link cannot decode at all.
Running disparity stays in {−1, +1}DC wander on an AC-coupled link → the receiver's slicer drifts off centre.
No more than 5 identical bits in a row, across codeword boundariesThe CDR loses lock. This is the property that caught two of the three defects below.
The comma pattern never occurs in dataThe receiver aligns to a false byte boundary and every subsequent byte is garbage.

No double-error syndrome equals a single-error syndromeA 2-bit error is silently ‘fixed’ into a 3-bit error. Worse than no ECC.

Every one of those is checkable by enumeration on a laptop in under a second, and every one of them failed at least once during this work.

Worked example 85. The defect that would have shipped
Given. The MIPI CSI-2 packet-header ECC parity masks, written from memory, were about to go into both the C++ model and the RTL.
Method. Before writing any code with them, count the syndromes: each of the 24 data bits and 6 parity bits must produce a distinct, non-zero syndrome, or the code cannot even correct single errors.
Numbers. 27 distinct syndromes out of the 30 required, and 96 pairs where a double-bit error is indistinguishable from a single-bit error.
The check that caught it is four lines of Python and it ran before any Verilog existed. The cost of not running it would have been discovered at a customer's integration bench, months later, as ‘your ECC sometimes makes things worse’.
How this is got wrong. The tempting reading is “close enough, it is mostly right.” It is not mostly right — it is not a single-error-correcting code at all. Three of the 24 data bits share a syndrome with another bit, so roughly one single-bit header error in ten would be ‘corrected’ by flipping the wrong bit, turning a recoverable error into a corrupted packet length. A block like this passes a random-data regression perfectly, because random data contains no bit errors.

Z21.4 The pattern in the three 8b/10b defects

Three separate defects in the encoder all had the same root, and it was not a typo. It was a compression rule that was really an unstated hypothesis.

How a good idea became three bugs
StepJustification
1The 8b/10b tables have two columns — one per running disparity. Writing both invites a typo in one column only.A typo in one column is invisible to any check that only exercises the other.
2Observation: most second-column entries are the bitwise complement of the first, and entries with zero disparity appear in both columns unchanged.True for the majority of entries, which is what made it convincing.
3So: store one column, derive the other. Half the table, half the typo surface.This reasoning is correct as far as it goes, and the comment in the first draft said exactly this.
4But ‘zero disparity implies one codeword’ is a hypothesis, not a fact.A 4-bit code with two ones and two zeros has disparity zero — and so does its complement. Both are legal on disparity grounds, so disparity alone cannot pick one.
5What picks between them is run length, not disparity.D.x.3 is 1100 after one six-bit prefix and 0011 after another, because 001111 followed by 1100 puts six ones in a row and breaks the CDR.
6The compression therefore collapsed nine genuinely-distinct table entries into one each, and the property check found it: 1082 run-length violations and 2048 false commas.Then, after fixing the 4-bit tables, 556 violations remained — the same hypothesis was also wrong for exactly one 5b/6b entry, D.07 (111000/000111).

The lesson generalises past 8b/10b: every scheme for not writing something down twice encodes an assumption about why the two copies agree. When that assumption is right, the scheme removes a whole class of error — the register-map generator of Part Z4 and the single-C++-source flow of Part Z14 both work exactly this way. When it is wrong, it replaces typos with a systematic error, which is much harder to see, because every instance is wrong in the same plausible way.

The difference between the two cases is not cleverness. It is whether you checked.

Z21.5 The provenance ledger

The repository already requires this for paper citations (Gate G022): every claim carries how well it was verified. Protocol constants get the same treatment, because they are the same kind of claim.

Ethernet FCS CRC-32 (Part Z1)independently verifiedChecked against Python's zlib.crc32, an implementation written by somebody else from the standard. This is the strongest level available and it is available only because a free reference implementation exists.

Notice how much the last row differs from the rest. Ethernet's CRC-32 is fully pinned down not because the Ethernet standard is easier to read, but because somebody shipped a free, widely-used implementation of it. When you are choosing which protocol block to build first as a one-person house, the existence of an independent reference implementation is worth more than the clarity of the specification — it is the difference between “proven” and “argued”.

Z21.6 What to write in the datasheet

All of the above is worthless if it stays in a commit message. The boundary between proven and assumed belongs on the page the customer reads, phrased without hedging:

## 확인 수준 (Verification status)

이 블록은 다음을 **전수로** 확인했다:
  * 코드워드 528 개가 RD 마다 서로 다르다 (전단사)
  * running disparity 가 -1 / +1 을 벗어나지 않는다
  * 같은 비트가 5 개를 넘게 이어지지 않는다 -- **코드워드 이음 전부에서**
  * 콤마 무늬가 데이터 흐름에 나타나지 않는다

이 블록은 다음을 **확인하지 못했다**:
  * IEEE 802.3 Clause 36 Table 36-1/36-2 와 바이트까지 같은가
    -> 상호운용 시험 전에 그 표로 대조할 것.  구조는 그대로 쓸 수 있고
       바꿀 곳은 `enc8b10b.v` 의 case 문 두 개뿐이다.
  * K.23.7 · K.27.7 · K.29.7 · K.30.7 (일부러 뺐다)
  * 복호기 (이 판은 부호기만이다)

A customer who reads that knows exactly what they are buying and what work remains. A customer who reads “IEEE 802.3 compliant” on a block that was never compared to IEEE 802.3 finds out later, and tells other people.

There is a commercial argument here too, and it is not the obvious one. Publishing the boundary does not make the block look weaker — it makes it look measured, and it is the only version of the claim that survives contact with a reviewer. Every vendor says “compliant”. Almost none says which of their properties were checked by enumeration and which by reading.
