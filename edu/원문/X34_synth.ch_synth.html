X34. Logic Synthesis: What the Tool Is Actually Doing

Synthesis is the step an IP designer has least visibility into and most dependence on. Its behaviour is not arbitrary: it is a sequence of well-defined transformations with known strengths, and knowing them turns ‘the tool did something odd’ into a specific diagnosis.

Technology mapping is optimal on trees and heuristic on graphs, and that single fact explains most of what a synthesis tool does well. The classic formulation covers a Boolean network with library cells at minimum cost. If the network is a tree, dynamic programming over the nodes gives a provably optimal cover in linear time. Real networks are DAGs with reconvergent fanout, so the tool partitions them into trees at multiple-fanout points, maps each optimally, and accepts that the partition itself was a heuristic choice. The practical consequence is that logic with heavy reconvergence maps worse than logic without it, and that restructuring an expression to reduce fanout — which looks cosmetic in RTL — can measurably change the result.

Sometimes it does, and it cannot in general — proving exclusivity is a Boolean problem it does not always attempt. Writing case, or annotating the chain as parallel, tells it directly. This is the single highest-value RTL coding habit for timing, and it costs nothing; a priority structure should appear only where priority is actually meant, and then the depth is a deliberate cost rather than an accident.

X34.3 Retiming: moving registers without changing behaviour

Why retiming is a graph problem with an exact answer
StepJustification
1Model the circuit as a graph: nodes are combinational blocks with delay, edges carry a register count.The standard retiming model.
2Retiming assigns each node an integer rv: move rv registers from its outputs to its inputs.Registers on edge (u,v) become w + rv − ru.
3Legality requires every edge to keep a non-negative count: ru − rv ≤ w.A system of difference constraints — exactly the structure Part X26 identified as solvable.
4Achieving period P adds more difference constraints between node pairs.Derived from the longest combinational path between them.
5So ‘is period P achievable by retiming?’ is a negative-cycle test, and binary search over P finds the optimum.Polynomial, exact, and implemented in every synthesis tool.
6What it cannot do: change the number of registers on any cycle.The latency around a feedback loop is invariant under retiming, which is why retiming cannot fix a loop that is too long — Part X4's DFE problem is exactly this, and the answer there was unrolling, which changes the graph.
Retiming is exact and is nevertheless often turned off, for reasons worth knowing. It renames and moves registers, which breaks the structural correspondence equivalence checking depends on (Part X33), so verification becomes sequential equivalence checking — a much harder problem that may not complete. It also destroys the correspondence between RTL signal names and netlist nodes, which makes debug and ECOs painful, and it can interact badly with scan insertion and with clock gating. The common compromise is to retime within a clearly delimited pipeline and to verify that block by simulation against its pre-retiming version, rather than enabling it design-wide.
Problem. Synthesis reports your block at 620 MHz against a 700 MHz target. List what you would try, in order of cost.
Solution. Cheapest first, because the early items often suffice. Check the constraints before the design: an over-constrained input delay, a missing multicycle path, or a clock defined without its uncertainty will each produce a believable-looking failure that no RTL change fixes. Read the critical path and classify it — if it crosses a whole datapath it is structural, if it is a long priority chain it is X34.2, if it starts or ends at a boundary it is a constraint issue, and each has a different fix. Try the free restructuring: turn an if-chain into a case, split a wide comparison, move a constant multiplication to a shift-add, precompute something that depends only on slowly changing inputs (Part X9's rule). Then pipeline — one more stage, which costs latency and a verification change and is usually decisive. Then re-architect: parallel slices at a lower rate, which is Part X7's energy argument arriving as a timing fix. What not to do first is instantiate gates by hand; it is slow, it does not port, and the tool is better at it than you are except in the rare case where you know something it cannot — and then you should be telling it, through a constraint, rather than bypassing it.
