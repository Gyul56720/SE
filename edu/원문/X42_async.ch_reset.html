X42. Reset, Initialisation and the States Nobody Simulates

Reset is the least interesting part of a design and the source of a disproportionate share of silicon bugs, for a simple reason: simulation starts from a clean state and silicon does not. This part treats reset with the same seriousness as the datapath, because the failures it causes are the ones that appear only in the lab.

Why de-assertion is the dangerous edge
StepJustification
1A flop with an asynchronous reset has recovery and removal times: the reset must be stable for a window around the clock edge.Exactly analogous to setup and hold, and checked by the same static timing analysis.
2Reset assertion is asynchronous and harmless: the flop goes to its reset value whenever it arrives.There is no race, because the destination is unconditional.
3De-assertion races the clock.If reset releases within the recovery window, the flop may go metastable or may capture the pre-reset value.
4With one clock, the tool checks and fixes it.Recovery and removal are ordinary timing checks.
5With a large design, the reset tree's own skew means different flops leave reset on different cycles.A state machine can then advance while part of its state is still reset, reaching a state the designer never enumerated. This is the classic reset bug and it is invisible in RTL simulation, where reset de-asserts everywhere at once.
6Remedy: synchronise the de-assertion in each clock domain, and treat the reset tree like a clock tree.Balanced, buffered, and timed.
Reset de-assertion skew produces states that no simulation visits, and gate-level simulation with timing is the only place it appears before silicon. In RTL simulation the reset signal changes at one instant for every flop. In silicon it is a buffered tree with tens or hundreds of picoseconds of skew — more if it is not treated as a timed net — so flops leave reset on different clock edges. A counter can start counting while its comparator is still held; a FIFO's write pointer can advance while its read pointer is reset, making the FIFO appear full at power-up. The two defences are structural: synchronise de-assertion per domain so all flops in a domain release on the same edge, and design state machines so that a partially-reset state is not reachable — usually by holding the whole machine in an idle state until an explicit enable.

X-optimism and X-pessimism are both wrong, in opposite directions, and the remedies differ. Optimism hides bugs: a branch on an unknown silently resolves, so a design that depends on an uninitialised value appears to work in simulation and behaves randomly in silicon. Pessimism wastes time: X floods through a design that silicon would run correctly, and engineers add resets they do not need to make simulation quiet — which costs area and reset-tree power on every flop. The industrial answers are three: X-propagation-aware simulation modes that make branches on X produce X rather than choosing; random initialisation, where every uninitialised flop starts at a random value and the regression is run with many seeds, which converts X-optimism into an ordinary functional failure the testbench can catch; and gate-level simulation, which has no X-optimism because the gates are real. Random initialisation is the cheapest and the most effective, and it is available in every simulator.

Given. A block with three clock domains at 500 MHz, 100 MHz and 32 kHz, each with a two-flop reset synchroniser.
Method. Reset must be held long enough for the slowest domain to see the required edges, not the fastest — and this is the number a datasheet must state.

How this is got wrong. By quoting the reset requirement in clock cycles without saying which clock. ‘Assert reset for 16 cycles’ is ambiguous in a multi-clock block and is wrong by four orders of magnitude if the reader picks the fast clock. State the requirement in absolute time, and state it for the slowest clock the block can be configured with — including the case where a clock is stopped, which requires either that reset be held until it starts or that the domain be reset asynchronously and independently.
Problem. Your block occasionally fails to come out of reset, roughly one boot in a thousand. Where do you look?
Solution. The frequency is the clue: one in a thousand is a race, not a logic error, because a logic error would be deterministic. Three candidates, in order. Reset de-assertion recovery: if any domain's reset is not synchronised, de-assertion races the clock and metastability resolves the wrong way occasionally — the rate is computable from Part X3's MTBF formula with the reset edge as the asynchronous event, and one in a thousand boots is entirely consistent with an unsynchronised reset. Clock-before-reset ordering: if reset is released in the same window that a PLL locks or a clock gate opens, some flops see edges and some do not, giving the partial-reset state of X42.1; this shows a dependence on temperature or supply, because they change the lock time. An uninitialised state element that is usually benign: a flop without reset whose value normally does not matter, except in the rare case — and this is what random-initialisation regression is for. The diagnostic that separates them is to vary the reset pulse width and the clock start time: a recovery race moves with clock phase, an ordering problem moves with pulse width, and an uninitialised value moves with neither.
