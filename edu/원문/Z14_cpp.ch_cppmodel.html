Z14. The C++ Model Layer — One Source, Two Destinations

Ask a working design house where its models live and you rarely hear “SystemVerilog.” You hear C or C++. The RTL is what you sell; the C++ is what tells you the RTL is right, and increasingly it is also what generates the RTL. This part builds that layer for real. Every file named here is in this repository, compiles with g++, and is exercised while this page renders.

Z14.1 Why the model is C++ and not Python

Earlier parts of this book used Python golden models (zlib for CRC-32, gf.py for the Galois field). That was right for those blocks: the model existed already, independently, which is the property that makes a golden model worth having. It stops being right the moment the model has to do two jobs:

Table 447. What the model layer has to do, and what language can do it
JobPythonC++Why
Be the verification referenceyesyesBoth express the algorithm exactly.
Run billions of vectorsnoyesMeasured below: 144 M evaluations/s in C++. CPython is ~1000× slower.
Be the HLS inputnoyesEvery HLS tool in industry takes C, C++ or SystemC. None takes Python.
Be bit-accurate to the RTLawkwardyesPython ints are arbitrary precision. Overflow and truncation must be simulated by hand; in C++ the fixed-width types do it.

The third row is the one that changes the architecture of the whole flow. If the model is also the HLS input, then the model and the RTL cannot disagree, because there is only one description:

The conventional flow has three descriptions — a Python model, a C++ HLS source and hand-written RTL — and therefore three chances to disagree. When they disagree, nobody knows which is right, because each was written from the spec by a different person on a different day. The structure above removes two of the three.

Z14.2 The shared header, and why it has no vendor types

edu/model/ipmodel.h declares the fixed-point contract. It deliberately uses int32_t and hand-written saturation rather than ap_fixed or hls::stream. That was not a style choice; it was measured. Part Z15 gives the four one-variable controls that forced it.

// C++ 에서 음수 우시프트는 C++20 이전에는 구현정의지만, gcc·clang 은
// 산술 시프트로 하고 Bambu 도 같다 -- 그래도 기대는 것이 싫어서
// **나눗셈으로 적지 않는다**: 나눗셈은 0 쪽으로 자르고 시프트는 -무한 쪽으로
// 자른다.  둘이 음수에서 다르다.  RTL 은 시프트를 하므로 모델도 시프트다.
static inline int32_t asr(int32_t v, int n) {
    return (v < 0) ? ~((~v) >> n) : (v >> n);   // 부호와 무관하게 floor 시프트
}

// n비트 부호있는 범위로 포화.  자르지(wrap) 않고 **포화**하는 이유:
// 링크 등화기에서 wrap 은 큰 양수를 큰 음수로 뒤집어 슬라이서를 정반대로
// 틀리게 만든다.  포화는 틀려도 같은 부호 쪽으로 틀린다.
static inline int32_t sat(int32_t v, int n) {
    const int32_t hi = (int32_t)((1u << (n - 1)) - 1);
    const int32_t lo = -hi - 1;
    return v > hi ? hi : (v < lo ? lo : v);
}

// 아래 n비트만 남긴다 (부호 없음).  RTL 의 `[n-1:0]` 과 같다.
static inline uint32_t mask(uint32_t v, int n) {
    return n >= 32 ? v : (v & ((1u << n) - 1));
}

Two details in that code are worth the ink, because both are places where a model and an RTL silently part company.

Why the shift is written as a shift and not a division
StepJustification
1The RTL computes acc[16:7] — an arithmetic right shift by 7.That is what the hardware does; a shift is free, a divider is not.
2In C, acc / 128 rounds toward zero. acc >> 7 rounds toward negative infinity.Integer division truncates toward zero by definition (C99 6.5.5); a shift discards low bits, which floors.
3For acc = -1: division gives 0, shift gives −1.−1/128 = −0.0078 truncates to 0; −1 >> 7 = −1.
4So writing the model with division makes it disagree with the RTL on every negative value whose magnitude is below the shift amount.That is roughly half of all small negative accumulator values — common in an equaliser sitting near zero.
5Therefore asr() is written as a shift, with the sign handled explicitly so it does not rely on implementation-defined behaviour.C++ left negative right-shift implementation-defined until C++20.

The second is saturation versus wrapping. A wrap turns a large positive accumulator into a large negative one, which drives the slicer to exactly the wrong decision; a saturate is still wrong but wrong in the same direction. The model saturates because the RTL saturates, and the RTL saturates because the specification says so. All three have to agree or the comparison is theatre.

Z14.3 Proving three architectures equal — by exhaustion

fir.h contains the same filter written three ways: the textbook form, a width-narrowed form, and a symmetry-folded form that uses two multipliers instead of four. They have to compute the same function. Most projects establish that by running a few thousand random vectors and declaring victory. Here the input space is four 8-bit samples, so it has exactly 4,294,967,296 points — and that is small enough to check all of them.

Table 448. Exhaustive equivalence, measured
QuantityValueWhat it means
Input space4,294,967,2962564 — every possible input
Wall time29.7 sg++ -O2, one core
Rate144,419,484/sEach point evaluates all three variants
Disagreements0Not “none found” — none exist
Distinct outputs256All 256 output codes occur, so the check is not degenerate

That last row is the gate this repository puts on every measurement. A comparison that only ever sees one output value has proved nothing, however many vectors it ran. equiv.cpp counts distinct outputs and exits non-zero if there are fewer than two — the same rule the RTL harness applies in Part Z1.

The word “proof” is used carefully. This is exhaustive over the stated input space, which is the combinational function of four samples. It says nothing about the sequential wrapper, the reset behaviour, or the handshake. Those need different arguments — and in Part Z15 one of them costs us a bug.

Z14.4 What verification time actually looks like

“C++ simulates a thousand times faster than RTL” is repeated everywhere and is almost never measured by the person repeating it. Measuring it on this design produces a more useful answer than the folklore.

Table 449. Vectors per second, same algorithm, same machine
PathVectors/sRelativeWhat is included
C++, compute only144,419,4841,616×The arithmetic, nothing else (equiv.cpp)
C++, formatted to a file5,110,45557×Same arithmetic plus printf of five integers
RTL, iverilog + vvp89,3451×Event-driven simulation of the synthesisable design
Worked example 75. Where the speed advantage goes
Given. C++ computes at 144,419,484/s but emits formatted vectors at only 5,110,455/s.
Method. Divide. The ratio is the cost of text formatting relative to the algorithm itself.
Numbers. 28×. Formatting five integers as decimal text costs about 28 times more than computing the filter output.
The practical rule: a C++ reference that talks to the RTL through a text file throws away almost all of its speed advantage. Use the file for the few thousand vectors the RTL will actually run, and keep the billion-vector sweeps entirely inside C++.
How this is got wrong. The obvious reading is “file I/O is slow.” It was measured and it is not: writing 200,000 vectors to a file ran at 5,110,455/s and discarding them to /dev/null ran at 5,398,353/s — a 5 % difference. The cost is printf's decimal conversion, not the disk. Replacing text with a binary buffer, or comparing in memory and never serialising at all, recovers the other 96 %.

So the honest version of the folklore is: the algorithm is about 1,600× faster in C++, and a badly plumbed harness will give you 57×. Both are worth having; they buy different things. The 57× path is how you drive the RTL. The 1,600× path is how you settle the algorithm before any RTL exists — and that is where the schedule is actually won, because a bug found in the C++ costs minutes and the same bug found in a gate-level regression costs days.
