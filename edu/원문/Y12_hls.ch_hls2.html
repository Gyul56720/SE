Y12. High-Level Synthesis in a Small Design House

High-level synthesis promises to turn C++ into RTL, which for a one-person house sounds like a way to multiply headcount. It is a real tool with a real place, and the place is narrower than the marketing and wider than the scepticism. This part states where it wins, where it does not, and what this repository measured when it tried to synthesise a production C++ library with an open-source tool.

Y12.1 What HLS actually decides for you

The three transformations, and which one is the hard one
StepJustification
1Scheduling: assign each operation to a clock cycle, respecting data dependences and the target period.The tool solves a constrained scheduling problem, typically with a list-scheduling heuristic or an ILP formulation for small regions.
2Allocation: decide how many of each resource exist.Two multiplies in different cycles may share one multiplier.
3Binding: assign operations to specific resource instances, and variables to registers or memories.Introduces multiplexers, which is where a naive binding loses the timing the scheduler thought it had.
4All three are driven by pragmas, not by the C++ semantics.This is the fact that determines everything else. The same C++ with different pragmas produces designs differing by orders of magnitude in area and throughput, which means the C++ is not the design — the C++ plus the pragmas plus the tool version is the design.
5So HLS source is not portable between tools in any practical sense.The pragma dialects differ, the library types (ap_fixed, hls::stream) differ, and the scheduling behaviour differs. Measured in this repository: a production Xilinx Vitis library did not build under an open-source HLS tool without modification.
Table 388. Where HLS wins and where it does not
SituationHLSWhy
Datapath-heavy, regular loops (filters, transforms, linear algebra)StrongScheduling a loop nest is exactly what the tool is good at
Design-space exploration — ten variants of one algorithmVery strongChanging a pragma is minutes; rewriting RTL is days. This is the best argument for HLS

The strongest case for HLS in a small house is exploration, not production. The question ‘what does this algorithm cost at four different parallelism factors?’ takes an afternoon in HLS and a fortnight in RTL, and the answer changes the architecture. Having taken the decision, writing the production block in RTL is often still the right call — and the HLS model remains useful as a golden reference, since it is C++ that is known to produce the same numbers. Used this way, HLS is a modelling tool that happens to emit RTL, which fits the role this book is written for.

Y12.2 What this repository measured

This repository built an open-source HLS tool from source and attempted to synthesise a production vendor C++ library with it. The findings are recorded in survey/synth/합성결과.md (144 lines) and are summarised here because they are the kind of result that is rarely written down.

Pragma dialectVendor pragmas are not recognised by the other tool; the code compiles and schedules differentlyHLS source does not port. Budget a rewrite, not a recompile

Two lessons from that exercise are worth more than the result itself. First, the blockers were only separable by controlled experiments: all three appeared as ‘it does not work’ until each was isolated with one variable changed at a time, and before that isolation it would have been easy — and wrong — to report a single cause. Second, an early attempt to name the cause was withdrawn because the run had timed out before reaching the pass in question, so the claim was a guess and not a measurement. The rule that produced both corrections is the one this whole book applies: a number or a cause you have not measured is not a finding, however confident you are.

Y12.3 Verifying HLS output

Table 390. The three levels of HLS verification
LevelWhat it comparesCatchesCost
C simulationThe C++ against your test vectorsAlgorithm bugsSeconds — run constantly
C/RTL co-simulationThe generated RTL against the same C++ on the same vectorsTool bugs and pragma misunderstandingsMinutes to hours
RTL verificationThe generated RTL in its real environmentInterface and integration problems the co-simulation harness hidesAs for any RTL
Why C/RTL co-simulation is not optional. It is tempting to reason that if the C++ is correct and the tool is correct then the RTL is correct. The second premise is the problem: HLS tools have bugs, and more commonly the pragmas do not mean what the writer thought — a dependence the tool was told to ignore was real, a loop it was told to pipeline could not be, an interface protocol was inferred differently from what the integrator expects. Co-simulation catches all of these for the cost of running the vectors twice. It is also the only thing that makes the C++ usable as a golden model afterwards, since it establishes that the two really do agree.

How this is got wrong. By counting the saving and then shipping the HLS output without the verification days. The arithmetic above holds only because the last two rows are included; an HLS flow without co-simulation is faster and produces RTL nobody should trust. The second common error is to count the setup as a one-off when it is per-project: tool versions, library versions and pragma behaviour change, and a flow that worked last year needs re-establishing. Budget the setup every time and the saving is still large for exploration and small or negative for a single production block — which is exactly the recommendation in Y12.1, now with numbers behind it.
Problem. A customer asks whether your block was written in RTL or generated from HLS. Does it matter, and how do you answer?
Solution. It matters to them for three legitimate reasons and you should answer plainly. Maintainability: if they must modify the block, generated RTL is unpleasant to edit, so they need either the C++ and the flow, or a commitment that you will make changes. Quality of results: generated RTL is usually larger and slower than good hand RTL at the same function, and if they are area- or frequency-constrained that is their business. Predictability: regenerating with a different tool version can change the result, so they will want to know the RTL they receive is frozen and verified as delivered, not regenerated on demand. The answer that satisfies all three is to ship frozen, verified RTL with its synthesis and timing reports, and to state the provenance. Concealing it is the bad option: it is discoverable from the generated code's shape in about five minutes, and being caught concealing something harmless costs more than the thing concealed.
