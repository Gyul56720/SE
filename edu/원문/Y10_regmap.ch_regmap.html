Y10. The Register Map and the Software Interface

The register map is the part of a block that software sees, the part a customer integrates against, and the part that is hardest to change after release. It is also, in most projects, the artefact with the least design attention per hour of downstream consequence. This part works through one map in full and states the rules that each entry follows.

Y10.2 Access types, and the race each one prevents

Table 383. Register access types

WOWrite onlyCommand registersUnreadable state cannot be restored after suspend; prefer RW with a self-clearing bit
RW1Writable once until resetLockable configurationSoftware must know the lock exists
The read-modify-write race is the defect this table exists to prevent, and it is worth stating concretely. Suppose STATUS bits lived in CTRL. A driver reads CTRL, changes ENABLE, and writes it back. Between the read and the write, hardware set an error bit. The write puts back the old value of that bit and the error is lost — silently, rarely, and only under load. The rule is structural: never mix software-written and hardware-written bits in one register, and where an event must be cleared by software, use W1C so that the write names exactly the bits it intends. This costs one extra register and removes a class of bug that is close to undebuggable in the field.

Each is a divergence between what software believes and what hardware does, found at integration. The generator's value is in the defects it removes, not the keystrokes, and stating it that way is also how to justify the two weeks to a manager who sees only the keystrokes.
Problem. What should a register do when software writes a reserved bit?
Solution. Define it, and define it in the direction that leaves you room. The two defensible choices are ‘reserved, write zero, read undefined’ and ‘reserved, preserve on write, read as written’. The second is much better for forward compatibility: software does a read-modify-write and unknowingly preserves bits a future version defines, so an old driver keeps working with new hardware. The first is simpler and breaks that property. What is not acceptable is leaving it unspecified, because software will discover the behaviour empirically and depend on it, and you will then be unable to change it. The same principle applies to every ‘don't care’ in a specification: an unspecified behaviour is not free, it is a behaviour your customers will come to rely on before you have decided what it should be.
Problem. Your block is in a power domain that can be switched off. What does that do to the register map?
Solution. It adds a requirement that is easy to miss and expensive to retrofit: every register software may need after resume must be restorable. That means no write-only registers whose value cannot be read back, no state that exists only in hardware counters software cannot reconstruct, and a documented save/restore list telling the driver exactly which offsets to store. It also raises a design question about which registers should be in an always-on domain — typically the ones controlling wake-up and the power sequence itself, since a register that controls power-up cannot live in the domain being powered up. Getting this wrong produces a block that works until the first suspend/resume cycle, which in a mobile or automotive product is within minutes of the customer first running real software on it.
