Y7. Debug and Bring-Up, With the Arithmetic

Bring-up is the phase in which the difference between engineers is largest, and most of that difference is method rather than knowledge. The method is binary search over hypotheses, executed with discipline, and it can be made quantitative: each observation should halve the space of possible causes, and an observation that does not is a waste of an afternoon.

Y7.1 Debugging as information gain

Why the right measurement is the one that splits the space evenly
StepJustification
1Let there be N plausible causes, each with prior probability pi.The hypothesis space after reading the symptom.
2A test partitions the space: outcome A is consistent with a subset, outcome B with the rest.Any observation does this, well or badly.
3The information gained is the entropy reduction, maximised when the two subsets have equal probability mass.Not equal count — equal probability. Splitting off one unlikely cause teaches almost nothing.
4k ideal tests reduce N equiprobable causes to N/2k.So twenty causes need about five tests, not twenty.
5A test whose outcome you can predict has zero information.If you are confident what will happen, do not run it. This single rule eliminates most wasted bring-up time.

A bring-up with 32 plausible causes is five good measurements or thirty-two bad ones. The whole skill is in choosing tests that split the space rather than tests that confirm a favourite hypothesis.
The favourite-hypothesis trap has a specific signature. An engineer who believes the problem is in module X runs tests that would be consistent with X, gets results consistent with X, and becomes more confident — while every one of those tests was also consistent with Y and Z. The discipline that prevents it is to write down what each outcome would rule out before running the test. If the answer is ‘nothing, either way’, the test is confirmation and not evidence. This is the same rule as the verification one in Part X8: a test that no broken implementation would fail is not a test.

Y7.2 The bring-up sequence, in dependency order

Table 426. Bring up in this order, because each step depends on the previous
StepCheckIf it fails
1. PowerEvery rail at the right voltage, in the right sequence, with the ripple in specNothing above this means anything. Sequence violations can damage parts
2. ClocksEvery clock present, at the right frequency, with acceptable jitterMeasure at the die if possible; a clock present at the oscillator is not a clock present at the block
3. ResetAsserted long enough, released cleanly and synchronouslyThe most common silent failure — a block that half-resets produces a state that no simulation ever visited
4. Register accessRead an ID register; write and read back a scratch registerIf this fails, everything above is suspect; if it works, the bus, clock, reset and power are all proven at once
5. Static configurationProgram the block; read back every registerRead-back mismatch localises to the register file immediately
6. LoopbackInternal loopback first, then externalSeparates the block from the channel — the single most valuable feature to design in
7. One transactionOne packet, one frame, one transferDebuggable; a stream is not
8. Line rateContinuous trafficReveals everything the single transaction hid: buffering, back pressure, rate adaptation, alignment
9. Corner conditionsTemperature, voltage, rate extremesWhere the margin problems live
Step 4 is worth more than its position suggests. A readable identification register with a known constant value proves, in one transaction, that the supply is up, the clock is running, the reset released, the bus is connected, the address decode is right and the endianness matches. There is no other single test with that much power, and providing one costs a design a dozen gates. An IP block without an ID register and a scratch register is harder to bring up by a factor that is hard to overstate, and their absence is a reasonable reason for a customer to choose a competitor.
Worked example 68. Why internal loopback pays for itself in one bring-up
Given. A SerDes-attached block fails to pass traffic. Without loopback there are, say, 24 plausible causes spanning the transmitter, the channel, the connector, the far end and the receiver. Internal loopback splits them into 'inside the chip' and 'outside'.
Method. Apply the information argument: count the tests needed with and without the feature, at roughly two hours per test including setup.
Plausible causes24
Ideal tests without loopback5

But: tests without loopback are not even splitsthis is the real saving

How this is got wrong. By counting only the ideal test count, which barely changes. The value of loopback is not that it reduces log2N by one; it is that without it, no available test splits the space evenly — every measurement is at one end of the chain and rules out little. A feature that creates an even split where none existed is worth far more than its effect on the count suggests. The same argument justifies per-stage error counters, snapshot registers and a pattern generator: each one manufactures a clean partition of the hypothesis space.

Problem. A link passes traffic for exactly 71 minutes and then drops a frame, reliably. What wraps in 71 minutes?
Solution. Do the arithmetic rather than guessing. At 1 Gbit/s and 8 bits per byte a byte counter increments 125 million times a second; 71 minutes is about 4260 s, giving roughly 5.3×1011 bytes — close to 239. At a 156.25 MHz clock, 4260 s is about 6.7×1011 cycles, near 239.3. So look for a counter of about 39 or 40 bits — a 40-bit statistics counter, or a timestamp. The technique generalises: convert the failure period into counts of every periodic event in the system and see which lands on a power of two. It also works for suspiciously round numbers in other bases: 71 minutes is not obviously special, which is exactly why the conversion is necessary. A failure at 49.7 days would be a 32-bit millisecond counter and is recognisable on sight; the same reasoning found it.
Problem. Silicon fails a case that simulation passes. Where do you look first, and what does that tell you about your verification plan?
Solution. Look at the list of things the simulation did not model, because that is where the answer is by definition. The usual entries: reset — simulation often starts from an initialised state that silicon never has, so an uninitialised register that simulation reads as a known value reads as garbage in silicon; X-propagation — a simulator's optimistic X handling can let an unknown resolve to a definite value through a multiplexer, hiding exactly this class of bug, which is why X-pessimistic or four-state gate-level simulation exists; clock and power sequencing, rarely modelled at all; analogue behaviour, from supply droop to the settling of an off-chip device; and real timing, since RTL simulation is untimed. What this says about the plan is concrete: each of these has a known mitigation — randomised reset values, X-pessimistic simulation, gate-level simulation with back-annotated timing, and a modelled power sequence — and the plan should name which ones it uses and which it consciously declines. A plan that does not mention them has not declined them; it has forgotten them, and the difference shows up here.
