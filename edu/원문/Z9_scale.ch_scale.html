Z9. Scaling the Agent to a Block That Is Actually Big

The blocks this book's agent verifies are small — tens to hundreds of lines. A sellable block is thousands. This part is about what changes, because several things that work at the small scale stop working, and knowing which ones in advance is the difference between a method and a demonstration.

Worked example 96. When the mutation pass stops fitting in a night
Given. Mutants scale roughly with lines; each mutant is run on k seeds; each run takes time proportional to the design.
Method. Compute the triple product at three sizes and find where twelve hours runs out.
30 lines: mutants × seeds × run8 × 1 × 0.03 s = 0.24 s
300 lines80 × 2 × 0.3 s = 48 s
3000 lines800 × 2 × 3 s = 1.333 h

Sampling 10 % nightly at 30k lines13.33 h
How this is got wrong. By treating the mutation score as something run once at release. Sampled nightly it is a trend, and the trend is what detects Part Z6's first failure mode — the oracle standing still while the design grows. A single number at release cannot detect that, and by then it is too late to act on it anyway.

Z9.2 Shrinking a sequence, not a value

Delta debugging, and why it is worth implementing
StepJustification
1A sequential failure is a sequence of transactions, not one input.So the current shrink — replay the one failing stimulus — does not apply.
2Naive minimisation removes one transaction at a time and re-runs: O(n2) runs for length n.At n = 10 000 and one second a run, that is weeks.
3Delta debugging halves instead: try the first half, then the second, then quarters, keeping any subset that still fails.O(n log n) in the worst case and far better in practice, because failures usually depend on a few transactions.
4The result is a 1-minimal sequence: removing any single transaction makes it pass.Which is usually two or three transactions out of ten thousand, and that is a debuggable report.
5It needs only a predicate: does this sequence still fail?Which the harness already provides. That is why it is cheap to add — the expensive part, the oracle, already exists.

The last row is the one to build first, and it is routinely skipped. Every failure the agent has ever found, reduced to its minimal reproducer, is a test that costs nothing to re-run and that is known to have caught a real bug once. A growing file of them is a regression suite assembled for free from work already done, and it is the only part of the stimulus that is guaranteed to be relevant to this design rather than to a designer's idea of it. This repository's agent writes the minimal reproducer into its ledger; turning that ledger into a replay set is a few lines and should be the first thing added when a block gets big.
Problem. At what size should you stop using one agent and split the block?
Solution. The question is better posed as: at what size does the oracle stop being a single comparison? The agent's structure is indifferent to size; what fails is the golden model's granularity. While one model consumes the block's inputs and produces its outputs, one comparison suffices however large the block is. The break comes when a failure's distance from its cause becomes too large — an error injected in a pipeline's first stage that manifests as a wrong packet ten thousand cycles later, where the minimal reproducer is still ten thousand transactions and the repair search has no cone to restrict to. At that point split the comparison, not the block: add internal checkpoints where the model and the RTL can be compared — after the syndrome stage, after the key equation, after Chien — each with its own small oracle. This is step-and-compare from Part X19 applied to a datapath, and it converts one hard debugging problem into several easy ones. The cost is that the internal interfaces become part of the verification contract and cannot be changed freely, which is a real constraint and is usually worth it.
