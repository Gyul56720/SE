T3. 준안정 — 설계로 없앨 수 없는 단 하나의 실패

다른 모든 타이밍 양은 통과하게 만들 수 있다. 이것만은 드물게 만들 수 있을 뿐이고, 얼마나 드문지를 당신이 말해야 한다.

셋업 위반은 일정 문제다. 데이터가 늦었고, 클럭을 늦추거나 논리를 줄이면 고쳐진다. 준안정은 그것이 아니다. 플립플롭이 클럭 에지 바로 그 순간에 변하고 있는 입력을 표본화하면, 출력이 두 합법적인 준위 사이에 무한정 머물 수 있다. 아무리 느리게 해도 없어지지 않는다 — 표본화 순간과 데이터 천이는 서로 무관하므로 그 나쁜 우연은 또 일어난다. 물음은 얼마나 자주냐, 그리고 그것을 예산에 넣었느냐뿐이다.

이 장은 그 물음에 수로 답한 다음, 나머지 분량을 더 흔한 실패에 쓴다. 수를 바르게 계산하고 2 단 동기화기를 넣고도 멈추는 칩을 내보내는 기술자들 — 경계를 건넌 것이 한 비트가 아니었기 때문이다.

T3.1 결정이 왜 무한정 걸릴 수 있나

유도 — 교차 결합 쌍에서 지수함수까지
이렇게 된다왜냐하면
1플립플롭의 저장 소자는 고리를 이룬 인버터 둘이다. 각각의 출력이 다른 쪽의 입력을 몬다.그 고리가 클럭 없이 상태를 붙드는 것이다 — 축전기를 따로 이름 붙이지 않고도 기억을 갖는 디지털 설계의 유일한 구조다.
2그 고리에는 평형점이 셋 있다. 단단한 0, 단단한 1, 그리고 두 인버터가 각자의 스위칭 문턱에 앉는 가운데 한 점.Vout1 대 Vin1 과 두 번째 인버터의 거울 곡선을 그리면 세 번 만난다. 가운데 교점이 준안정점이다.
3가운데 평형은 불안정하다. 거기서 고리 이득이 A² > 1 이므로 어떤 벗어남이든 자란다.인버터마다 문턱에서 소신호 이득 A = −gm(ro,n ∥ ro,p) 를 갖고, T1 이 두 항을 다 줬다.
4그 둘레에서 선형화하면 C·dv/dt = (A − 1)·v/R, 즉 v(t) = v0·et/τ 이고 τ = RC/(A − 1) 이다.여기서 τ, 결정 시간상수가 나온다. 그것은 회로의 성질이고 — 대략 고리의 RC 를 그 남는 이득으로 나눈 것 — 당신이 고를 수 있는 규격이 아니다.
5올바른 준위로 결판나려면 고리가 벗어남을 v0 에서 대략 VDD/2 까지 키워야 하고, 그것이 t = τ·ln(VDD/2v0) 걸린다.시간은 표본이 가운데에 얼마나 가까이 떨어졌는지의 로그다 — 그리고 v0 는 얼마든지 작을 수 있으므로 t 에 상한이 없다. 대비할 최악의 경우가 없고 분포만 있다.
6결판나는 데 tr 보다 오래 걸리는 창 안에 표본이 떨어질 확률은 e−tr/τ 로 준다.클럭 주기 안에서 도착이 고르고 v0 가 에지에 얼마나 가까웠는지에 비례하므로, 지수가 곧바로 나온다.
저 유도에서 결론 둘이 떨어지고 둘 다 실무에서 중요하다. 첫째, τ 는 소신호 양이다. 그래서 이득이 나빠지는 바로 그 자리에서 나빠진다 — 느린 코너, 낮은 전압, 높은 온도. 둘째, 준안정점은 플롭이 전류를 가장 많이 태우는 자리다 — 두 소자가 다 켜져 있다. 자주 준안정에 빠지는 설계는 논리적으로만 실패하는 것이 아니라, 예산에 없던 전류까지 끌어간다.

T3.2 MTBF, 그리고 그 안의 기호 하나하나가 실제로 무엇인가

MTBF (mean time between failures) — 동기화기가 주어진 시간 안에 결판내지 못하는 사건 둘 사이의 평균 시간. 보장이 아니라 비율이다 — MTBF 1000 년은 첫 실패가 1000 년째에 난다는 뜻이 아니라, 실패가 그 평균을 갖는 포아송이라는 뜻이다.
MTBF 식

MTBF = etr/τ / (T0·fc·fd)

tr — 해결 시간: 무엇인가가 읽기 전에 동기화기 플롭에게 정착하라고 준 시간. 한 단 건넘이라면 Tclk 에서 그 플롭 자신의 tcq 를 빼고, 그것을 읽는 쪽의 셋업을 빼고, 사이의 논리를 뺀 것이다. τ — 결정 시간상수, T3.1 에서 왔고 여기서는 25 ps. T0 — 표본이 준안정에 빠질 수 있는 구경의 실효 폭, 여기서는 1 ps. 둘 다 유도된 것이 아니라 셀마다 코너마다 잰 것이다. fc — 표본화(목적지) 클럭 주파수. fd — 비동기 입력이 변하는 비율.

지수에 들어 있는 것은 tr 뿐이고, 이 식의 공학적 내용은 전부 그것이다: 당신이 할 수 있는 것은 전부 선형이고, 당신이 제어할 수 없는 것이 지수다. fd 를 두 배로 하면 MTBF 가 반이 된다. 동기화기 단을 하나 더하면 지수가 곱해진다.

어디에 쓰나설계의 모든 비동기 경계: 바깥 인터럽트, 리셋 해제, 누름 버튼, 클럭 도메인을 건너가는 FIFO 포인터, PHY 의 복원 클럭 도메인이 코어와 만나는 자리.
언제 쓰나아키텍처 단계에서 깊이를 고르고, 사인오프에서 수를 적는다. MTBF 와 그것을 계산한 조건 없이 'CDC 안전' 이라고 적은 IP 데이터시트는 아무것도 주장하지 않은 것이다.
어떻게 쓰나τ 와 T0 를 라이브러리의 동기화기 셀 특성화에서 받는다(코너마다 공개돼 있다). tr 은 이상적인 클럭 주기가 아니라 실제 경로에서 낸다. 그리고 MTBF 를 느린 코너에서 적는다. τ 가 거기서 가장 나쁘기 때문이다.
실제 코드는 이렇게 생겼다
// The synchroniser, written so the tools recognise it.
// The attribute is not decoration: it tells the tool to keep the two flops
// adjacent and out of retiming, and it tells CDC checkers this is intentional.
(* ASYNC_REG = "TRUE" *) reg [1:0] sync_q;          // Xilinx; Intel: altera_attribute
always_ff @(posedge clk_dst or negedge rst_n) begin
    if (!rst_n) sync_q <= 2'b00;
    else        sync_q <= {sync_q[0], async_in};    // 2-stage
end
wire safe_in = sync_q[1];

// And the constraint, without which STA tries to time an impossible path:
// set_max_delay -datapath_only 2.0 -from [get_pins u_src/*/Q] -to [get_pins u_sync/sync_q_reg[0]/D]
// NOT set_false_path -- a false path lets the tool put unbounded wire delay there,
// and then the first stage's own setup window is no longer what you assumed.
여기서 틀린다. 건넘에 set_false_path 를 거는 것이 가장 흔한 CDC 제약 잘못이다. 타이밍 보고서를 조용하게 만들지만, 동기화기로 들어가는 배선 지연의 한계도 같이 없앤다 — 그래서 원천이 목적지 에지에 얼마든지 가까이 변할 수 있게 되고 게다가 버스의 두 비트 사이 스큐에 상한이 없어진다. set_max_delay -datapath_only 를 쓰라.

T3.3 동기화기는 CDC 의 해답이 아니다

지금까지는 전부 한 비트 이야기다. 실제로 실리콘까지 닿는 실패는 MTBF 를 잘못 잡아서 나는 일이 거의 없다. 버스의 비트마다 제대로 동기화해 놓고도 진 설계자들에게서 난다.

다중 비트 문제, 그리고 빠져나가는 세 길

서로 독립인 동기화기는 서로 독립으로 결정한다. 같은 원천 주기에 두 비트가 변하면 각각이 경계의 어느 쪽으로든 결판날 수 있으므로, 목적지는 중간값을 볼 수 있다 — 원천이 한 번도 몰지 않은 코드를. 이진 계수기가 0111 → 1000 으로 건너가는 것을 1111 로도 0000 으로도, 그 사이 아무것으로도 볼 수 있다. 어떤 MTBF 계산도 이것을 못 잡는다. 플롭은 하나하나 다 옳게 동작했다.

어디에 쓰나클럭 경계를 건너는 모든 버스, 계수기, 포인터, 상태 워드, 설정 필드. 실제로는 FIFO 포인터, 인터럽트 상태 레지스터, 그리고 느린 설정 도메인이 쓰고 빠른 데이터패스가 읽는 '모드' 필드.
언제 쓰나비트가 하나를 넘는 순간부터. 3 비트라고 32 비트보다 안전하지 않다 — 중요한 것은 폭이 아니라 동시성이다.
어떻게 쓰나하나를 고르라. (1) 그레이 코드 — 하나 셀 때마다 한 비트만 변하므로 중간에 잡힌 표본은 옛 값 아니면 새 값이고 둘 다 올바르다. 계수기와 포인터에는 되고 임의의 데이터에는 안 된다. (2) 핸드셰이크 — 데이터를 안정하게 붙들고 요청 비트 하나만 건넨다. 받는 쪽이 응답한다. 왕복 지연이 들지만 무엇에든 된다. (3) 비동기 FIFO — 그레이 코드 포인터를 갖는 이중 포트 메모리. (1) 과 (2) 를 합친 것이고, 흐르는 데이터에는 이것을 내보낸다.
실제 코드는 이렇게 생겼다
// Gray-coded pointer crossing -- the standard async FIFO core.
// The pointer is converted to gray BEFORE crossing and back AFTER.
function automatic [PW:0] bin2gray(input [PW:0] b); return b ^ (b >> 1); endfunction

always_ff @(posedge wclk or negedge wrst_n)
    if (!wrst_n) {wbin, wgray} <= '0;
    else         {wbin, wgray} <= {wbin_next, bin2gray(wbin_next)};

// crossing: gray value only, two stages, one synchroniser per bit is now SAFE
// because at most one bit differs between consecutive gray values.
(* ASYNC_REG = "TRUE" *) reg [PW:0] wq1_rgray, wq2_rgray;
always_ff @(posedge wclk or negedge wrst_n)
    if (!wrst_n) {wq2_rgray, wq1_rgray} <= '0;
    else         {wq2_rgray, wq1_rgray} <= {wq1_rgray, rgray};

// FULL is computed from the SYNCHRONISED read pointer, so it is CONSERVATIVE:
// it can be asserted when the FIFO has already been drained, never the reverse.
assign wfull = (wgray_next == {~wq2_rgray[PW:PW-1], wq2_rgray[PW-2:0]});
여기서 틀린다. 그레이 코드는 포인터를 지키지 데이터를 지키지 않는다. 비동기 FIFO 의 데이터 경로는 이중 포트 RAM 이고, 그것이 안전한 까닭은 오직 읽기 주소가 쓰기 쪽이 아직 다 쓰지 못한 자리에 닿는 것이 허용되지 않기 때문이다 — 보수적인 full/empty 비교가 사 주는 것이 그것이다. 그레이 코드 수법을 데이터 버스에 베껴 놓아도 아무 소용이 없다. 이어지는 데이터 워드는 여러 비트가 한꺼번에 다르다.
실제로 난 일
건넘은 준안정 사건이 하나도 없이도 실패할 수 있다. 원천 펄스가 목적지 클럭 주기 하나보다 짧으면 목적지는 그것을 영영 표본화하지 못할 수 있다 — 동기화기는 매번 깨끗하게 옛 값으로 결판난다. 이것은 확률적 실패가 아니라 확정적 실패이고, MTBF 분석에는 안 보인다. 그것을 막는 규칙: 느린 도메인으로 건너가는 신호는 목적지 주기의 1.5 배 이상 붙들어야 한다. 아니면 레벨 토글로 바꾸고 돌아오는 핸드셰이크를 둔다.

준정적신호 (quasi-static signal) — 목적지가 그것을 쓰지 않는 동안에만 변하도록 규약으로 보장된 건넘 신호 — 보통 블록이 켜지기 전에 쓰는 설정 필드다. 동기화기는 필요 없지만, 데이터시트에 적힌 규칙과 그렇다고 말하는 CDC 예외는 필요하다. 적어 두지 않은 준정적 가정이야말로 IP 가 실험실에서는 되고 고객 시스템에서는 안 되는 길이다.

T3.4 리셋: 모두가 잊는 건넘

리셋은 본디 비동기다 — 어떤 클럭도 돌기 전에 동작해야 한다 — 그리고 어쩔 수 없이 동기이기도 하다. 엉뚱한 순간에 풀면 플롭의 리커버리 시간을 어겨서 상태 기계를 첫 주기에 준안정 상태로 만들기 때문이다. 해법은 모든 설계에서 같고, 한 문장으로 외워 둘 값어치가 있다: 비동기로 걸고, 동기로 푼다.

리커버리 · 리무벌 (recovery and removal)

리커버리 시간은 리셋 해제에 걸리는 셋업 제약이다. 리셋은 활성 클럭 에지보다 최소한 trecovery 앞서 풀려야 한다. 리무벌 시간은 그에 대응하는 홀드 제약이다. 다른 타이밍 이음과 똑같이 특성화되어 .lib 에 들어 있다 — 그 말은 STA 가 그것을 그 플롭에서 리셋이 타이밍이 걸린 동기 신호일 때만 검사한다는 뜻이다.

동기화기 없이 풀리는 비동기 리셋은 클럭과 그런 관계가 없으므로 STA 는 아무것도 보고하지 않고, 실패는 전원을 올린 뒤 상태 기계가 가끔 불법 상태에서 출발하는 꼴로 나타난다 — 대개 한 코너에서, 어떤 보드에서만, 어떤 전원 상승 모양에서만.

어디에 쓰나모든 클럭 도메인. 클럭이 셋인 설계는 리셋 동기화기가 셋 필요하고, 각각 자기 도메인으로 클럭되며 모두 같은 비동기 원천을 받는다.
언제 쓰나늘. 값은 도메인마다 플롭 둘이고, 그것이 막아 주는 실패는 재현하기 가장 어려운 부류다.
어떻게 쓰나거는 것은 바로 통과시키고(클럭 없이), 푸는 것은 플롭 둘을 거치게 한다. 그러고 나서 제약한다. 해제는 이제 동기 신호이므로 STA 가 그것이 닿는 모든 플롭에서 리커버리/리무벌을 검사한다.
실제 코드는 이렇게 생겼다
// Reset synchroniser -- one per clock domain.
module reset_sync (input clk, input arst_n, output rst_n);
    (* ASYNC_REG = "TRUE" *) reg [1:0] q;
    always_ff @(posedge clk or negedge arst_n)
        if (!arst_n) q <= 2'b00;          // ASSERT: asynchronous, no clock needed
        else         q <= {q[0], 1'b1};   // RELEASE: two clocked stages
    assign rst_n = q[1];
endmodule

// SDC: the asynchronous assertion is not a timed path; the release is.
set_false_path -from [get_ports arst_n] -to [get_pins u_rsync/q_reg[0]/CLR]
// and every flop fed by rst_n gets a normal recovery/removal check -- verify with:
//   report_timing -delay_type max -check_type recovery -from [get_pins u_rsync/q_reg[1]/Q]
여기서 틀린다. 동기화기 자신의 플롭을 동기화된 리셋으로 리셋하는 것은 빠져나갈 길 없는 고리다. 해제 에지를 놓치면 블록이 영영 리셋에서 못 나온다. 동기화기는 클리어 핀에 날것의 비동기 리셋을 받아야 한다. 리셋 동기화기의 두 플롭이 0 으로 리셋되고 1 을 밀어 넣는 것이지 그 반대가 아닌 까닭도 이것이다.

T3.5 STA 가 못 보는 것, 그리고 CDC 도구가 대신 하는 것

예외 파일이야말로 CDC 사인오프에서 그 분석에 뜻이 있었는지를 정하는 부분이다. 예외 이백 개를 달고 돌려서 나온 초록 요약은 증거가 아니다. 그것은 기술자 한 사람의 주장 이백 개다. IP 납품물은 CDC 예외를 읽을 수 있는 문서로 같이 내보내야 한다. 하나마다 까닭 한 줄씩. 통합하는 쪽이 그 전부를 물려받는데, 넷리스트에서 그것을 되살려 낼 수는 없기 때문이다.
구조뿐 아니라 시뮬레이션으로도 건넘을 증명하기

구조적 CDC 분석은 동기화기가 있다는 것을 증명한다. 원천이 그 동기화기가 가정하는 규약을 지키는지는 증명하지 못한다 — 요청이 높은 동안 데이터가 안정한지, 펄스가 충분히 긴지, 준정적 필드가 데이터패스가 도는 동안 쓰이지 않는지. 그것들은 시간적 성질이고, 손으로 쓰거나 CDC 도구가 생성한 어서션으로 검사한다.

쓸 수 있는 가장 강한 검사는 준안정 주입까지 더한다. 시뮬레이터가 동기화기 출력을 무작위로 한 주기 늦춰서, 건넘이 즉시 결판날 때만 도는 설계가 실리콘이 아니라 회귀에서 실패하게 만든다.

어디에 쓰나클럭이 하나를 넘는 모든 것의 블록 수준 검증, 그리고 남의 클럭 구조 안으로 팔 생각인 모든 IP.
언제 쓰나RTL 을 얼릴 때마다 구조적 CDC 를 돌리고, 야간 회귀에서 주입을 돌린다. 둘은 서로 다른 버그를 찾고 어느 쪽도 다른 쪽을 대신하지 못한다.
어떻게 쓰나어서션을 건넘 모듈에 묶고, 주입을 켠 채 회귀를 돌리고, 결과를 납품물의 검증 절에 건넘 수와 예외 수와 함께 적는다.
실제 코드는 이렇게 생겼다
// The protocol the handshake crossing assumes, stated as a checkable property.
property data_stable_while_req;
    @(posedge clk_src) disable iff (!rst_n)
        req |-> ##0 $stable(data) throughout (req [*1:$] ##1 ack_sync);
endproperty
assert property (data_stable_while_req)
    else $error("CDC: data changed while req was asserted -- the receiver may latch a mix");

// Metastability injection (simulation only): the synchroniser may take one extra cycle.
`ifdef CDC_INJECT
    always_ff @(posedge clk_dst)
        if ($urandom_range(0,99) < 5) sync_q[1] <= sync_q[1];   // hold: resolve later
`endif
여기서 틀린다. 원천 도메인 신호에 대해 목적지 도메인에서 쓴 어서션은 그 자체가 클럭 도메인 건넘이고, 테스트벤치가 만들어 낸 가짜 실패를 보고할 수 있다. 원천 신호는 원천 도메인에서 표본화하고 (@(posedge clk_src)) 불리언 결과만 건네라.

이 장을 끝내는 수는 둘이고, 들고 갈 것이 그 둘이다. 1 GHz 에서 1 단 건넘은 대략 1.8 년에 한 번 실패하고, τ 가 두 배인 같은 건넘은 2 단으로도 대략 1.8 년에 한 번 실패한다. 첫 번째 수가 동기화기가 존재하는 까닭이고, 두 번째 수가 답을 늘 그 코너와 함께 적어야 하는 까닭이다.

다음 장은 이 장이 내내 가정하고 있던 것 — 표본은 맞거나 틀리거나 둘 중 하나라는 것 — 을 분포로 바꾼다. 잡음은 혼성신호 IP 의 모든 아날로그 측정 아래에 바닥을 깔고, 준안정과 달리 전력·면적과 곧바로 맞바꿀 수 있다.

특허로 가는 길 — 이 주제에서 발명이 일어나는 자리
준안정 자체는 물리이고, 2 플롭 동기화기는 이 글을 읽는 누구보다도 오래됐다. 지금도 청구되고 있는 것은 그 둘레의 배치다: 다중 비트 건넘을 N 개가 아니라 동기화기 하나로 안전하게 만드는 포인터 부호화(그레이 코드와 그 후예들). 동작 모드에 따라 동기화기 깊이를 바꾸는 지연 대 MTBF 방식. 자격 신호 하나만 동기화하고 데이터는 경계 너머로 안정하게 붙들어서 데이터를 아예 동기화하지 않는 데이터 경로 건넘. 이 하나하나가 플롭에 대한 논의가 아니라 무엇이 건너야 하는가 에 대한 논의다. 이 장을 이렇게 물으며 읽으라: 내 신호 가운데 정말로 건너야 하는 것은 무엇이고, 나머지는 무엇이 있으면 한쪽에 머물 수 있는가?
