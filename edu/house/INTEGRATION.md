# CRC-32 Streaming Engine — 통합 가이드

통합하는 사람이 **전화하지 않고** 끝낼 수 있게 쓴 문서다. 교안 Y5 장이 말하는
"지원 비용은 문서 품질에 반비례한다" 의 실천이다.

## 1. 클럭과 리셋

- 클럭 하나만 쓴다. 도메인 교차가 블록 안에 없다 — **통합자가 CDC 를 분석할
  것이 없다**(교안 X39 장이 권하는 구조).
- `rst_n` 은 **동기** 리셋이다. 비동기로 걸면 해제 에지가 클럭과 경주한다
  (교안 X42 장). 비동기 리셋 트리를 쓰는 시스템이면 **도메인마다 두 플롭으로
  해제를 동기화해서** 넣어라.
- 리셋은 최소 **2 사이클** 유지한다. 그보다 짧으면 `acc` 가 확정되지 않는다.

## 2. 핸드셰이크

- `s_ready` 를 `s_valid` 생성에 **조합으로 쓰지 마라**. 이 블록은 그 규칙을
  지키지만, 상대쪽이 어기면 고리가 생긴다.
- 출력이 안 빠지면 입력을 안 받는다(`s_ready = ~(m_valid & ~m_ready)`).
  즉 **패킷마다 CRC 를 가져가야 다음 패킷이 흐른다.** 뒤쪽이 느리면 앞이 멈춘다 —
  버퍼를 넣고 싶으면 출력 쪽에 스킷 버퍼를 하나 두면 된다(교안 X37 장).

## 3. 타이밍 닫기

- 임계 경로는 `crc_byte` 의 8 단계 조합 갱신이다. XOR 8 단 정도.
- 더 빠르게 필요하면 **바이트를 병렬로** 처리하는 판(32/64 비트)이 필요하다.
  같은 다항식이므로 행렬 형태로 펼치면 된다 — 현재 판에는 없다.
- 경계 신호를 등록해서 쓰고 싶으면 스킷 버퍼를 넣어라. 블록 안에는 없다
  (일부러 — 필요 없는 지연을 강요하지 않는다).

## 4. 비트 순서와 규약 — **가장 흔한 통합 오류**

- 다항식 0x04C11DB7, **반사 입력·반사 출력**, 초기값 0xFFFFFFFF,
  최종 XOR 0xFFFFFFFF. 즉 파이썬 `zlib.crc32` 와 **같다**.
- 이더넷 FCS 는 이 값을 **바이트 순서 그대로** 전송한다. 다른 규약(예: CRC-32C,
  또는 비반사 판)을 쓰는 시스템이면 이 블록이 아니다.
- **의심되면 `zlib.crc32(b"123456789")` 를 기준으로 맞춰라** — 0xCBF43926.

## 5. 검증 환경 같이 쓰기

블록과 함께 오는 것:

```
edu/agent/blocks/crc32_stream/dut.v      RTL
edu/agent/blocks/crc32_stream/tb.v       테스트벤치 (무작위 back-pressure)
edu/agent/blocks/crc32_stream/block.py   골든모델 연결 + 성능 한계
```

고치고 나서 다시 검증하려면:

```bash
bash edu/house/release.sh crc32_stream
```

**고객이 재현할 수 있어야 한다**(교안 Z3 장). 위 명령이 데이터시트의 모든 숫자를
다시 낸다.

## 6. 우리에게 물어야 할 때

- 다른 다항식·다른 반사 규약이 필요할 때 (파라미터화는 어렵지 않다)
- 바이트보다 넓은 데이터패스가 필요할 때 (구조가 달라진다)
- 하드 매크로·특정 공정 면적 수치가 필요할 때
