# mathgen — 어려운 문제를 출제하는 생성기를 탐색한다

목표: **정답이 검증되고 · 기계가 못 풀고 · 지저분하지 않게 어려운** 문제 생성기를 찾는다.
무엇이 더 어려운가는 LLM 이 아니라 sympy 가 정한다.

```
씨앗 생성기 ──> Evol-Instruct 연산자로 진화 ──> 후보 생성기
                                                   │
                                    judge 가 격리 실행해 3축 채점 (sympy 전용)
                                                   │
                                     세 축 모두 이기면 챔피언 교체 (래칫)
```

## 논문 근거

| 논문 | 가져온 것 |
|---|---|
| [WizardMath / Evol-Instruct](https://arxiv.org/pdf/2308.09583) · **Microsoft** | **In-Depth Evolving 5연산자** — 제약 추가 / 심화 / 구체화 / 추론단계 증가 / 입력 복잡화. 한 라운드에 하나만 적용한다 |
| [VeriEvol](https://arxiv.org/html/2606.23543v1) | **난이도와 정답 신뢰성의 분리.** 연산자는 난이도만 올리고 정답은 별도 검증이 보증한다 |
| [MathScale](https://arxiv.org/abs/2403.02884) · **Microsoft Research** | 씨앗에서 개념을 뽑아 조합 (여기서는 족 목록이 그 역할) |
| [LLMs Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798) · **Google DeepMind**, ICLR'24 | 내재적 자기교정은 개선이 없거나 성능을 떨어뜨린다 → **채점에 LLM 을 쓰지 않는다** |

## 세 축

| 축 | 정의 | 왜 |
|---|---|---|
| ① **정당성** | `diff(답, x)` 가 피적분함수와 같은가 | 푸는 것보다 **확인이 압도적으로 싸다.** 이 비대칭성이 심판이 성립하는 이유 |
| ② **비자명성** | `sympy.integrate` 가 시간 안에 못 푸는가 | 기계가 바로 푸는 것은 문제가 아니다 |
| ③ **압축성** | 풀이 연산수 / 펼친 문제의 연산수 | **절대 길이가 아니라 비율** |

**세 축이 정면으로 싸운다.** ②를 올리려고 계수를 키우면 ③이 무너지고, ③을 지키려고
단순하게 만들면 ②가 무너지고, 둘 다 맞추려고 답을 대충 내면 ①이 무너진다.

### ③을 왜 비율로 재는가

절대 길이(단계 수 ≤ K)로 재면 **내가 이미 구조를 아는 문제만 통과한다** — 짧은 풀이가
있음을 확인하려면 그 풀이를 알아야 하기 때문이다. 그러면 새 유형이 원천 봉쇄된다.

비율로 재면 지저분해도 된다. 막는 것은 **압축되지 않는 지저분함**뿐이다. 그리고 이 구별이
실제로 일어난다(실측):

| 족 | 압축비 | |
|---|---|---|
| `(x²+c)/√(x⁴+ax+b)` 의 도함수 | **0.44** | 압축된다 = 구조가 있다 |
| `exp(a·x·exp(b·x))` 의 도함수 | **1.77** | 압축 안 된다 = 풀이가 문제보다 크다 |

## 거꾸로 만들기

씨앗의 핵심 수는 이것이다:

```
답 F 를 고른다  ──>  f = F' 를 문제로 낸다  ──>  정답은 F (구성상 확실)
```

정당성이 **구성으로 보장되므로** LLM 은 정답을 고민할 필요가 없다. 오직 "sympy 가 f 에서
F 를 되찾지 못하게" 만드는 데만 집중한다. VeriEvol 의 분리를 구조로 강제한 것이다.

### 틈은 좁다 — 그래서 탐색 문제다

답 F 를 12개 형태로 훑어 **2개만** sympy 가 못 되찾았다(실측):

| 되찾지 못함 | 되찾음 |
|---|---|
| `(x²+c)/√(x⁴+ax+b)` (시간 초과) | 다항×지수, 로그 합성, 중첩 근호, 지수(삼각), |
| `exp(a·x·exp(b·x))` (Integral 로 반환) | 유리×로그, 역삼각 합성, 삼각 거듭 합성, 지수/다항 비, 근호+로그, 분수 지수 |

틈이 넓으면 손으로 열거하면 된다. **좁아서 탐색이 필요하다.**

## 심판이 막는 것 / 못 막는 것

**막는다** (회귀 검사로 고정, `tests/test_mathgen_judge.py`)

| 부정행위 | 어떻게 막히나 |
|---|---|
| 문제문에 답 흘리기 | 정규화 후 문자열 검사 |
| 답이 틀림 | 미분해서 독립 재검증 |
| 같은 seed 에 다른 문제 | 두 번 생성해 비교 |
| 퇴화한 문제 (`∫7 dx`) | 변수·연산수·상수답 검사 |
| 전역 변수로 검증기에 신호 | **`check` 프로세스가 생성기를 임포트조차 안 한다** |
| 기계가 이미 푸는 문제 | 별도 프로세스의 `sympy.integrate`, 시간 초과가 곧 신호 |
| 계산만 길어서 어려운 것 | 압축비 |

**못 막는다** — 생성기가 절대경로에 파일을 숨기는 것. 그리고 **"사람에게 좋은 문제인가"는
sympy 가 답할 수 있는 질문이 아니다.** 여기서 재는 것은 그것이 아니다.

## 파일

| 파일 | 역할 |
|---|---|
| `judge.py` | 독립 심판. 3축, sympy 전용, 프로세스 격리 |
| `_worker.py` | `generate` / `check` / `machine` 을 각각 다른 프로세스로 |
| `evolve.py` | 자가개선 루프. Evol-Instruct 연산자 + 래칫 |
| `seeds/backward_hard.py` | 거꾸로 만드는 씨앗. 세 축 통과 |
| `seeds/baseline_poly.py` | 대조군. **떨어져야 정상** (sympy 가 즉시 푼다) |

## 쓰는 법

```bash
pip install sympy

# 생성기 하나 채점
python3 mathgen/judge.py --gen mathgen/seeds/backward_hard.py
python3 mathgen/judge.py --gen <내_생성기.py> --baseline mathgen/champion.py --json

# 자가개선 루프 (GEMINI_API_KEY 필요)
python3 mathgen/evolve.py --status
python3 mathgen/evolve.py --rounds 5
python3 mathgen/evolve.py --rounds 1 --operator deepening

# 심판 자신의 회귀 검사 (LLM·네트워크 불필요)
python3 tests/test_mathgen_judge.py
```

## 생성기 계약

```python
def generate(seed: int) -> dict:
    return {
        "statement": "...",   # 사람이 읽는 문제문. 답을 적으면 즉시 실격
        "spec": {"task": "integrate", "expr": "<피적분함수>", "var": "x"},
        "answer": "...",      # sympy 가 파싱할 수 있는 문자열
        "solution": ["...",]  # 중간식 리스트
    }
```

같은 seed 에는 항상 같은 문제. sympy 와 표준 라이브러리만.

## 정직하게 남기는 한계

- **task 는 `integrate` 만 실질적으로 검증된다.** `solve` 와 `limit` 은 배선돼 있지만
  씨앗이 없고 검증 강도가 다르다 (특히 `limit` 은 수치 확인이라 약하다)
- **압축비의 "무식한 비용"은 대리값이다** — 식을 펼쳤을 때의 연산 수. 실제 손계산량과
  단조 관계인지는 확인하지 않았다
- **sympy 가 못 푼다 ≠ 사람에게 어렵다.** 반대 방향도 마찬가지다. 이 심판은 기계 난이도를
  재지 인간 난이도를 재지 않는다
