# 09. 값 매기기와 내놓기

> **여는 때**: `지금어디.sh` 가 전부 `[o]` 가 된 뒤.
> **먼저 밝힐 것**: 아래의 **금액은 예시이고 검증된 시세가 아니다.**
> 이 문서가 주는 것은 **값을 정하는 방법**이지 값이 아니다.
> 실제 값은 아래 3절의 방법으로 **직접 조사해서** 정한다.

---

## 1. 무엇을 파는가 — 네 가지 중 고른다

| 방식 | 받는 돈 | 주는 것 | 1인 하우스에 |
|---|---|---|---|
| **소스 라이선스** | 한 번 + 제품당 로열티 | RTL 소스 전체 | ○ 가장 단순 |
| **넷리스트/암호화** | 한 번 | 합성된 것만 | △ 도구가 필요 |
| **용역 (NRE)** | 시간당/프로젝트당 | 고객 요구대로 제작 | ○ **현금 흐름이 빠르다** |
| **유지보수 계약** | 연간 | 버그 수정, 질문 응대 | ○ 안정적 |

**처음에는 용역 + 소스 라이선스**를 권한다. 넷리스트 암호화는
상용 도구가 필요하고, 로열티는 고객의 출하량을 믿어야 해서 1인이 관리하기 어렵다.

---

## 2. 원가를 먼저 안다 — 값은 그 다음이다

값을 못 매기는 이유는 대개 **자기 원가를 모르기 때문**이다.

```
원가 = (설계 일수 + 검증 일수 + 문서 일수) × 하루 목표 수입
     + 도구·장비 (무료 흐름이면 ≈ 0)
```

첫 IP 의 실제 일수를 기록해 둔다. 이 매뉴얼대로면:

| 단계 | 첫 IP | 두 번째부터 |
|---|---|---|
| 02~03 고르기·스펙 | 1일 | 0.5일 |
| 04 C++ 모델 | 1~2일 | 1일 |
| 05 RTL | 2~5일 | 2일 |
| 06 검증 | 2~4일 | 1~2일 |
| 07 합성 | 1일 | 0.5일 |
| 08 문서 | 2일 | 1일 |
| **합** | **9~15일** | **6~7일** |

**이 표를 자기 실측으로 바꾸는 것이 첫 IP 의 가장 큰 수확이다.**
두 번째 견적부터는 짐작이 아니라 기록으로 낸다.

---

## 3. 시세를 조사하는 방법 — 이 매뉴얼은 시세를 모른다

값은 원가가 아니라 **시장**이 정한다. 직접 조사한다.

| 조사처 | 무엇을 얻나 |
|---|---|
| IP 중개 플랫폼 (Design&Reuse 등)의 공개 목록 | 비슷한 블록의 가격대 유무 |
| 공개 IP 벤더의 웹사이트 | 가격은 대개 비공개 → **문의 메일을 보내 본다** |
| 프리랜스 RTL 설계 시급 (지역별) | 용역 단가의 하한 |
| 오픈소스 대체재 (OpenCores 등) | **이것이 상한을 누른다** |

마지막 줄이 중요하다. **무료 대체재가 있는 블록은 비싸게 못 판다.**
파는 것은 RTL 이 아니라 **검증·문서·지원**이라는 뜻이기도 하다.

> 그래서 02단계에서 "살 사람이 둘 이상인가" 를 물었다. 그리고 그래서
> 06단계(검증)와 08단계(문서)에 RTL 쓰는 시간만큼을 쓴다.
> **RTL 은 흔하고 검증된 RTL 은 흔하지 않다.**

---

## 4. 값을 올리는 것 / 내리는 것

| 값을 올리는 것 | 왜 |
|---|---|
| **전수 검증 증거** | "2^32 가지 전부 대조" 는 대부분의 벤더가 못 하는 말이다 |
| **변이 점수** | 검사가 문다는 것을 수로 보인다 |
| 실측 면적·주파수 (조건 포함) | 고객이 자기 칩 계획을 바로 세운다 |
| 통합 가이드 품질 | 고객의 통합 인건비를 줄여 준다 |
| 독립 구현과의 대조 | "zlib 과 비트까지 같다" |
| 알려진 문제 목록 | 신뢰. 역설적이지만 사실이다 |

| 값을 내리는 것 | 왜 |
|---|---|
| 무료 대체재가 있다 | 상한이 눌린다 |
| 표준 준수를 증명 못 한다 | 고객이 직접 확인해야 한다 |
| 문서가 부실하다 | 고객의 통합 비용이 내 가격에서 깎인다 |
| 레퍼런스(쓴 곳)가 없다 | 첫 고객은 언제나 싸다 |

---

## 5. 첫 고객을 만드는 법

1인 하우스의 진짜 문제는 만드는 것이 아니라 **파는 것**이다.

### 순서

1. **완성된 것 하나를 먼저 만든다.** (이 매뉴얼 08단계까지)
   견적서만 들고 가면 아무도 안 믿는다. 돌아가는 것을 보여 준다.
2. **공개한다.** 데이터시트와 검증 결과를 웹/GitHub 에 올린다.
   RTL 은 안 줘도 된다. **데이터시트가 명함이다.**
3. **좁게 접근한다.** "IP 팝니다" 가 아니라
   "귀사 제품 X 에 들어가는 Y 를 이런 조건으로 검증해 두었습니다".
4. **첫 건은 용역으로 받는다.** 라이선스보다 현금이 빠르고, 고객의
   실제 요구를 배운다. 그 요구가 두 번째 제품의 스펙이 된다.

### 첫 메일에 반드시 넣을 것

- 무엇인지 **한 줄**
- 실측 면적·주파수 **조건과 함께**
- 검증 강도 한 줄 (전수/변이점수)
- **못 한 것 한 줄** ← 이것이 신뢰를 만든다
- 데이터시트 링크

길게 쓰지 않는다. 읽는 사람은 엔지니어이고, 수와 조건만 본다.

---

## 6. 계약에서 빠뜨리기 쉬운 것

| 항목 | 안 정하면 |
|---|---|
| **납품 정의** | "언제 끝났나"로 다툰다. → 08단계 통과 기준을 그대로 계약서에 |
| 수정 범위와 횟수 | 무한 수정 요구 |
| 지원 기간과 방법 | 2년 뒤에도 전화가 온다 |
| 소유권 / 재사용권 | **다음 고객에게 못 판다.** 가장 비싼 실수 |
| 표준 준수 책임 | 상호운용 실패의 책임 소재 |
| 지연 배상 | — |

**소유권 줄이 가장 중요하다.** 용역으로 만든 것의 권리를 통째로 넘기면
그 블록을 다시 못 판다. "고객은 사용권, 나는 소유권" 이 기본이고,
독점을 원하면 값을 더 받는다.

---

## 7. 하지 말 것

- **검증 안 된 것을 팔지 않는다.** 한 번 걸리면 1인 하우스는 회복이 없다.
- **"표준 준수" 를 확인 없이 쓰지 않는다.** 확인한 만큼만 쓴다.
- **아날로그를 수주하지 않는다.** PLL·SerDes·ADC 는 범위 밖이다.
- **동시에 두 고객의 커스터마이즈를 받지 않는다.** 둘 다 늦는다.
- **값을 너무 낮게 시작하지 않는다.** 올리기가 내리기보다 훨씬 어렵다.

---
