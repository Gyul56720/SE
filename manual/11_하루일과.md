# 11. 하루 일과와 주간 계획

> **여는 때**: 언제나. 특히 "오늘 뭐 하지" 가 될 때.

---

## 하루

### 시작 (5분)

```bash
cd "$(git rev-parse --show-toplevel)"
bash manual/지금어디.sh
```

`[ ]` 가 붙은 **맨 위 한 줄**만 본다. 그것이 오늘의 일이다.
여러 개를 동시에 하지 않는다.

### 일하는 중 — 고리를 짧게 돈다

| 단계 | 고리 | 한 바퀴 |
|---|---|---|
| 04 모델 | 고치고 → `./golden self` | 10초 |
| 05 RTL | 고치고 → `verilator --lint-only -Wall` | 1초 |
| 06 검증 | 고치고 → `./검증.sh` | 30초 |
| 07 합성 | 고치고 → `synth.sh` | 1분 |

**한 바퀴가 1분을 넘으면 고리가 너무 크다.** 30분 작업하고 한 번
돌리면, 깨졌을 때 30분치 중 어디가 원인인지 모른다.

### 끝낼 때 (10분) — 이것을 빠뜨리지 않는다

```bash
# 1. 오늘 잰 수를 기록한다
./검증.sh 2000 7 | tee -a ../검증결과.txt

# 2. 새로 겪은 막힘을 적는다
$EDITOR manual/10_막힐때.md

# 3. 커밋한다
git add -A && git commit -m "<무엇을 했나>"

# 4. 내일 첫 줄을 확인한다
bash manual/지금어디.sh | tail -5
```

**2번이 가장 아깝기 쉽고 가장 값지다.** 오늘 40분 걸려 푼 것을 안 적으면
석 달 뒤에 또 40분 걸린다. 한 줄이면 된다.

## 하루를 어떻게 나누나

혼자 일할 때 무너지는 방식은 정해져 있다: **재미있는 것(RTL)만 하고
지루한 것(문서·검증)을 미룬다.** 그러면 만든 것을 못 판다.

| 시간대 | 무엇 | 왜 |
|---|---|---|
| 오전 (집중) | **만든다** — 모델, RTL, 알고리즘 | 머리가 제일 맑을 때 |
| 오후 전반 | **검증한다** | 만든 직후가 기억이 살아 있다 |
| 오후 후반 | **문서** 또는 조사 | 집중력이 덜 들고 미루면 안 되는 것 |
| 끝 10분 | 기록·커밋 | |

**문서를 마지막 주에 몰아 쓰지 않는다.** 그때는 왜 그렇게 정했는지
이미 잊었고, 잊은 채로 쓴 문서가 나중에 틀린 답을 준다.

### 금요일 범위 점검 — 15분, 반드시 한다

세 가지만 묻는다.

1. **이번 주에 `지금어디.sh` 의 `[o]` 가 몇 개 늘었나?**
   0개면 막힌 것이다. 다음 주에 같은 방식으로 하면 또 0개다.
2. **스펙 12절(범위 밖)에 추가할 것이 생겼나?**
   "이것도 넣을까" 하고 넘어간 것들. 넣기로 했으면 스펙을 고치고,
   안 넣기로 했으면 **범위 밖에 적는다.** 적지 않으면 계속 생각난다.
3. **3주 안에 못 끝날 것 같으면 무엇을 자를 것인가?**
   02단계에서 미리 정해 둔 것이 있다. 지금 자를 때인지 본다.

> 1인 하우스가 실패하는 가장 흔한 방식은 **범위가 조용히 늘어나는 것**이다.
> 기능이 하나씩 붙고, 완성이 계속 2주 뒤가 되고, 1년이 지나도 판 것이 없다.
> **자르는 결정을 금요일에 15분씩 하면** 그 일이 안 생긴다.

## 막혔을 때의 규칙

**한 문제에 2시간을 넘기지 않는다.**

| 경과 | 하는 일 |
|---|---|
| 0~30분 | 혼자 본다 |
| 30분 | [10_막힐때.md](10_막힐때.md) 를 증상으로 검색한다 |
| 1시간 | **최소 재현 예제**를 만든다. 대개 여기서 풀린다 |
| 2시간 | 그 문제를 **적어 두고 다른 단계로 넘어간다** |
| 다음 날 | 다시 본다 |

최소 재현 예제가 강력한 이유: 문제를 줄이는 과정에서 원인이 드러난다.
그리고 줄여도 재현되면 **그것이 그대로 회귀 시험이 된다.**

## 4~6주 표준 일정 (첫 IP)

| 주 | 무엇 | 끝나면 |
|---|---|---|
| **1주** | 00·01 (설치·한 바퀴), 02·03 (고르기·스펙) | `지금어디.sh` 1~2단계 `[o]` |
| **2주** | 04 C++ 모델, 05 RTL 시작 | 3단계 `[o]`, lint 경고 0 |
| **3주** | 05 RTL 마무리, 06 검증 | 4~5단계 `[o]` |
| **4주** | 06 검증(변이 점수), 07 합성 | 6단계 `[o]` |
| **5주** | 08 문서, 납품 묶음 시험 | 7단계 `[o]` |
| **6주** | 09 값매기기, 공개 | 내놓는다 |

**두 번째 IP 부터는 3주**다. 모델 뼈대, TB 뼈대, 검증 스크립트,
문서 템플릿이 전부 재사용되기 때문이다.

## 여러 IP 를 갖게 되면

첫 제품이 끝나면 이렇게 쌓는다.

1. **같은 계열로 넓힌다.** CRC-32 를 했으면 CRC-16·CRC-8 을
   파라미터로 묶는다. 검증 하니스가 그대로 쓰인다.
2. **붙는 것을 만든다.** 레지스터 파일, APB 브리지, FIFO.
   기존 IP 에 옵션으로 붙여 팔 수 있다.
3. **묶어서 판다.** 블록 셋을 "서브시스템" 으로 묶으면 개별 합보다 비싸다.

세 가지 다 **새 검증 환경이 필요 없다**는 공통점이 있다.
그것이 1인 하우스가 규모를 늘리는 유일한 현실적인 길이다.
