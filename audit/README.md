# audit -- 변경을 실제로 돌려 보는 감사

```
바뀐 파일 ──> 그 파일을 붙드는 검사(이름 + 임포트로 찾음) ──> 격리 판에서 끝까지 돌린다
                     │
                안 걸리면 ──> **"검사 없는 변경"** 이라고 크게 말한다
```

## 왜 있나

이 저장소에서 버그를 잡아 온 것은 눈이 아니라 실행이다. `seek.sh` 는 `bash -n` 과
grep 을 다 통과하고도 한 줄도 안 돌았고(한글 변수명), `sandbox` 의 첫 검사는 한글
파일명이 복사에서 통째로 빠지는 것을 잡았다(git quotepath). "감사 도중에 버그를
잡았습니다" 를 기능으로 만들면 이 꼴이다 -- **바뀐 것에 대응하는 검사를 찾아
실제로 돌리는 것.**

- 미커밋 감사(기본): **지금 트리 사본**에서 돈다 -- 커밋하기 전에 잡는 자리다.
- `--커밋`: HEAD 워크트리에서 돈다 -- 방금 커밋이 성한지 뒤늦게 본다.

## 검사 없는 변경이 제일 큰 발견이다

검사가 걸리지 않은 .py 변경은 통과도 실패도 아니다 -- **아무도 안 본 것**이고, 버그가
샌다면 거기다. 보고에 크게 적는다. 기본 끝값은 그것으로 빨간불을 내지 않는다(늘 우는
경보는 아무도 안 듣는다). `--엄격` 이면 그것도 1 이다.

## 쓰기

```bash
python3 audit/run.py            # 미커밋 변경 감사
python3 audit/run.py --커밋      # 마지막 커밋 감사
python3 audit/run.py --엄격      # 안 덮인 .py 변경도 빨간불
python3 tests/test_audit.py     # 임시 저장소에서 red-green 으로 배선 검사
```

디스코드: `!감사` · `!감사 커밋` (관리 채널만 -- 검사마다 격리 판을 깐다).

## 옆방과의 분업

| | 언제 | 무엇을 |
|---|---|---|
| 여기 audit | 변경 직후 | 그 변경을 붙드는 검사만 골라 돌린다 |
| `scripts/precheck.sh` | 밀기 직전 | 고정 목록을 HEAD 에서 돌린다 |
| `gatekeeper.py` | 커밋 경로 | 저장소 전체 불변식 |
| `self_challenge.py` | 사고 후 | 진단을 red-green 으로 증명해 게이트로 승격 |

감사가 잡은 버그의 진단을 남기고 싶으면 노트가 아니라 self_challenge 로 증명해서
게이트로 만든다 -- 증명 안 된 진단은 노트로도 안 남긴다(이 저장소의 규율).
