# 도구를 쓸 때 지키는 것

이 문서는 원칙이 아니라 **실측 기록**이다. 2026-09-03 하루 동안 오케스트레이터 배관과
진단 도구에서 버그 15개를 고쳤고, 그 15개가 어떤 병이었는지를 세어서 나온 규칙이다.
각 규칙에는 그것을 만든 커밋이 붙어 있다. 규칙이 추상적으로 들리면 커밋을 봐라.

기계로 검사할 수 있는 항목은 `tools/lint_tooling.py` 에 넣었다. 규칙을 새로 추가하면
검사도 같이 추가한다 -- 검사 없는 규칙은 다음 주에 잊힌다.

    python3 tools/lint_tooling.py          # 전부 검사
    python3 tools/lint_tooling.py --list   # 규칙과 근거만 보기
    python3 tests/test_tooling_rules.py    # 검사 자체가 실패해야 할 때 실패하는가

세 번째가 핵심이다. **실패해야 할 때 실패하지 못하는 검사는 아무 소용이 없다.** 첫 판에서 규칙 10 개 중 넷이
실패하지 못했다 -- 셋은 조건을 OR 로 둬서 하나만 남겨도 통과했고, 하나는 되살리는 방법이
약했다. 검사가 없었으면 아무것도 걸러내지 못하는 규칙 넷을 통과로 착각했을 것이다.

**그런데 손으로 쓴 red-green 도 반쪽이다.** 그것이 증명하는 것은 "내가 고른 그 변형에
걸린다"뿐이고, 변형과 규칙을 같은 사람이 같은 때에 쓰므로 맹점을 공유한다 -- 규칙
④(검사기는 대상과 다른 출처)가 red-green 자체에 걸린다. 실제로 심판-무해에서는 규칙이
아니라 **변형을** 고쳐야 했다. 그래서 셋을 겹쳐 쓴다.

  손으로 쓴 변형   그 버그를 되살려 걸리는가. 의도를 담지만 내가 고른다
  유도된 변형      require 패턴를 전부 지우면 걸리는가. **반응 여부**만 증명한다
  규칙의 모양      require 에 OR 가 있는가, 정의부에도 걸리는가. **강도**를 본다

셋째가 실제로 물었다. 붙이자마자 **살아 있는 아무것도 걸러내지 못하는 규칙 둘을 더 잡았다** --
RPM-분리의 `_is_rpm\(e\)` 와 버전-보존의 `_snapshot_code\(` 가 각자의 `def` 줄에도
걸려 있었다. 호출만 지우는 진짜 회귀에는 둘 다 반응하지 못했는데, 손으로 쓴 변형이
정의와 호출을 한꺼번에 바꾸는 바람에 우연히 실패해서 정상으로 보였다.

주석도 패턴를 만족시킨다. 패턴 검사의 어쩔 수 없는 한계다.

## 무엇이 틀렸었나

20 커밋 중 15 개가 내가 만든 도구의 버그 수정이었다. 병으로 묶으면 여섯 가지다.

| 병 | 건수 | 사례 |
|---|---|---|
| else 가 다 삼킨다 | 5 | `429/503/404` -> "구글 문제" · `M>=19` -> "구간 안" · 태그 없음 -> "알려진 방식 밖" · 거리 0 -> "미세조정" · 429 한 덩어리 |
| 내 기계에 없는 것 | 2 | 저장소 `.env` 없음 · `GEMINI_API_KEY_FALLBACK` 없음 |
| 이름을 재보지 않고 믿는다 | 2 | `_model_rank` 가 이름으로 등급 (실측은 26배 반대) · `TIMEOUT=60` (실측 145초) |
| 검사기와 대상이 같은 출처 | 2 | 재계획이 심판을 지움 · 재채점이 저장소 원본 예산을 읽음 |
| 축 자체가 없다 | 2 | 503 에 시간 축 없음 · 기각 사유를 아무도 안 읽음 |
| 형제를 안 찾는다 | 2 | `[3]` 고치고 `[2]` 방치 · `.env` 경로 고치고 환경변수 방치 |

두 가지를 더 기록해 둔다.

**계산층에는 버그가 없었다.** `Fraction` 정확 연산, AST 파싱, rANS, Hadamard, 전개행렬
랭크 -- 0 건. 15 개 전부 **이름 붙이고 · 분류하고 · 보고하는 층**이다. 계산에는 정답이
있어서(3+4=7) 틀리면 바로 드러나지만, 보고층의 "정답"은 내가 지어낸 것이라 대조할
대상이 없다.

**내가 읽어서 찾은 것은 0 건이다.** 13 건은 VM 실행 출력이, 2 건은 사용자의 질문이
잡았다. 이것은 우연이 아니라 이 저장소가 증명하려는 것 자체다 -- 검증이 생성보다 싸다.
내 코드에도 똑같이 적용된다. 나는 내 코드의 나쁜 생성기이고, 실행이 싼 심판이다.

## 규칙

### ① else 는 "모른다"다

분류기를 이렇게 쓰지 마라.

```python
if 아는_경우_1: ...
elif 아는_경우_2: ...
else: <떠오른 것 중 제일 그럴듯한 것>   # 여기가 거짓말이 사는 자리
```

실측된 거짓말들:

    비-200         -> "구글 쪽 문제"      (실은 우리 마감이 60초였다)
    ListModels 503 -> "키가 죽었다"       (실은 용량 문제였다)
    M >= 19        -> "구간 [19,23] 안"   (실은 27, 구간 위였다)
    태그 없음        -> "미분류, 흥미롭다"   (실은 답을 상수로 적어 넣은 코드이었다)
    거리 0          -> "미세조정"           (실은 잴 것이 없었다)
    429            -> "오늘 소진"         (실은 1 분이면 풀리는 것이었다)

낙관도 비관도 아니다. **모르는데 안다고 말한다.** `else` 는 반드시 미지 범주여야 하고,
그 범주는 눈에 띄게 찍혀야 한다.
근거: `f732554`, `25ab7ca`, `860b2d7`, `6be1ed0`

### ② 분류는 상태공간의 분할이어야 한다

떠오른 경우의 나열이 아니라. 범주를 정할 때 "이 셋 말고 무엇이 가능한가"를 먼저 적는다.
`interval` 을 위/안/아래 셋으로 두었더니 **상한 재현(23)과 상한 돌파(22)가 같은 문장**으로
나왔다. 네 자리로 갈랐다: 위 / 상한과 같음 / 상한 아래 / 하한 아래.
근거: `f92748e`, `6be1ed0`

### ③ 이름·휴리스틱은 쓰기 전에 한 번 잰다

`_model_rank` 는 모델 **이름**으로 등급을 매겼다. flash 가 flash-lite 보다 낫다고.
한 번 재니 같은 4692 자 프롬프트를 flash-lite 는 5.45 초에, flash 는 145.55 초에
처리했다. **26 배 반대**였다. 이름으로는 알 수 없는 것이었다.

`TIMEOUT=60` 도 같은 병이다. 재보지 않고 박은 상수라, 145 초짜리 응답에 60 초 마감을
걸어놓고 그 결과로 돌아온 504 를 구글 탓했다.
근거: `0945e18`, `cea7e51`

### ④ 검사기는 대상과 다른 출처에서 읽는다

`planner.replan` 이 `plan.json` 을 통째로 새로 쓰면서, 밖에서 꽂아둔 심판도 같이
날아갔다. 그 뒤로는 LLM 이 제 답에 스스로 합격을 주고 `drive` 는 그것을 `solved` 로
올렸다. **검사기가 대상이 쓰는 파일에서 나오면 검사가 아니다.**

반대 방향도 있다. 재채점 안전망이 런의 예산이 아니라 저장소 원본 예산을 읽어서,
멀쩡한 통과에 "심판이 지워졌다"는 거짓 경보를 붙였다. **거짓 경보는 경보를 죽인다.**
근거: `cdc640b`, `69d5416`

### ⑤ 고친 뒤 형제를 찾는다

`[3]` 판정에서 "200 아닌 것을 뭉치면 진단이 아니다"라고 고쳐놓고 `[2]` 는 그대로 뒀다.
`.env` 시험의 탐색 경로를 고쳐놓고 환경변수는 그대로 뒀다. **둘 다 같은 병의 다른
얼굴이었고 둘 다 다음 실행에서 다시 걸렸다.** 고친 직후 `grep` 으로 같은 모양을 찾는다.
근거: `25ab7ca`, `e0defa3`

### ⑥ 내 기계에 없고 대상에 있는 것을 만들어서 돌린다

없는 것을 테스트하기는 쉽다. 어려운 것은 **있는 것**이다. `.env` 시험이 두 번 걸렸는데
둘 다 "내 컨테이너에는 없지만 VM 에는 있는 것"(저장소 `.env` 파일, `FALLBACK` 환경변수)
때문이었다. 통과는 "이 기계에서만 통과"라는 뜻일 뿐이다.

방법은 하나다. **대상 환경의 조건을 만들어서 돌린다.** 저장소 루트에 가짜 `.env` 를
만들고 두 환경변수를 넣은 채 시험을 돌리는 것. 한 번 그렇게 했고 그때만 통했다.
근거: `819df5f`, `e0defa3`

### ⑦ 없는 축은 리뷰에 안 보인다

`llm_pool` 에는 **시간 축이 아예 없었다.** 실패하면 다음 후보, 그것뿐. 그래서 503 이
쏟아질 때 후보 12 개를 몇 초에 태우고 죽었다. 버전 이력도 없었다 -- 수리가 덮어써서,
"같은 알고리즘을 미세조정한 것인지 교체한 것인지" 잴 대상이 남지 않았다. 기각 사유는
기록되고 있었는데 **아무도 읽지 않았다.**

틀린 것은 읽으면 보이지만 없는 것은 안 보인다. 실패해봐야 드러난다.
근거: `f21f4c2`, `0a4c588`, `30745c2`, `7ec0f6d`
