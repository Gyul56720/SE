# solver — 스펙 하나를 던지면 스스로 개선하며 코드를 내는 루프

디스코드에 과제 설명을 붙여넣고 "이거 풀어줘"라고 하면, 봇이 이 루프에 넘긴다. 루프는
백그라운드에서 계속 돌며 해법을 고쳐 쓰고, 로컬 채점에서 더 좋아질 때만 챔피언을 교체한다.

```
디스코드 "이거 풀어줘 <스펙>"
  → 봇이 스펙을 파일로 저장하고 solver/start.py 에 넘긴다
  → start.py 가 백그라운드로 분리해 띄우고, 살아있는지 확인한 뒤 PID·로그를 보고한다
  → improve.py 가 반복한다: 제안(LLM) → 별도 프로세스 실행 → 로컬 채점 → 더 좋으면 채택
  → 언제든 --status 로 진행, --code 로 지금까지의 최종 코드
```

## 사용

```bash
python3 solver/start.py "<과제 설명 전문>"     # 새 과제 시작
python3 solver/start.py --spec-file spec.md   # 파일에서
python3 solver/start.py --status              # 진행 상황
python3 solver/start.py --code                # 최종 코드
python3 solver/start.py --stop                # 멈춤
```

## 이 루프가 성립하는 조건 — 읽고 시작할 것

**로컬 정답이 없으면 시작하지 않는다.** 이건 제약이 아니라 이 설계의 전제다.

이 저장소의 원칙은 "제안이 아니라 검증된 채택"이다. orchestrator 에서는 노드의 `check()` 가
심판이었고, 여기서는 `metric.py` 가 심판이다. LLM 은 코드를 **제안**할 뿐이고, 그것이 챔피언을
대체하려면 로컬 점수가 **엄격히** 더 높아야 한다.

심판이 없으면 루프는 개선이 아니라 표류다. 리더보드는 하루에 몇 번밖에 못 두드리고 테스트
정답도 없으므로, 손에 든 라벨 데이터 위에서 대회 지표를 재현하는 채점기가 유일한 심판이다.
그래서 `start.py` 는 `ground_truth.csv` 가 없으면 "시작했다"고 말하지 않고 종료한다.

## 데이터를 두는 곳

```
solver/tasks/<slug>/data/
    train/ground_truth.csv    제출과 같은 형식(node/edge 행). 로컬 채점의 정답.
    train/<dataset>.zarr      학습용 입력  (.npy 도 읽는다)
    test/<dataset>.zarr       제출용 입력
```

`dataset` 이름은 파일명에서 확장자를 뗀 것이고, `ground_truth.csv` 의 `dataset` 열과 같아야 한다.

## 해법의 계약

후보 코드는 이것 하나를 만족하면 된다:

```python
def solve(data_dir: str, out_csv: str) -> None:
    """data_dir 안의 각 입력을 읽어 out_csv 에 제출 형식으로 쓴다."""
```

루프는 이걸 **별도 프로세스**로 실행한다. 타임아웃과 격리가 둘 다 필요하기 때문이다 —
LLM 이 쓴 코드는 무한 루프이거나 메모리를 태울 수 있다.

## 무엇이 어떻게 걸러지는가

| 후보의 상태 | 어떻게 되는가 |
|---|---|
| 점수가 올랐다 | 챔피언 교체. `champion.py` 가 갱신된다 |
| 점수가 같거나 낮다 | 기각. 점수는 이력에 남아 다음 프롬프트의 근거가 된다 |
| 문법이 깨졌다 / `solve` 가 없다 | 실행 전 반려. 챔피언은 건드리지 않는다 |
| 멈추지 않는다 | `candidate_timeout` 에서 끊고 실패로 기록 |
| CSV 를 안 만들었다 | 그렇게 기록 |
| 제출 형식이 틀렸다 | 채점 단계에서 예외 → 사유가 그대로 이력에 남는다 |

채택되지 않은 후보 코드도 `candidates/` 에 전부 남는다. 왜 나빴는지가 정보이기 때문이다.

## 산출물

```
solver/tasks/<slug>/
    spec.md          받은 과제 설명 원문
    champion.py      지금까지 최고 점수의 해법  ← 최종 산출물
    champion.json    그 점수 상세 (edge/division, 데이터셋별 TP·FP·FN)
    history.jsonl    매 반복 1줄: 가설, 점수, 채택 여부, 실패 사유
    candidates/      각 반복이 만든 코드
    state.json       pid, 반복 수, 최고 점수
    log              백그라운드 실행 로그
```

전부 파일이다. 프로세스가 죽어도, VM 이 회수돼도 챔피언과 이력이 남고 다시 띄우면 이어서 돈다.

## 정직하게 적어두는 한계

1. **로컬 점수 ≠ 리더보드 점수.** `metric.py` 는 대회 설명을 옮긴 것이고, 설명만으로는 확정할
   수 없는 지점 세 곳(노드 과다 예측 페널티의 식, sparse 라벨 처리, division 매칭 범위)을
   가정으로 두었다. 파일 상단에 A/B/C 로 명시해 뒀다. 리더보드 점수를 알게 되면 로컬 점수와
   비교하라 — 차이가 크면 그 가정부터 의심해야 한다.

2. **학습 데이터에 과적합할 수 있다.** 루프는 로컬 점수만 올린다. 데이터셋이 여럿이면 일부를
   떼어 검증에만 쓰는 편이 안전하다.

3. **루프는 능력을 만들지 않는다.** 탐색을 자동화할 뿐이다. 모델이 그 과제를 못 풀면 점수는
   오르지 않는다. 이 루프가 보장하는 것은 "나빠지지 않는다"와 "왜 안 되는지가 기록된다"이지,
   "반드시 좋아진다"가 아니다.

4. **베이스라인은 일부러 약하다.** 고정 분위수 임계, 모양 무시, 한 프레임만 보는 연결,
   거리 하나로 하는 분열 판정 — 전부 개선 여지다. 바닥이 있어야 '개선'이 성립하기 때문에
   두었을 뿐이다.

## 검증

```bash
python3 tests/test_solver_loop.py     # LLM·실데이터 없이 합성 데이터로 red-green
```

채점기의 정확성(완벽 예측 1.0, 오배선·거리 초과·과다 예측 페널티), 대체 헝가리안이 완전탐색
최적과 일치하는지, 해법 코드가 다른 디렉토리로 복사돼도 도는지(실측으로 겪은 사고),
그리고 채택·기각·반려·타임아웃 네 경로를 전부 확인한다.
