# HLS 합성을 실제로 돌렸다 -- 무엇이 되고 무엇이 안 되는지 (2026-09-19)

이전까지 이 저장소는 "합성 하니스만 만들었고 HLS 도구를 돌린 적이 없다" 였다.
이제 돌렸다. **도구는 PandA Bambu 2024.10** 이고, 이 컨테이너에서 소스로 지었다.

## 도구를 어떻게 구했나 -- 여덟 번째 채널에서 뚫었다

앞의 일곱은 전부 막혔다. **막힌 곳을 적는다** -- "없는 것 같다" 로 끝내지 않는다.

    apt                              없음
    GitHub releases (AppImage)       전 태그 404 (2024.10 · 2024.04 · v2024.03 · v2023.1 · v0.9.8)
    PyPI                             tapa · siliconcompiler 래퍼뿐, 합성기 본체 없음
    conda-forge                      verilator · yosys 뿐
    release.bambuhls.eu              닿지 않음
    docs.amd.com (Vitis HLS 문서)     HTTP 000
    docker pull bambuhls/dev         auth.docker.io 는 통과, 레이어 CDN
                                     production.cloudfront.docker.com 이 403
    ----
    git clone + 소스 빌드            **된다**

소스 빌드에서 막혔던 것과 푼 방법:

    configure: gcc with -m32 and plugin not found   -> gcc-multilib · libc6-dev-i386 · gcc-13-plugin-dev
    clang >= 16.0.0 yes / < 17.0.0 no               -> clang-16 · llvm-16-dev · libclang-16-dev (18 은 너무 새것)
    panda_regressions/Makefile.in 없음              -> --depth 1 클론이라 서브모듈 누락
    ext/Coin-Cbc · ext/lpsolve5 없음                -> 선택 ILP 솔버. 빈 디렉터리를 만들면 automake 가 넘어간다
                                                       (조건부인데도 automake 는 디렉터리 존재를 요구한다)

## 도구가 진짜 도는지부터 확인했다

**"Bambu 가 그냥 고장났다" 는 시시한 설명을 재서 죽인다.** 순수 C 커널:

    fir8.c (8탭 FIR, 64샘플)  ->  rc=0, fir8.v 생성
                                  최대 주파수 101.0 MHz, 최소 슬랙 0.102 ns, 레지스터 37개

Verilog 가 나온다. 도구는 멀쩡하다.

## 무엇이 막는지 -- 1변수 대조 네 개

| 대조 | 바꾼 것 | 결과 |
|---|---|---|
| 1 | 순수 C | **rc=0, Verilog** |
| 2 | 대조1 과 **같은 C 에 `#pragma HLS PIPELINE II=1` 한 줄만 추가** | rc=11 `Loop pipelining pragma not supported` |
| 3 | C++ 템플릿 (프라그마 없음) | **rc=0, Verilog** |
| 4a | `ap_uint` 만 (`hls::stream` 없음) | **rc=0, Verilog, 119~147 MHz** |
| 4b | `hls::stream` 만 (다른 것 없음) | rc=1 `FixStructsPassedByValue` 크래시 |

**대조 2 가 핵심이다.** 같은 파일에서 한 줄만 바꿔 실패를 재현했다.
원인은 C++ 이 아니라 **프라그마 방언**이다.

**대조 4 가 두 번째다.** Xilinx 의 임의정밀 타입(`ap_uint`)은 **Bambu 에서 그냥 된다.**
막는 것은 `hls::stream` 이고, Bambu 의 IR 패스
(`src/frontend_analysis/IR_analysis/FixStructsPassedByValue.cpp:377`) 가 거기서 죽는다.

## 결론 -- 막는 것은 셋이고 서로 독립이다

    1. #pragma HLS 방언      Bambu 는 자기 프라그마 집합을 쓴다.  Xilinx 것을 오류로 낸다
    2. hls::stream          Bambu 의 IR 패스가 크래시한다.  최상위든 내부든 상관없다
    3. 템플릿 무게           ap_fixed 복소 Cholesky 는 프론트엔드에서 30분+ 를 쓴다

1 은 우회할 수 있다(프라그마 652줄을 벗겼고 실제로 다음 단계로 넘어갔다).
**2 는 우회할 수 없다** -- FINN·security·solver 의 모든 스트리밍 코어가 `hls::stream`
을 쓴다.  인터페이스를 배열로 바꿔도 안 된다(본문 안에서도 쓰기 때문).

### 정정 -- 결론으로 적기 전에 고친다

위 2번이 **말뭉치가 실패한 이유는 아니다.**  프라그마를 벗긴 진짜 최상위 셋은
전부 `hls::stream` 패스에 **도달조차 못 했다.**

    cholesky_top (복소 ap_fixed<24,8> 8x8)   rc=124   40분 타임아웃, 프론트엔드
    aes128_top                                rc=124   같음
    mvau_top                                  rc=124   같음

`FixStructsPassedByValue` 크래시는 **그것을 보려고 따로 쓴 최소 사례**에서 봤다.
말뭉치에서 본 것이 아니다.  "말뭉치가 hls::stream 때문에 실패했다" 고 쓰면
**추론을 실측으로 내놓는 것**이 된다.  쓰지 않는다.

그래서 프론트엔드 비용부터 갈랐다.

### 비용의 범인은 ap_fixed 하나다 -- 1변수씩 바꿔 쟀다

실패하는 최상위는 성공하는 것과 **세 가지가 동시에** 다르다(복소 · 고정소수점 · 8x8).
같은 Xilinx Cholesky 소스에 대해 하나씩만 바꿨다.

| 원소 타입 | 복소 | ap_fixed | 크기 | 프론트엔드 시간 | 어디서 멈췄나 |
|---|---|---|---|---|---|
| `float` | 아니오 | 아니오 | 4x4 | **10초** | FixStructsPassedByValue 도달 |
| `float` | 아니오 | 아니오 | 8x8 | **9초** | 같음 |
| `hls::x_complex<float>` | **예** | 아니오 | 8x8 | **9초** | 같음 |
| `ap_fixed<24,8>` | 아니오 | **예** | 8x8 | **>900초 타임아웃** | 못 감 |
| `hls::x_complex<ap_fixed<24,8>>` | **예** | **예** | 8x8 | **>2400초 타임아웃** | 못 감 |

**행렬을 4배로 키워도 공짜다(10초 vs 9초).  복소로 만들어도 공짜다(9초).
고정소수점으로 만들면 9초가 900초를 넘는다 -- 최소 100배.**
알고리즘은 한 줄도 안 바뀌었다.

이유는 스펙 2.3절에 이미 적어 둔 것이다, 컴파일러 쪽에서 본 것뿐이다.
`ap_fixed` 의 모든 산술 연산자가 결과 폭을 컴파일 타임에 계산하므로, 수식 하나가
서로 다른 타입의 격자를 인스턴스화한다.  **그 성질이 이 타입 시스템을 안전하게
만드는 바로 그 성질이고(폭 실수가 런타임 절단이 아니라 컴파일 오류가 된다),
여기서 합성을 막은 것도 그 성질이다.**

### 그래서 hls::stream 은 말뭉치의 장벽이 맞다 -- 이제 실측이다

원소 타입만 `float` 로 바꾸면 진짜 Xilinx Cholesky 가 **10초에 컴파일되고**
`FixStructsPassedByValue.cpp:377` 에서 죽는다 -- 최소 사례(대조 4b)와 **같은 줄이다.**
위에서 철회했던 추론이 이제 잰 것이 됐다.

## 결론 -- 장벽 셋, 전부 1변수 대조로 갈랐다

    1. #pragma HLS 방언      대조 2.  프라그마 652줄을 벗겨 우회했다
    2. hls::stream          대조 4b + 10.4.2.  못 우회한다 -- 모든 스트리밍 코어가 쓴다
    3. ap_fixed 비용         위 표.  타입 시스템 자체의 성질이라 못 우회한다

**이 말뭉치는 Bambu 로 합성되지 않았다.  설치 문제가 아니다.**
Vitis HLS 가 필요하고, 그것은 이 환경에서 구할 수 없다(위 일곱 채널).

## 내가 틀렸던 것 두 개 -- 남겨 둔다

**하나.** 프라그마를 벗길 때 `sed '/^\s*#pragma\s\+HLS/d'` 를 썼다.  역슬래시로
이어진 프라그마(`Vitis_solver/cholesky.hpp:539-540`)의 **첫 줄만 지워** 고아 토큰
`CholeskyTraits::UNROLL_FACTOR` 를 남겼고, 그것이 C++ 오류로 나왔다.  나는 그것을
하마터면 "Xilinx 코드가 비표준이다" 로 읽을 뻔했다.  **내 도구가 틀린 것이었다.**
말뭉치 전체에 그런 프라그마는 딱 하나다.  perl 로 이어진 줄까지 지우게 고쳤고,
고아 토큰 수를 0 으로 세어 확인한다.

**둘.** 최상위 함수명을 `aes_top` 으로 줬는데 실제 이름은 `aes128_top` 이었다.
Bambu 는 `Function aes_top not found in IR` 로 정확히 말했는데, 이것도 하마터면
합성 실패로 읽을 뻔했다.

두 오류 다 **"실패했다" 는 결과 자체는 맞았지만 이유가 틀렸을 뻔했다.**
그래서 실패 로그의 첫 줄을 매번 직접 읽었다.
