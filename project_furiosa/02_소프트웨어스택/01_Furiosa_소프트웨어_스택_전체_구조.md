# 01. Furiosa 소프트웨어 스택 전체 구조

## 1. 왜 알아야 하는가

AI 칩(NPU)은 하드웨어 스펙(TOPS, 메모리 대역폭)만으로 성능이 나오지 않는다. 모델을 실제로
칩 위에서 돌리려면 "프레임워크의 연산자 → 칩이 이해하는 명령어 → 칩 위에서의 실행"까지
이어지는 소프트웨어 파이프라인 전체가 필요하기 때문이다. 이 파이프라인의 각 층이 무엇을
하는지 모르면, 면접에서 "NPU 회사에서 SW 엔지니어가 뭘 하냐"는 질문에 컴파일러/런타임/
양자화/서빙 엔진 중 어느 레이어를 말하는지조차 구분하지 못한다. 또한 하드웨어 아키텍처
(TCP, PE, 슬라이스)와 소프트웨어 스택이 어떻게 1:1로 대응하는지 이해해야, "왜 이 회사는
컴파일러를 자체 개발하는가"라는 근본적 질문에 답할 수 있다.

## 2. 정의와 구조

Furiosa의 소프트웨어 스택은 최하층 하드웨어 제어부터 최상층 배포까지 6개 레이어로
구성된다 (developer.furiosa.ai/overview/software_stack.html 기준).

### 레이어 1 — 커널 디바이스 드라이버 + 펌웨어 + PE 런타임(PERT)

가장 아래층. "The kernel device driver enables the Linux operating system to recognize NPU
devices and expose them as Linux device files." 즉 리눅스가 NPU를 `/dev/` 아래 디바이스
파일로 인식하게 만드는 역할이다. 펌웨어는 NPU 칩 위에서 직접 실행되고, PERT(PE Runtime)가
저수준 API를 제공하며 호스트 런타임과의 통신 및 PE(Processing Element) 리소스의 스케줄링/
관리를 담당한다.

실제 설치 절차(developer.furiosa.ai/get_started/prerequisites.html)로 이 레이어를 구체적으로
확인할 수 있다: 지원 OS는 "Ubuntu 22.04 LTS (or Debian Bookworm) or later, or Rocky Linux 10 /
RHEL 10", 최소 커널은 "Linux Kernel 6.3 or later"이며, APT로
`sudo apt install build-essential linux-modules-extra-$(uname -r)` 후
`sudo apt install furiosa-driver-rngd furiosa-smi`로 드라이버를 설치하고
`furiosa-smi info`로 NPU 인식 여부를 확인한다.

### 레이어 2 — Furiosa 컴파일러

"The Furiosa Compiler optimizes model graphs and generates executable programs for the NPU."
PyTorch 등에서 만든 모델 그래프를 받아 그래프 레벨 최적화, 연산자 융합(operator fusion),
메모리 할당 최적화, 스케줄링, 레이어 간 데이터 이동 최적화를 수행해 NPU 실행 파일을 만든다.
`torch.compile()`의 FuriosaBackend나 `furiosa-llm` 패키지를 쓸 때 사용자에게는 이 과정이
투명하게(자동으로) 일어난다.

ISCA 2024 논문("TCP: A Tensor Contraction Processor for AI Workloads")은 이 컴파일러가
내부적으로 5단계로 동작한다고 공개했다.

1. **Primitive Operator Conversion** — PyTorch 등 프레임워크의 방대한 연산자를 element-wise
   연산, 특정 축 reduction, 선형대수 연산, reshape/indexing/slice, type conversion, 비교 연산
   등 소수의 기본 연산자로 분해한다.
2. **Tensor Kernel Generation** — 기본 연산자들을 read-contraction-vector-write 순서의
   커널로 클러스터링한다. 목표는 "연산자를 융합하고 중복 텐서 사용을 제거해 데이터 재사용을
   극대화"하는 것이다.
3. **Low-Level Operator Generation** — 커널을 저수준 연산자로 변환하고, 인접 레이어 간 shape가
   맞지 않으면 bridge operator를 삽입하며, 비용 함수로 최적 옵션을 고른다.
4. **Command Generation** — 저수준 연산자를 fetch/contraction/vector/transpose engine 등
   하드웨어 서브유닛에 (대체로 1:1로) 대응하는 커맨드 리스트로 변환한다.
5. **Binary Creation through Scheduling & Resource Allocation** — "a mix of heuristics, ILP
   (integer linear programming), and genetic algorithms"로 커맨드 실행 시점과 메모리 배치를
   결정해 SRAM(DM 슬라이스)/RF에 텐서를 매핑하고 최종 실행 파일을 만든다.

### 레이어 3 — Furiosa 런타임

"The Runtime loads the executables generated by the Furiosa compiler and runs them on the
NPU." 컴파일러가 만든 실행 파일을 로드해 NPU 프로그램 스케줄링, NPU/호스트 RAM 메모리 할당,
다중 NPU에 대한 통합 인터페이스 제공을 담당한다.

### 레이어 4 — Furiosa 모델 컴프레서 (양자화)

"The Furiosa Model Compressor is a toolkit for model calibration and quantization." 모델을
저정밀도로 변환하는 툴킷으로, BF16(W16A16)/FP8(W8A8)을 지원하고 INT8/INT4는 계획 중이다.

### 레이어 5 — Furiosa-LLM (응용 계층)

"Furiosa-LLM is a high-performance inference engine for LLM models, such as Llama and GPT-J."
vLLM 호환 API, PagedAttention, continuous batching, Hugging Face Hub 지원, OpenAI 호환 API
서버를 제공한다.

### 레이어 6 — Kubernetes 지원 (배포 계층)

"FuriosaAI's device plugin enables Kubernetes clusters to recognize FuriosaAI's NPUs and
schedule them for workloads." 클러스터 환경에서 NPU를 스케줄링 가능한 자원으로 노출한다.

### 공개 저장소와의 대응 관계

`github.com/furiosa-ai/furiosa-sdk`는 "deep-neural network inference using FuriosaAI NPU
chips"용 SDK로, 컴파일러/프로파일러/CLI/Python 바인딩을 제공한다. 최상위 구조는 `cpp/`(C++
코드), `python/`(바인딩), `docs/`, `examples/`, `tests/`, `Dockerfile`, `LICENSE.txt`
(Apache-2.0)이며 커밋 1,594개, 최신 릴리스 v0.9.0, archived/deprecated 표시는 없다. 단,
이 저장소가 공개하는 것은 폴더 구조/메타데이터 수준이며, 위에서 설명한 5단계 컴파일러
파이프라인이나 마이크로아키텍처 세부의 실제 구현 코드가 저장소의 어느 파일에 있는지는
근거 자료에 명시되지 않는다.

## 3. 핵심 사실 (Killing Fact)

$$ \boxed{\ \text{6-Layer Stack: Driver/Firmware/PERT} \rightarrow \text{Compiler} \rightarrow \text{Runtime} \rightarrow \text{Model Compressor} \rightarrow \text{Furiosa-LLM} \rightarrow \text{K8s}\ } $$

이 6개 레이어는 순서대로 "칩을 리눅스가 인식 → 모델을 칩 명령어로 변환 → 실행 파일을 칩에서
구동 → 모델을 가볍게 압축 → LLM 서빙 API 제공 → 클러스터에 배포"라는 파이프라인을 완성한다.
어느 한 레이어가 빠지면 나머지 레이어가 존재해도 모델을 실제로 서빙할 수 없다는 점에서,
이 순서 자체가 핵심 사실이다.

## 4. 핵심 설계 기법

### 기법 A: 연산자 분해와 커널 클러스터링 (컴파일러 1~2단계)

프레임워크마다 다른 수천 개의 연산자를 소수의 기본 연산자로 먼저 분해한 뒤, 다시
"read-contraction-vector-write" 패턴으로 묶어 커널을 만든다.

**왜 이렇게 설계했는가:** 프레임워크 연산자를 하드웨어에 직접 매핑하려 하면 프레임워크마다,
모델마다 별도의 컴파일 경로가 필요해진다. 소수의 기본 연산자로 먼저 통일하면 어떤
프레임워크에서 온 모델이든 동일한 하드웨어 매핑 로직을 재사용할 수 있고, 이후 단계에서
연산자를 자유롭게 융합해 데이터 재사용을 극대화할 수 있다.

### 기법 B: 비용 함수 기반 저수준 연산자 선택 (컴파일러 3단계)

레이어 간 텐서 shape가 맞지 않을 때 bridge operator를 자동 삽입하고, 여러 저수준 구현
후보 중 비용 함수로 최적안을 고른다.

**왜 이렇게 설계했는가:** 레이아웃 변환은 비용이 큰 연산이므로, 사람이 매번 수동으로
호환성을 맞추는 대신 컴파일러가 비용 모델을 근거로 자동 최적화하지 않으면 다양한 모델
아키텍처를 빠르게 지원할 수 없다.

### 기법 C: ILP + 유전 알고리즘 혼합 스케줄링 (컴파일러 5단계)

커맨드 실행 시점과 메모리 배치를 휴리스틱, ILP(정수계획법), 유전 알고리즘을 혼합해
결정한다.

**왜 이렇게 설계했는가:** 텐서를 SRAM/RF 어디에 배치하고 언제 실행할지의 탐색 공간은
축약이 임의의 축을 따라 가능하기 때문에 매우 크다. 단일 알고리즘(순수 ILP만, 혹은 순수
휴리스틱만)으로는 실용적 시간 안에 좋은 해를 못 찾거나 최적성이 떨어지므로, 여러 기법을
혼합해 절충한다.

### 기법 D: 컴파일러/런타임/양자화/서빙엔진의 레이어 분리

컴파일(정적, 모델→실행파일), 런타임(동적, 실행파일 구동), 양자화(모델 압축), LLM 서빙
(API/배칭)을 물리적으로 분리된 레이어로 둔다.

**왜 이렇게 설계했는가:** 예를 들어 양자화 포맷(FP8, INT8 등)이 늘어나도 컴파일러/런타임을
건드릴 필요가 없고, 서빙 엔진에 새 기능(continuous batching 등)을 추가해도 하드웨어 제어
로직에는 영향이 없다. 레이어 경계가 각 팀의 책임 경계와 일치해 독립적으로 개발/배포할 수
있다.

## 5. 자주 하는 오해 / 주의할 점

- **"NPU SW = 드라이버만 있으면 된다"는 오해**: 드라이버/펌웨어는 최하층 한 레이어일 뿐이고,
  실제 모델 성능을 좌우하는 것은 컴파일러의 연산자 융합/스케줄링 품질이다. GPU와 달리 NPU는
  범용 커널 라이브러리(cuBLAS 같은)에만 의존할 수 없어 컴파일러 역할이 더 크다.
- **컴파일러와 런타임을 혼동**: 컴파일러는 "모델 → 실행 파일"을 만드는 정적(static) 단계이고,
  런타임은 그 실행 파일을 "실제로 칩 위에서 구동"하는 동적(dynamic) 단계다. 컴파일은 배포 전
  한 번, 런타임은 매 추론 요청마다 동작한다.
- **furiosa-sdk 저장소 = 전체 구현이라는 오해**: 공개 저장소는 폴더 구조와 바인딩 수준만
  보여줄 뿐, 논문에 기술된 5단계 컴파일러 세부 알고리즘의 실제 구현 위치는 근거 자료로
  확인되지 않는다. "공개 = 전체 소스 공개"가 아니다.
- **양자화(레이어 4)를 컴파일러(레이어 2)의 일부로 착각**: 모델 컴프레서는 컴파일 이전에
  모델 자체를 압축하는 별도 툴킷이며, 컴파일러는 이미 양자화된(또는 원본) 모델 그래프를
  입력으로 받아 하드웨어 실행 파일로 변환하는 다른 단계다.

## 6. 대표예제 (추론 연습)

### 예제 1

Q: 어떤 NPU 스타트업이 "우리는 컴파일러팀 인원이 런타임팀보다 훨씬 많다"고 한다면, 왜
그럴 가능성이 높은지 이 챕터의 근거로 설명하라.

**풀이:**

1단계 — 런타임(레이어 3)은 이미 만들어진 실행 파일을 로드해서 스케줄링/메모리 할당만
수행하는, 상대적으로 안정적이고 범용적인 로직이다.
2단계 — 반면 컴파일러(레이어 2)는 연산자 분해→커널 클러스터링→저수준 변환→커맨드 생성→
스케줄링까지 5단계 파이프라인 전체를 담당하며, 새로운 모델 아키텍처(MoE, 새 attention
변형 등)가 나올 때마다 이 파이프라인 전체를 다시 검증/확장해야 한다.
3단계 — 특히 5단계의 ILP+유전 알고리즘 혼합 스케줄링처럼 최적화 문제 자체가 난이도 높은
연구 영역이라, 컴파일러 쪽에 훨씬 많은 엔지니어링 리소스가 들어갈 수밖에 없다.

**답: 컴파일러는 5단계의 복잡한 최적화 파이프라인을 새 모델마다 갱신해야 하는 반면, 런타임은 상대적으로 안정된 실행 계층이기 때문이다.**

### 예제 2

Q: Furiosa-LLM(레이어 5)에 새로운 양자화 포맷(예: NVFP4A16)을 지원하려면, 스택의 어느
레이어들을 건드려야 하는지 순서대로 설명하라.

**풀이:**

1단계 — 먼저 레이어 4(모델 컴프레서)가 해당 포맷으로 모델을 캘리브레이션/양자화할 수
있어야 한다.
2단계 — 그 양자화된 모델 그래프를 레이어 2(컴파일러)가 인식하고, 하드웨어의 Contraction
Engine이 해당 비트폭(DPE가 한 번에 처리하는 값 개수)에 맞춰 명령어를 생성할 수 있어야 한다.
3단계 — 레이어 3(런타임)은 새 포맷에 맞는 실행 파일을 그대로 로드하면 되므로 직접적인
변경은 상대적으로 적다.
4단계 — 마지막으로 레이어 5(Furiosa-LLM)가 이 포맷으로 서빙 요청을 받을 수 있도록 API/
설정을 노출해야 한다.

**답: 모델 컴프레서(4) → 컴파일러(2) → (런타임(3)은 대체로 무변경) → Furiosa-LLM(5) 순으로 확장이 필요하다.**

## 7. 유제 (면접 예상 질문)

1. Furiosa 소프트웨어 스택에서 "정적 단계"와 "동적 단계"를 나누어 설명하라. *(힌트: 컴파일 시점 vs 추론 시점을 기준으로 레이어를 분류)*
