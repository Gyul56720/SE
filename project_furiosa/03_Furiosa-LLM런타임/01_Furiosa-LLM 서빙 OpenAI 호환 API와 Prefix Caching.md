# 01. Furiosa-LLM 서빙: OpenAI 호환 API와 Prefix Caching

## 1. 왜 알아야 하는가

대규모 언어 모델(LLM) 서빙 환경에서 여러 요청이 동일한 시스템 프롬프트나 공통 명령 템플릿, 문서 기반 QA 등의 공통 접두사를 공유할 때, 이를 매번 처음부터 다시 연산하면 불필요한 중복 계산과 지연이 발생하기 때문에 실무에서는 접두사 캐싱 기법이 필수적이다. 또한 OpenAI 호환 API를 지원함으로써 기존의 표준화된 생태계 및 클라이언트 라이브러리를 코드 수정 없이 그대로 NPU 기반 인프라에 연동할 수 있으므로, 시스템 도입 비용과 개발 장벽을 대폭 낮출 수 있다.

## 2. 정의와 구조

### Furiosa-LLM 서빙 개요
Furiosa-LLM은 대형 언어 모델 및 멀티모달 모델을 위한 고성능 추론 엔진으로, vLLM 호환 API(LLM, LLMEngine, AsyncLLMEngine API) 및 OpenAI 호환 서버를 제공한다. 사용자는 `furiosa-llm serve [ARTIFACT_PATH]` 명령을 통해 서버를 실행할 수 있으며, 채팅 템플릿(`--chat-template`), 도구 호출 파서(`--tool-call-parser`), reasoning 파서 등을 함께 설정할 수 있다.

### Prefix Caching (프리픽스 캐싱) 동작 원리
접두사 캐싱의 목적은 공통 프롬프트 접두사를 가진 여러 요청에서 이전에 계산된 KV 캐시를 재사용하여 중복 계산을 제거하는 것이다. 스케줄러가 캐시 항목을 자동으로 관리하며, 새 요청과 대조하여 일치하는 항목을 재사용한다. 특히 토큰 레벨에서 작동하며, 효율적인 접두사 매칭을 위해 **radix tree (기수 트리)** 데이터 구조를 사용하여 가장 긴 토큰 정확 일치의 KV 블록을 재사용한다. 하이브리드 어텐션 모델의 경우, 전역 어텐션과 슬라이딩 윈도우 어텐션이 동일한 범위에서 유효할 때만 접두사 재사용이 가능하다. 접두사 캐싱은 기본적으로 활성화되어 있으며, 메모리 압력 증가 시 자동으로 축출된다.

## 3. 핵심 사실 (Killing Fact)

$$ \boxed{\ \text{Time-to-First-Token Reduction: } 50\% \sim 90\%\ } $$

긴 공유 접두사를 가진 요청에서 접두사 캐싱을 적용할 경우, 첫 토큰까지의 생성 시간(TTFT)을 50~90% 단축시킬 수 있음을 나타내는 핵심 성능 지표이다.

## 4. 핵심 설계 기법

### 기법 A: Radix-Tree 기반 접두사 매칭

토큰 레벨에서 작동하며 효율적인 접두사 매칭을 위해 radix tree 데이터 구조를 사용하여 가장 긴 토큰 정확 일치의 KV 블록을 재사용한다.

**왜 이렇게 설계했는가:** 공통 프롬프트 접두사를 가진 여러 요청 간에 중복 계산을 제거하고 첫 토큰까지의 생성 시간을 단축하기 위해서이다.

### 기법 B: OpenAI 호환 API 서버

/v1/chat/completions, /v1/completions, /v1/responses, /v1/embeddings 등 표준화된 엔드포인트를 제공하여 기존 OpenAI 클라이언트 코드와 호환되도록 동작한다.

**왜 이렇게 설계했는가:** 기존의 표준화된 생태계 및 클라이언트 라이브러리를 코드 수정 없이 그대로 NPU 기반 인프라에 연동할 수 있도록 하기 위함이다.

### 기법 C: 하이브리드 KV 캐시 관리

전역 어텐션과 슬라이딩 윈도우 어텐션이 동일한 범위에서 유효할 때만 접두사 재사용이 가능하도록 관리한다.

**왜 이렇게 설계했는가:** 슬라이딩 윈도우와 전역 어텐션이 혼합된 모델 구조에서 캐시 일관성과 정확성을 보장하기 위함이다.

## 5. 자주 하는 오해 / 주의할 점

처음 접할 때 beam search가 stream과 병행 가능하다고 오해하기 쉬우나, 근거 자료에 따르면 beam search는 stream과 병행 불가하다. 또한 에피머럴 스토리지를 사용할 경우 디스크 압박 시 캐시가 제거될 위험이 있으므로, 모델 캐시용으로 PVC(Persistent Volume Claim)를 구성해야 한다는 점을 놓치기 쉽다. 샘플링 파라미터의 우선순위가 요청 본문 > generation_config.json > API 기본값 순서로 적용된다는 점도 주의해야 한다.

## 6. 대표예제 (추론 연습)

### 예제 1

동일한 시스템 프롬프트(200토큰 분량)를 공유하는 10개의 동시 요청이 푸리오사 LLM 서버로 들어왔을 때, 접두사 캐싱이 활성화된 상태에서의 동작 추론

**풀이:**

1단계 — 첫 번째 요청이 처리될 때, 시스템 프롬프트에 해당하는 200토큰의 KV 캐시가 Radix-tree 구조에 저장된다. 2단계 — 이후 들어오는 나머지 9개의 요청은 스케줄러가 Radix-tree를 통해 공통 접두사를 대조하고 가장 긴 토큰 정확 일치 블록을 찾아낸다. 3단계 — 중복 계산 없이 기존에 계산된 KV 캐시를 재사용하므로, 첫 토큰까지의 시간(TTFT)이 50~90% 단축된다.

**답: 시스템 프롬프트 영역의 중복 연산이 제거되며, 후속 요청들의 첫 토큰 생성 시간이 대폭 단축된다.**

### 예제 2

OpenAI 호환 API를 사용하는 클라이언트 코드에서 `model="EMPTY"`로 설정된 cURL 요청을 보낼 때 서버 측 모델 이름 처리 방식 추론

**풀이:**

1단계 — 클라이언트가 `/v1/chat/completions` 엔드포인트로 요청을 보낼 때 본문에 `model` 파라미터를 포함한다. 2단계 — 푸리오사 LLM 서버의 API 파라미터 규정에 따라, 요청 본문의 model 파라미터(예: "EMPTY")는 서버 측에서 무시되고 실행 중인 아티팩트의 모델 설정이 적용된다. 3단계 — 따라서 클라이언트는 별도의 모델 ID 변경 없이 표준화된 방식으로 응답을 받을 수 있다.

**답: 요청 본문의 model 파라미터는 서버에서 무시되고 실행 중인 모델 아티팩트에 맞춰 요청이 처리된다.**

## 7. 유제 (면접 예상 질문)

1. Radix-tree 기반 접두사 캐싱이 메모리 압력 상황에서 어떻게 관리되며, 비활성화하려면 어떤 서버 실행 옵션을 사용해야 하는가? *(힌트: furiosa-llm serve 명령어의 옵션과 메모리 압력 시의 자동 축출 동작을 확인할 것.)*
2. 푸리오사 LLM 서빙 환경에서 빔 서치(beam search)를 사용할 때 스트리밍(stream) 기능과 함께 사용할 수 없는 이유는 무엇인가? *(힌트: 근거 자료의 주의 사항 항목을 참고할 것.)*
3. 쿠버네티스 환경에서 대형 모델 로딩을 대비하여 헬스체크 설정 시 주의해야 할 점과 권장되는 초기 지연 시간(initialDelaySeconds)은 무엇인가? *(힌트: k8s_deployment.html 문서의 헬스체크 및 설정 요구사항을 확인할 것.)*

## 8. 다음 챕터와의 연결

이번 챕터에서 학습한 Furiosa-LLM 서빙 및 OpenAI 호환 API 구조는, 단일 NPU를 넘어 여러 RNGD 카드에 걸쳐 모델을 나누어 실행하는 다음 챕터의 모델 병렬화(Model Parallelism) 및 tensor_parallel_size 제약 조건과 직접적으로 연결된다.
