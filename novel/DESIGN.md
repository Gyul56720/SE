# 소설 오케스트레이션 — 무엇을 떼오고 무엇을 바꿨나

원 설계 문서(Director-Actor + LangGraph + Critic)를 기반으로, 이 저장소가 이미 값을 치르고
배운 것들에 맞춰 재구성했다.

## 떼온 것

| 출처 | 무엇을 | 왜 |
|---|---|---|
| `gates/__init__.py` | **`check(ctx) -> list[위반]` 규약** | 소설에서 "실패했다"는 수리 신호가 못 된다. 어느 규칙이 어디서 왜 깨졌는지가 있어야 되먹일 것이 생긴다 |
| `plan_schema.py` | 파일 영속 + 재개 | 장편은 며칠 돌고 반드시 중간에 죽는다 |
| `orchestrator.py` | 단위별 즉시 저장, verified 건너뛰기 | 재개가 공짜가 된다 |
| `llm_pool.py` | 쿼터·모델 자동 전환 | 그대로 쓴다 |
| `mathgen`, `compression` | **심판 분리 원칙**, 격리 실행, design/holdout | 이 저장소의 중심 교훈 |
| `solve.py` | `rounds.jsonl` 식 라운드 기록 | 도는 중에 보이고 죽어도 남는다 |
| 원 문서 | Director-Actor 분리, `inner_thought`/`speech` 분리, `is_letter_mode`, Dialogue-to-Description | 여기는 원 설계가 정확했다 |

`inner_thought`와 `speech`의 분리는 하루키 문체의 핵심을 제대로 기계화했다. 말과 속마음의
괴리가 곧 그 문체다. 편지 모드로 동기 대화를 강제 차단하는 것도 소설의 실제 구조와 맞는다.

## 바꾼 것

### 1. Critic 을 둘로 갈랐다 ← 가장 큰 변경

원 설계의 Critic 은 LLM 이 LLM 출력을 주관적으로 평가하고 **롤백을 결정**했다.
`mathgen/README.md` 가 그것을 하지 말라고 적어둔 구조다(DeepMind, *LLMs Cannot Self-Correct
Reasoning Yet* — 내재적 자기교정은 개선이 없거나 성능을 떨어뜨린다).

    기계 관문 (novel/gate.py)  -- 결정적으로 판정되는 것만. **기각 권한을 갖는다**
    LLM 비평가                 -- "하루키다운가" 같은 취향. **자문만. 기각 권한 없음**

"소설엔 sympy 가 없으니 어쩔 수 없다"가 아니다. 요구된 검사의 상당수가 기계적으로 판정된다
(V001~V008). 그것까지 LLM 의 변덕에 맡길 이유가 없다.

**2026-09-04 축소**: 그 원칙을 한 걸음 더 밀어, 기계가 판정할 **자격**이 있는 것만 남겼다.
모순은 사실이라 판정하지만, 감정 폭·리듬·분량·클리프행어는 의견이다. 아래 표에서 굵게
표시되지 않은 항목들(V002·V003·V005·V006 등 13개)은 관문에서 빠졌고 프롬프트 규율로만
남았다. 목록은 `novel/README.md` 를 보라.

### 2. 단측 압력을 양측으로 — 미도리를 지키는 관문

원 설계 §6: *"미도리가 갑자기 지나치게 쾌활하게 행동하여 상실의 분위기를 저해한다면 롤백"*.

밝은 쪽 이탈만 벌하고 어두운 쪽은 안 벌하면 수십 턴 뒤 전체가 균일한 우울로 수렴한다.
압축에서 3진 양자화로 굴러떨어진 것과 같은 퇴화다. 그리고 **미도리는 진짜로 웃긴 인물**이라,
밝음만 벌하는 관문은 소설의 절반을 삭제한다.

그래서 수준이 아니라 **폭**을 본다. `Character.emotion_envelope` 로 인물별 하한을 두어
(미도리: `{"joy": 40}`), 씬 안에서 그 축이 한 번도 거기 닿지 않으면 **기각**한다.

### 3. 나오코↔미도리 축을 스키마에 넣었다

원 문서 §2 가 이 소설의 진짜 상태 공간을 정확히 짚었다 — 죽음의 인력과 삶의 추동 사이의
동요. 그런데 §4 스키마에는 그 축이 없고 `joy/melancholy/isolation` 셋뿐이었다.
`narrative_pull`(−100 나오코 … +100 미도리)을 추가했다. **문서 자신의 가장 좋은 통찰이
구현에 안 실려 있었다.**

### 4. 화자 부재 씬의 구멍을 막았다

Actor 들이 자율 상호작용하면 화자가 없는 씬이 필연적으로 생기는데, 1인칭 회고는 그것을
서술할 수 없다. 원 설계는 이 문제를 다루지 않았다. 해답은 문서가 이미 갖고 있었다 —
편지 모드다. 이제 규칙으로 강제한다(V007): **화자가 없는 씬은 `letter` 또는 `reported`
여야 한다.** 원작이 나오코의 요양원을 편지와 레이코의 입으로 전달하는 것과 같다.

### 5. 회고 프레임을 분위기가 아니라 상태로

"37세의 회상"이 프롬프트의 분위기 지시로만 있었다. 그 프레임의 힘은 **서술자가 결말을 이미
안다는 아이러니**에서 나온다. `Novel.narrator_foreknowledge` 로 상태화해서 Narrator 가
씬마다 흘리게 한다. 부탁이 아니라 주입이다.

### 6. LangGraph 를 쓰지 않는다

`plan_schema.py` 첫 문단이 이 저장소의 실측 교훈을 적어놨다:

> *"인메모리 상태(LangGraph MemorySaver 등)는 프로세스 재시작에 소실되고, 메모리 노트는
> 읽히지 않으면 무효다."*

원 설계 §3.2 가 추천하는 것이 정확히 그것이다. 이미 값을 치르고 배운 것을 새 에이전트에서
되풀이할 이유가 없다. `Novel.save()` / `next_pending()` 으로 대체했다 — 소설은 선형이라
DAG 도 필요 없고 씬 시퀀스면 된다.

### 7. Pydantic 대신 dataclass

`requirements.txt` 에 pydantic 이 없다. 의존성을 늘리지 않고 `plan_schema.py` 와 같은 모양을
쓴다.

## 관문이 검사하는 것

| 규칙 | 무엇 | 등급 |
|---|---|---|
| V001 | 턴 형식·감정 범위 | hard |
| V002 | 턴당 감정 급변 (>35) | hard |
| V003 | 감정 폭 붕괴 / 인물 봉투 미달 | soft / **hard** |
| V004 | 타인 내면을 사실로 서술 (시점 위반) | hard |
| V005 | 감정 직접 서술 | 1회 soft, 그 이상 hard |
| V006 | 푼크툼 유실 | soft |
| V007 | 화자 부재 씬의 직접 서술 | hard |
| V008 | 지식 누출 | hard |

**soft 를 둔 이유**가 있다. 과잉 기각하는 심판은 맞는 답도 버린다 — 직선거리에서 상대 임계만
쓰다가 진짜 최소가 0 일 때 정답을 기각한 것이 그 사례다. 한국어 패턴 검사는 정밀도가 100%
가 아니므로 애매한 것은 기각이 아니라 보고로 내린다.

과잉 기각을 실제로 막는지도 회귀 검사에 박았다:

- `"나는 미도리가 ~라고 생각했다"` → **통과** (화자의 추측이지 단정이 아니다)
- 대사 안의 `"난 외로웠다"` → **통과** (금지되는 것은 서술이지 대사가 아니다)
- 턴이 하나뿐인 인물 → 폭 붕괴로 보고하지 않는다 (변동 폭이 0 인 게 당연하다)

마지막 것은 실제로 처음에 오검출을 냈고, 깨끗한 씬을 흔드는 것을 보고 고쳤다.

## 아직 없는 것

`director.py` / `actors.py` / `narrator.py` — LLM 을 부르는 세 조각. 원 문서의 프롬프트가
좋아서 그대로 쓰되 새 스키마(`narrative_pull`, `mode`, `foreknowledge`)에 맞춰 조정하면 된다.
`drive.py` — 씬 시퀀스 루프. 관문 위반 목록을 Director/Actor 프롬프트에 되먹이는 부분.

**점수판도 아직 없다.** 버전 2가 버전 1보다 나은지 잴 방법이 없으면 눈 감고 튜닝하게 된다.
최소한 고정 시드 씬 세트 + 관문 통과율 + 소규모 홀드아웃 인간 A/B 가 필요하다.

## 저작권

인물(와타나베·나오코·미도리·레이코)과 세계를 그대로 쓰고 장편 분량을 생성하면 2차적
저작물이 된다. 개인 실험이면 무방하나 배포·공개는 다른 문제다.

**아키텍처는 인물에 의존하지 않는다.** 구조 매핑(회고 1인칭, 이항 대립 축, 편지 모드,
푼크툼, 절제된 묘사)만 남기고 인물과 세계를 창작으로 바꾸면 그대로 돈다. `state.py` 의
`Character` 와 `emotion_envelope` 가 이미 그렇게 일반화돼 있다 — 기술적으로 잃는 것이 없다.
