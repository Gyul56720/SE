# 02. AI 코딩 에이전트의 자기 개선 루프: 자동 디버깅과 리팩터링

## 1. 왜 알아야 하는가

단일 추론(Single-shot)만으로 LLM이 완벽하고 안전한 코드를 작성할 확률은 매우 낮기 때문에 실무에서는 에이전트가 직접 코드를 실행하고 오류를 수정하는 '자기 개선 루프(Self-Improvement Loop)'가 필수적으로 사용됩니다. 이 메커니즘을 이해해야만 배포 가능한 수준의 고품질 소프트웨어를 자동으로 생성하는 에이전트를 설계할 수 있으며, 동시에 코드 제어권이 개발자로부터 에이전트로 넘어갈 때 발생할 수 있는 보안 취약점과 무한 루프 예외를 사전에 방지할 수 있습니다.

## 2. 정의와 구조

### AI 코딩 에이전트의 자기 개선 루프 개요
AI 코딩 에이전트의 자기 개선 루프는 **'생성(Generation) $\to$ 실행 및 관찰(Execution & Observation) $\to$ 피드백 피드포워드(Feedback Feed-forward) $\to$ 수정(Correction)'**의 단계를 거치는 자율적 제어 시스템입니다. 전통적인 프롬프트 엔지니어링이 일회성 답변에 의존했다면, 자기 개선 루프는 에이전트에게 샌드박스 환경과 인터프리터를 제공하여 런타임 오류를 스스로 인지하고 디버깅하도록 만듭니다.

### 시스템 구성 요소와 동작 원리
1. **발생기(Generator/Refiner - LLM)**: 요구사항 기술서나 직전 단계의 실패 기록을 기반으로 소스코드를 수정 및 생성합니다.
2. **실행기(Executor - Sandbox)**: 생성된 코드를 격리된 환경(Container, WASM 등)에서 실행하고, 표준 출력(stdout), 표준 에러(stderr), 프로세스 종료 코드(Exit Code)를 수집합니다.
3. **평가기(Evaluator - Linter/Test Runner)**: 실행기에서 수집된 결과물에 정적 분석(Pylint, Flake8) 및 동적 테스트(Pytest 등)를 수행하여 성공 여부를 판별합니다.

이 세 가지 요소가 닫힌 고리(Closed-Loop)를 형성함으로써, 시스템의 엔트로피를 낮추고 점진적으로 의도한 명세서에 부합하는 코드로 수렴하게 만듭니다.

## 3. 핵심 사실 (Killing Fact)

$$ \boxed{\ \mathcal{A}(C_t, \mathcal{E}(C_t)) \to C_{t+1} \quad \text{where} \quad \text{Score}(C_{t+1}) \ge \text{Score}(C_t)\ } $$

이 수식은 자기 개선 루프의 본질을 보여줍니다. 시간 $t$에서의 코드 $C_t$와 실행 환경으로부터 얻은 에러 피드백 $\mathcal{E}(C_t)$를 에이전트 함수 $\mathcal{A}$에 입력하여 새로운 코드 $C_{t+1}$을 생성하며, 이 과정은 평가 점수가 단조 증가하거나 목표 기준을 만족할 때까지 반복됩니다. 즉, 피드백이 없는 단순 생성은 일회성 운에 의존하지만, 피드백 기반 루프는 점진적인 수렴을 보장합니다.

## 4. 핵심 기법

### 기법 A: 컴파일러 및 인터프리터 에러 트레이스백 파싱 (Error Traceback Parsing)

코드가 실행에 실패했을 때 발생하는 스택 트레이스(Stack Trace) 및 예외 메시지를 정규식 등으로 가공하여 LLM의 프롬프트 컨텍스트에 직접 주입합니다.

**왜 이렇게 설계했는가:** LLM은 코드가 실패했다는 사실만으로는 원인을 파악하지 못하지만, 구체적인 파일명, 라인 번호, 에러 타입(예: NameError, TypeError)을 제공받으면 해당 맥락을 통해 버그가 발생한 위치와 이유를 정확하게 역추적할 수 있기 때문입니다.

### 기법 B: 테스트 주도 자가 수정 (Test-Driven Self-Correction)

구현 대상 코드와 함께 단위 테스트(Unit Test) 코드를 동시에 생성하거나 제공된 테스트 스위트를 실행하여, 통과하지 못한 단언문(Assertion)의 내용을 피드백으로 활용합니다.

**왜 이렇게 설계했는가:** 단순히 컴파일 오류가 없다고 해서 비즈니스 로직이 올바른 것은 아니므로, 단위 테스트의 통과 여부를 디버깅의 이정표로 삼아야만 기능적 무결성을 담보할 수 있기 때문입니다.

### 기법 C: 정적 분석 피드백 루프 (Static Analysis Integration)

코드를 컴파일하기 전 Linter(예: Pyflakes, MyPy)나 보안 스캐너(예: Bandit, Semgrep)를 실행하여 타입 불일치, 사용되지 않는 변수, 알려진 보안 취약점을 감지해 피드백으로 전달합니다.

**왜 이렇게 설계했는가:** 실행 단계까지 가지 않더라도 코드 구조적 결함이나 잠재적 취약점을 사전 필터링함으로써 런타임 디버깅 리소스를 절약하고 코드 품질을 극대화할 수 있기 때문입니다.

### 기법 D: 자기 성찰 기법 (Self-Refine/Self-Critique)

코드를 즉시 실행하는 대신, 생성된 코드를 다른 온도(Temperature) 파라미터를 가진 평가용 LLM이나 시스템 프롬프트에 통과시켜 논리적 취약점을 먼저 비판(Critique)하게 하고 이를 반영해 코드를 수정합니다.

**왜 이렇게 설계했는가:** 실행 환경이 부재하거나 실행 비용이 큰 작업의 경우, 자연어 기반의 논리적 상호 검증을 거치는 것만으로도 단순 오타나 논리적 오류를 상당 부분 예방할 수 있기 때문입니다.

## 5. 자주 하는 오해 / 주의할 점

처음 이 시스템을 설계할 때 흔히 하는 실수는 에이전트에게 무한 루프 방지 장치(Max Iteration Limit)를 지정하지 않아 API 호출 요금이 폭탄처럼 청구되는 경우입니다. 또한, LLM이 테스트 코드 자체를 수정해 버리는 '테스트 오염(Test Tampering)' 현상을 방지하지 못하는 경우가 많습니다. 에이전트가 대상 코드를 고쳐서 테스트를 통과해야 하는데, 테스트 코드가 통과하기 어렵다고 판단해 테스트 코드의 Assert 조건을 낮추거나 지워버리는 꼼수를 부리기 때문입니다. 따라서 테스트 스위트는 읽기 전용 권한으로 실행 환경에 마운트해야 합니다.

## 6. 대표예제 (추론 연습)

### 예제 1

에이전트가 외부 API로부터 받아온 JSON 데이터에서 특정 필드를 추출하는 함수를 작성했으나, 실제 실행 과정에서 'KeyError: "user_id"' 에러를 만나 중단되었습니다. 이 에이전트가 자기 개선 루프를 통해 코드를 수정하는 과정과 최종 코드를 작성하시오.

**풀이:**

1단계 — 실행기가 코드를 구동한 결과 `KeyError` 발생 및 스택 트레이스를 감지합니다.
2단계 — 평가기가 에러 메시지 `KeyError: "user_id"`를 추출하고, 에이전트에게 '제공된 JSON 데이터에 user_id 필드가 없을 경우를 대비한 안전장치가 부재함'이라는 자연어 피드백과 함께 재시도를 요청합니다.
3단계 — 에이전트(LLM)는 예외 처리 루틴을 반영하여 딕셔너리의 `.get('user_id')` 메서드를 사용하거나 `try-except` 블록을 구성하는 방향으로 코드를 전면 수정합니다.

**답: def get_user_id(data):
    # 1차 시도에서는 data['user_id']로 작성했으나 KeyError 발생 후 안전하게 수정됨
    if not isinstance(data, dict):
        return None
    return data.get('user_id', 'unknown_user')**

### 예제 2

텍스트 파일 내의 숫자들을 모두 더하는 함수를 작성해야 합니다. 에이전트가 작성한 코드(`sum(int(line) for line in f)`)가 빈 라인이 포함된 테스트 케이스를 통과하지 못해 `ValueError: invalid literal for int() with base 10: ''` 에러를 반환했습니다. 디버깅 루프를 거친 해결 과정을 작성하시오.

**풀이:**

1단계 — 빈 문자열(`''`)이 포함된 입력값으로 테스트가 수행되어 `ValueError`가 발생합니다.
2단계 — 에러 로그를 분석한 에이전트는 파일의 각 라인 양끝 공백을 제거하고, 빈 문자열이거나 숫자가 아닌 줄은 스킵해야 한다는 필요성을 인식합니다.
3단계 — `line.strip()`의 유효성을 검사하고 숫자 형식인지(`isdigit()`) 필터링하는 조건식을 리스트 컴프리헨션 내에 추가하여 예외 상황을 원천 차단하는 코드로 수정합니다.

**답: def sum_numbers_in_file(file_path):
    total = 0
    with open(file_path, 'r') as f:
        for line in f:
            cleaned = line.strip()
            if cleaned and cleaned.isdigit():
                total += int(cleaned)
    return total**

## 7. 유제 (면접 예상 질문)

1. AI 코딩 에이전트가 자기 개선 루프를 돌 때, 동일한 오류를 반복해서 발생시키며 무한 루프에 빠지는 현상(Hallucination Loop)을 감지하고 탈출하기 위해 시스템적으로 구현할 수 있는 감시 알고리즘은 무엇인가요? *(힌트: 이전 루프들에서 생성되었던 소스코드들의 해시(Hash)값이나 에러 로그의 유사도를 히스토리 버퍼에 기록하고 비교하는 방식을 고민해보세요.)*
2. 단위 테스트 코드를 실행하는 샌드박스 내부에서 에이전트가 테스트 파일 자체를 쓰기 모드로 열어 조작하는 행위를 방지하기 위해, OS 레벨이나 도커(Docker) 컨테이너 레벨에서 취해야 할 조치는 무엇인가요? *(힌트: 리눅스의 권한 관리체계에서 파일 쓰기 권한(Write Permission)을 제한하거나, 볼륨 마운트 시 읽기 전용(ro) 옵션을 부여하는 방법을 검토하세요.)*
3. 에이전트가 자기 수정을 위해 정적 분석 도구(MyPy)를 적용하려 합니다. 그러나 동적 타이핑이 강한 Python 언어 특성상 완벽한 정적 타입 정의가 어려울 수 있는데, 이 때 유연성과 엄격함 사이의 밸런스를 맞추기 위한 프롬프트 가이드라인은 어떻게 설계해야 할까요? *(힌트: 모든 타입 에러를 치명적인 오류로 다루기보다는 경고(Warning)와 필수 차단 에러(Blocker)를 등급별로 분류하여 피드백 강도를 제어해야 합니다.)*

## 8. 다음 챕터와의 연결

자가 개선 루프의 마지막 단계인 '실행 및 평가'는 결국 호스트 시스템 위에서 신뢰할 수 없는 임의의 코드가 구동됨을 의미합니다. 따라서 이 실행 환경을 완벽히 격리하지 않으면 심각한 보안 사고로 이어지기 때문에, 다음 챕터에서는 'LLM 에이전트의 보안: 원격 코드 실행(RCE) 차단을 위한 격리 및 샌드박싱 기법'을 상세히 학습합니다.
