# 01. 자기 수정 코드(Self-Modifying Code)의 개념과 역사

## 1. 왜 알아야 하는가

현대 소프트웨어와 LLM 시스템 엔지니어링에서 자가 수정(Self-Modification) 메커니즘을 이해하는 것은 매우 중요합니다. 왜냐하면 실행 중에 코드가 스스로를 변경하는 원리는 현대적인 JIT 컴파일러의 핵심 성능 최적화 수단이자 컴퓨터 보안의 핵심 방어선인 W^X(Write XOR Execute) 규칙을 설계하게 만든 근본 배경이기 때문입니다. 또한, 이 개념은 현대 LLM 에이전트가 런타임에 코드를 생성하고 실행하며 실시간으로 수정하는 '자가 수정 루프'의 이론적 모태가 됩니다.

## 2. 정의와 구조

### 1. 자기 수정 코드(Self-Modifying Code)의 정의
자기 수정 코드(SMC)는 실행 중에 메모리에 로드된 자기 자신의 명령어를 동적으로 수정, 대체 또는 추가하여 원래의 제어 흐름과 다른 동작을 수행하는 소프트웨어 기법입니다.

### 2. 역사적 배경과 폰 노이만 구조
초기 컴퓨터 아키텍처인 폰 노이만 구조(Von Neumann Architecture)에서는 프로그램의 명령어(Code)와 연산 대상 데이터(Data)가 동일한 물리적 메모리 버스와 주소 공간을 공유합니다. 이러한 구조적 특성 때문에 프로그램이 특정 메모리 주소에 새로운 값을 쓰는 행위($\text{Write}$)가 곧 다음에 실행될 기계어 명령어를 바꾸는 행위($\text{Modify}$)로 연결될 수 있었습니다. 과거 메모리 자원이 극도로 한정되어 있던 에니악(ENIAC) 시절이나 초기 어셈블리어 환경에서는 메모리를 절약하기 위해 반복문의 인덱스 증가나 조건 분기 주소를 명령어 코드 자체의 비트를 연산하여 수정하는 방식이 흔히 사용되었습니다.

### 3. 현대적 보안 통제와 W^X (Write XOR Execute)
동적으로 명령어를 변경하는 행위는 버퍼 오버플로우와 같은 메모리 오염 취약점을 통해 공격자가 악성 쉘코드를 메모리에 주입하고 실행할 수 있는 심각한 위협을 낳았습니다. 이에 대응하여 현대 운영체제는 메모리 페이지의 권한을 엄격히 통제하는 $W \oplus X$ (Write XOR Execute) 보호 메커니즘을 하드웨어 수준에서 제공합니다. 이 규칙 하에 쓰기가 가능한 메모리 영역은 실행할 수 없고, 실행이 가능한 영역은 쓸 수 없도록 강제되므로, 런타임에서의 임의적인 자가 수정 코드는 운영체제에 의해 차단(Segmentation Fault)됩니다.

## 3. 핵심 사실 (Killing Fact)

$$ \boxed{\ \text{Code} \equiv \text{Data} \implies W \oplus X \text{ Enforcement Required}\ } $$

코드와 데이터가 동일한 메모리 공간을 공유한다는 폰 노이만 아키텍처의 근본 원칙은 자가 수정을 가능하게 만들었으나, 현대 보안 구조에서는 이를 임의 코드 실행 공격의 핵심 경로로 규정하여 쓰기 권한과 실행 권한을 물리적으로 동시에 주지 않음으로써 이를 원천 차단합니다.

## 4. 핵심 기법

### 기법 A: 메모리 매핑 권한 전환 (mprotect)

동적 기계어 생성 후, 해당 메모리 버퍼의 보호 특성을 mprotect() 등의 시스템 콜을 호출하여 PROT_WRITE(쓰기 가능)에서 PROT_EXEC(실행 가능)으로 변경한 뒤 호출합니다.

**왜 이렇게 설계했는가:** 현대 OS가 강제하는 W^X 정책을 우회하여 런타임에 동적으로 작성된 기계어 명령어를 정상적으로 실행 메모리에 로드하기 위해 고안된 표준 메커니즘이기 때문입니다.

### 기법 B: JIT (Just-In-Time) 컴파일러의 런타임 최적화

자바스크립트 V8 엔진이나 Java VM이 런타임에 핫스팟(반복 실행되는 가상 머신 바이트코드)을 찾아 즉석에서 머신 코드로 번역하고 메모리 영역에 주입하여 실행 경로를 대체합니다.

**왜 이렇게 설계했는가:** 인터프리터의 느린 성능을 극복하기 위해, 컴파일 타임이 아닌 실행 시간에 사용자의 실행 패턴 데이터를 수집하고 이를 반영하여 실시간 최적화 코드를 메모리에 동적으로 작성해야 하기 때문입니다.

### 기법 C: 다형성 및 변형 암호화 (Polymorphic Decryption Loop)

실행 파일 내 본문 코드는 암호화해 두고, 진입점(Entry Point)에는 짧은 복호화 루틴만 배치하여 실행 직후 메모리상에서 원래의 명령어를 복원하고 해당 코드로 제어권을 제어 흐름(Control Flow)을 넘깁니다.

**왜 이렇게 설계했는가:** 시그니처 기반의 정적 분석 보안 도구가 파일 원본 데이터를 분석하는 것을 회피하고, 실제 실행 속도 저하를 최소화하면서 런타임에만 정상 코드를 노출시키기 위해서 설계되었습니다.

## 5. 자주 하는 오해 / 주의할 점

가장 흔한 오해는 현대 컴퓨터에서 자가 수정 코드가 물리적으로 완전히 금지되었다고 생각하는 것입니다. 비록 하드웨어와 OS 수준에서 보안 장치가 마련되어 있지만, 브라우저의 JavaScript 엔진이나 자바 가상머신 등 동적 성능 최적화가 필수적인 고성능 런타임 환경에서는 앞서 언급한 권한 전환 기법을 사용하여 여전히 대규모의 자가 수정(JIT)이 발생합니다. 또한, 많은 엔지니어들이 LLM이 생성한 코드를 바로 파이썬의 eval()이나 exec()로 동적 실행하는 구조를 가벼운 '자가 수정 스크립트' 정도로 여겨 가볍게 생각하는데, 이는 전통적인 자가 수정 코드가 직면했던 '메모리 쓰기 권한 남용을 통한 제어권 탈취 공격'과 본질적으로 완벽하게 동일한 인젝션 취약점을 내부 애플리케이션에 영입하는 치명적인 실수입니다.

## 6. 대표예제 (추론 연습)

### 예제 1

W^X 보안 기법이 활성화되지 않은 구형 임베디드 장치에서, 입력된 난수의 값에 따라 조건 분기문의 목적지 주소 코드를 어셈블리 수준에서 직접 연산하여 바이트를 수정하는 자가 수정 펌웨어 기법을 분석 중입니다. 이 펌웨어가 가진 근본적인 보안 취약점과 안전한 정적 코드로의 전환 논리를 설명하시오.

**풀이:**

1단계 — 해당 코드는 데이터 영역의 난수 입력값에 따라 실행 명령어가 가리키는 포인터를 런타임에 직접 수정하기 때문에, 입력값에 비정상적인 버퍼 데이터나 조작된 값이 입력되는 경우 프로그램 제어 흐름 자체가 의도하지 않은 비실행 영역으로 강제 분기될 수 있습니다.
2단계 — 이를 해결하기 위해서는 동적으로 명령어를 직접 바꾸는 방식 대신, 실행 코드 영역을 완전한 읽기 전용(ROM)으로 하드웨어 마운트하고 조건 분기를 스위치-케이스(Switch-Case) 문이나 룩업 테이블(Lookup Table) 형태의 정적 분기문으로 재설계해야 합니다.
3단계 — 이를 통해 입력 데이터의 오염이 실제 실행될 명령어의 오피코드(Opcode) 자체를 파괴할 수 있는 가능성을 원천적으로 배제할 수 있습니다.

**답: 해당 기법은 입력값 검증 실패 시 흐름 제어 가로채기(Control Flow Hijacking) 취약점을 야기하므로, 가변적인 명령어 대체를 폐기하고 정적 룩업 테이블과 컴파일러 기반의 고정 분기문 구조로 리팩토링해야 합니다.**

### 예제 2

한 주니어 개발자가 사용자가 입력한 비정상적인 로그를 파싱하고 수정하기 위해, 임의의 파이썬 코드 문자열을 받아서 오류를 정정하고 이를 로컬 서버 런타임에 직접 exec() 함수로 구동하는 자가 정정 시스템을 구축하려 합니다. 이 구조에 숨겨진 악성 임의 코드 실행 위험을 도출하고 대안 설계를 제시하시오.

**풀이:**

1단계 — 파이썬의 exec()는 인자로 들어오는 텍스트 문자열을 데이터가 아닌 실제 실행 가능한 파이썬 파싱 트리 명령어로 즉시 변환하여 메모리에서 실행합니다.
2단계 — 만약 악의적인 사용자가 프롬프트나 입력 텍스트 내에 OS 명령어나 원격 쉘을 실행시키는 기법(예: import os; os.system('...'))을 은밀히 포함하여 전달하면, 자가 수정 루프를 지향하는 엔진이 무비판적으로 타겟 머신의 제어권을 전부 내어주게 됩니다.
3단계 — 이를 완전 방어하려면 입력 코드를 호스트 프로세스 내부에서 직접 실행하는 것을 전면 금지하고, 네트워크 인터페이스가 차단되고 읽기 전용 루트 파일시스템을 가진 일회성 도커(Docker) 컨테이너나 gVisor와 같은 분리된 가상 샌드박스 내부로 전송하여 결과를 엄격히 검증한 뒤 제한적 API로만 통신하도록 아키텍처를 전면 격리해야 합니다.

**답: 동적 문자열을 로컬 권한으로 직접 exec()하는 구조는 호스트 시스템을 완전 장악하는 임의 코드 실행(ACE) 취약점을 유발하므로, 실행 메커니즘을 완전히 분리된 호스트 격리 샌드박스(Sandbox) 환경에서 실행하도록 구축해야 합니다.**

## 7. 유제 (면접 예상 질문)

1. 현대 운영체제의 W^X 정책 하에서 동적 바이너리 변형이나 JIT 컴파일러가 정상 작동하기 위해 권한 전환 루틴에서 필수적으로 발생하는 시스템 콜 흐름을 기술하십시오. *(힌트: 메모리 영역을 할당하기 위해 호출하는 mmap() 함수에서 처음에는 어떠한 권한 조합을 준 뒤 기계어를 작성하고, 최종적으로 실행하기 직전에는 권한을 어떻게 마스킹 전환하는지 떠올려보세요.)*
2. 정적 분석 도구(IDA Pro, Ghidra 등)에서 자가 수정 바이너리를 올바르게 해석하지 못하고 무의미한 데이터 바이트로만 식별하는 이유는 무엇이며, 리버스 엔지니어는 이를 해석하기 위해 왜 '메모리 덤프(Memory Dump)'나 동적 디버거를 병행해야 합니까? *(힌트: 디스크에 저장된 정적 파일 상태의 바이너리는 암호화되어 있어 디코딩되지 않았지만, 실행 중에 메모리에서 자가 복원 루틴이 완전히 작동하고 난 직후의 상태는 다르다는 점에 초점을 맞추어 생각해 보세요.)*
3. LLM 시스템이 작성한 코드를 수정하는 AI 에이전트 루프에서 발생할 수 있는 무한 루프 에러와, 기계어 자가 수정 코드의 무한 루프 현상의 공통적 상태 머신 위험성을 추론하시오. *(힌트: 두 환경 모두 상태 정지(Halting)를 보장할 수 없기 때문에 실행 카운터나 시간 제한(Time-out)과 같은 강제 인터럽트 장치가 없으면 시스템 자원이 어떻게 고갈되는지 분석하세요.)*

## 8. 다음 챕터와의 연결

이번 장에서 배운 자가 수정 코드의 기계어 수준 역사와 메모리 보호 메커니즘은, 현대 LLM 기반 시스템에서 가장 활발히 연구되고 있는 자가 정제(Self-Refinement) 및 동적 코드 분석 루프의 이론적 기반이 됩니다. 다음 장에서는 이 원리를 바탕으로 하여 인간의 정적 프로그래밍 개입 없이 LLM 에이전트가 런타임에 스스로 단위 테스트를 수행하고 안전한 샌드박스 내부에서 논리 오류를 보완하는 'LLM 기반 자가 개선 루프의 설계 아키텍처'를 본격적으로 배웁니다.
