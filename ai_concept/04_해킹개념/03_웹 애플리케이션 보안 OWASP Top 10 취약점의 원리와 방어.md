# 03. 웹 애플리케이션 보안: OWASP Top 10 취약점의 원리와 방어

## 1. 왜 알아야 하는가

웹 애플리케이션은 사용자와 기업의 데이터를 연결하는 최전선의 인터페이스이기 때문에 가장 빈번한 공격 표적이 됩니다. 실무에서 OWASP Top 10과 같은 표준 보안 취약점을 이해하지 못하면 단 한 줄의 코드 실수만으로도 전체 데이터베이스가 유출되거나 서버 제어권을 침해당할 수 있습니다. 따라서 안전한 소프트웨어를 설계하고 기술 면접에서 아키텍처의 안정성을 입증하기 위해서는 이러한 취약점들의 발생 원리와 코드 수준의 방어 대책을 명확히 파악하고 있어야 합니다.

## 2. 정의와 구조

### OWASP Top 10의 개념과 의의

OWASP(Open Web Application Security Project)는 웹 애플리케이션 보안 향상을 목적으로 하는 비영리 단체로, 전 세계 보안 전문가들의 합의를 바탕으로 가장 빈번하고 치명적인 10대 웹 보안 위험을 주기적으로 발표합니다. 이는 단순히 체크리스트를 제공하는 것을 넘어, 현대 웹 개발 환경의 기술 변화(예: 마이크로서비스, 클라우드 네이티브, API 중심 아키텍처)에 따른 보안 위협의 우선순위를 제시합니다.

### 핵심 취약점 메커니즘 분석

1. **인젝션(Injection, A03:2021)**: 사용자 입력값이 프로그램의 명령어나 쿼리의 일부로 해석되어 실행되는 취약점입니다. 데이터 영역과 명령 영역이 엄격히 분리되지 않고 문자열 연결(Concatenation) 방식으로 쿼리가 동적 생성되기 때문에 발생합니다. 대표적으로 SQL Injection과 커맨드 인젝션이 있습니다.

2. **취약한 접근 제어(Broken Access Control, A01:2021)**: 사용자가 자신의 권한을 벗어난 리소스나 기능에 접근할 수 있는 상태를 의미합니다. 서버 측에서 요청의 주체와 요청 대상 리소스 간의 권한 관계를 매번 검증하지 않고, 클라이언트가 전달한 식별자(예: URL 파라미터의 ID값)를 그대로 신뢰하기 때문에 발생합니다.

3. **암호화 실패(Cryptographic Failures, A02:2021)**: 민감한 데이터(비밀번호, 개인정보 등)를 전송하거나 저장할 때 적절한 암호화 알고리즘을 사용하지 않거나, 취약한 암호 키 관리체계로 인해 정보가 노출되는 현상입니다. 기밀성과 무결성을 보장하는 현대적 대칭/비대칭 암호 표준을 준수하지 않기 때문에 발생합니다.

4. **크로스 사이트 스크립팅(XSS, Cross-Site Scripting)**: 공격자가 삽입한 악성 스크립트가 피해자의 웹 브라우저 내에서 실행되어 세션 토큰을 탈취하거나 페이지를 변조하는 공격입니다. 웹 애플리케이션이 사용자 입력을 적절히 정화(Sanitization)하거나 출력 인코딩(Output Encoding)을 하지 않고 그대로 브라우저에 렌더링하기 때문에 발생합니다.

## 3. 핵심 사실 (Killing Fact)

$$ \boxed{\ \text{Security} = \text{Input Whitelisting} \cap \text{Parameterized Queries} \cap \text{Context-Aware Output Encoding} \cap \text{Server-Side Authorization}\ } $$

웹 애플리케이션 보안의 핵심은 '클라이언트가 보내는 모든 입력은 악의적일 수 있다'는 비신뢰(Zero Trust) 원칙입니다. 입력값 검증, 쿼리 매개변수화, 출력값 인코딩, 서버 측 권한 검증이라는 이 네 가지 방어 레이어가 유기적으로 결합되어야만 OWASP Top 10의 대다수를 차지하는 인젝션, XSS, 권한 우회 공격을 원천적으로 차단할 수 있습니다.

## 4. 핵심 기법

### 기법 A: 매개변수화된 쿼리 (Prepared Statements)

SQL 쿼리 템플릿을 데이터베이스 엔진에 미리 컴파일하여 등록하고, 사용자 입력값은 플레이스홀더(?)를 통해 단순 데이터 파라미터로만 바인딩하여 쿼리를 실행합니다.

**왜 이렇게 설계했는가:** SQL 가이드라인과 사용자 입력 데이터가 완전히 분리되어 처리되기 때문에, 입력값 내에 SQL 예약어(UNION, OR 등)가 포함되어 있더라도 데이터베이스 엔진이 이를 명령어 구조로 해석하지 않고 단순 리터럴 문자로만 처리하여 SQL 인젝션을 원천 차단할 수 있기 때문입니다.

### 기법 B: 맥락 의존적 출력 인코딩 (Context-Aware Output Encoding)

사용자가 입력한 데이터를 브라우저에 출력할 때, 출력되는 위치(HTML 본문, 속성값, 자바스크립트 블록 등)에 맞춰 특수문자를 안전한 엔티티 형식(예: `<`를 `&lt;`로 변환)으로 치환합니다.

**왜 이렇게 설계했는가:** 브라우저 파서가 입력 데이터를 실행 가능한 스크립트 태그가 아닌 단순 렌더링용 텍스트 문자열로 해석하도록 강제함으로써 악성 스크립트의 실행(XSS)을 방지하기 때문입니다.

### 기법 C: 서버 사이드 세션 기반 인가 체계

클라이언트가 리소스 접근 요청 시 보낸 토큰(JWT 등)이나 세션 정보를 기반으로, 서버 내부의 비즈니스 로직 및 DB 레벨에서 해당 행위자의 리소스 소유권을 직접 조회하여 검증합니다.

**왜 이렇게 설계했는가:** 클라이언트 사이드에서 조작할 수 있는 URL 파라미터나 UI 상의 은닉 처리(CSS hidden 등)는 공격자가 무단으로 변조하여 전송할 수 있으므로, 최종 권한 판단 권한은 조작 불가능한 서버 측 통제 하에 두어야 하기 때문입니다.

### 기법 D: 안전한 역직렬화 (Safe Deserialization)

신뢰할 수 없는 외부 입력으로부터 언어 자체의 고유한 객체 직렬화 포맷(Java Serialization, Python Pickle 등)의 사용을 금지하고, 대신 원시 데이터 타입만 포함하는 표준 JSON 또는 Protocol Buffers 포맷을 채택합니다.

**왜 이렇게 설계했는가:** 언어 자체의 역직렬화 메커니즘은 바이트 스트림 복원 과정에서 예기치 않은 클래스의 생성자나 가비지 컬렉터 메서드를 트리거하여 원격 코드 실행(RCE)으로 이어질 위험이 매우 크기 때문입니다.

## 5. 자주 하는 오해 / 주의할 점

가장 흔한 실수는 '클라이언트 측 유효성 검사(Javascript Validation)'만으로 보안이 유지된다고 믿는 것입니다. 공격자는 프록시 툴이나 API 클라이언트를 사용해 브라우저를 완전히 우회하여 서버에 직접 조작된 요청을 보낼 수 있으므로, 모든 입력 검증은 반드시 서버 측에서 재수행되어야 합니다. 또한, 특정 단어를 치환하거나 제거하는 방식의 '블랙리스트 필터링'은 인코딩 우회 기법(우회 대소문자 혼용, NULL 바이트 주입 등)에 매우 취약하므로, 허용된 형식만 수용하는 '화이트리스트' 방식을 기본 정책으로 삼아야 합니다.

## 6. 대표예제 (추론 연습)

### 예제 1

한 쇼핑몰 서비스의 주문 내역 상세 조회 API 주소는 `/api/orders?order_id=500` 입니다. 로그인한 사용자가 이 주소의 `order_id` 파라미터 값을 `501`, `502`로 변경하자 다른 사람의 주문 내역과 주소가 그대로 화면에 노출되는 현상이 발견되었습니다. 이 취약점의 유형 명칭과 이를 해결하기 위한 서버 측 보완 조치를 서술하시오.

**풀이:**

1단계 - 취약점 분석: 공격자가 URL의 리소스 식별자(Parameter)를 임의로 조작하여 권한이 없는 데이터에 접근하고 있으므로, 이는 OWASP Top 10 중 '취약한 접근 제어(Broken Access Control)'의 하위 범주인 '안전하지 않은 직접 객체 참조(IDOR)'에 해당합니다.
2단계 - 원인 진단: 서버가 데이터베이스에서 주문 정보를 조회할 때 단순히 `WHERE order_id = :order_id` 조건만 적용하고 있으며, 현재 인증된 세션의 사용자 ID와 주문의 소유자 ID가 일치하는지 검증하지 않기 때문에 발생합니다.
3단계 - 보완 조치 설계: 쿼리를 실행할 때 세션에서 안전하게 추출한 사용자의 고유 ID(`session_user_id`)를 조건절에 결합하여 `WHERE order_id = :order_id AND customer_id = :session_user_id` 형태로 조회하도록 비즈니스 로직을 변경합니다. 이렇게 하면 타인의 ID를 입력해도 데이터가 조회되지 않습니다.

**답: 해당 취약점은 IDOR(Broken Access Control)입니다. 이를 해결하기 위해 요청 파라미터인 `order_id`를 조회 조건으로 삼을 때, 현재 로그인한 세션 정보에서 추출한 사용자 고유 식별자(`customer_id`)를 데이터베이스 조회 조건문에 필수로 추가하여 소유권 검증 과정을 서버 사이드에서 강제해야 합니다.**

### 예제 2

한 게시판 서비스에서 사용자가 작성한 본문 내용이 화면에 렌더링될 때, 사용자가 `<script>alert(document.cookie)</script>`를 입력하자 게시글을 조회하는 모든 사용자의 브라우저에서 경고창이 뜨며 세션 쿠키가 노출되는 문제가 발생했습니다. 이 취약점을 해결하기 위한 가장 효과적인 개발 단계에서의 해결책은 무엇입니까?

**풀이:**

1단계 - 취약점 분석: 사용자가 입력한 악성 스크립트가 정화되지 않고 데이터베이스에 저장된 후, 다른 사용자들에게 그대로 출력되어 브라우저 컨텍스트 내에서 실행되고 있으므로 '저장형 크로스 사이트 스크립팅(Stored XSS)' 취약점입니다.
2단계 - 원인 진단: 웹 템플릿 엔진이 사용자 데이터 필드를 출력할 때 태그 해석 방지 인코딩을 적용하지 않았거나, 개발자가 가공되지 않은 원시 HTML(Unescaped HTML)을 출력하도록 코드를 작성했기 때문입니다.
3단계 - 보완 조치 설계: 화면에 데이터를 출력하는 뷰 레벨에서 특수 기호들을 문자 엔티티 형태로 강제 변환하는 '콘텍스트 의존적 출력 인코딩(Context-Aware Output Encoding)'을 전면 적용합니다. 예를 들어 Thymeleaf, React, Vue 등의 최신 프레임워크가 제공하는 자동 에스케이프 기능을 기본 활성화 상태로 유지하고 개발자가 이를 수동으로 끄지 않도록 코딩 규칙을 제한합니다.

**답: 해당 취약점은 Stored XSS입니다. 이를 방지하기 위해 뷰 레이어에서 웹 프레임워크의 자동 HTML Escaping 기능을 사용하거나, 사용자 정의 데이터를 출력할 때 명시적으로 Context-Aware Output Encoding을 수행하여 스크립트 코드가 단순 텍스트로 브라우저에 표시되도록 조치해야 합니다.**

## 7. 유제 (면접 예상 질문)

1. 사용자로부터 검색 키워드를 입력받아 웹 페이지에 바로 보여주는 검색 결과 화면이 있습니다. 이 화면에서 Reflected XSS 공격을 방어하기 위한 방어 메커니즘을 구체적으로 설명하시오. *(힌트: 입력 데이터가 서버를 거쳐 브라우저 응답으로 반환되는 즉시 실행되므로, HTTP 응답 헤더의 'Content-Type' 지정과 출력 인코딩이 핵심 역할을 합니다.)*
2. 데이터베이스 조회 성능 향상을 위해 동적으로 복잡한 SQL 문을 조립해야 하는 상황입니다. Prepared Statement를 전면 도입하기 어려운 제약 조건 하에서 SQL Injection을 방어할 수 있는 대안적인 검증 방법론은 무엇입니까? *(힌트: 입력값의 도메인을 엄격히 한정하는 '화이트리스트 패턴 매칭' 또는 '정규 표현식 기반 유효성 검사' 기법을 연계하여 해결책을 구상해 보세요.)*
3. 비밀번호 저장을 위해 일방향 해시 함수인 MD5나 SHA-1을 사용하는 것은 왜 위험하며, 실무에서 이를 대체하기 위해 권장되는 해시 알고리즘과 그 보완책(Salt, Stretching)의 원리는 무엇입니까? *(힌트: MD5 등은 계산 속도가 너무 빨라 브루트 포스나 레인보우 테이블 공격에 쉽게 뚫리기 때문에, 솔팅을 적용하고 의도적으로 연산 속도를 늦추는(Key Stretching) 전용 패스워드 해시 알고리즘이 필요합니다.)*

## 8. 다음 챕터와의 연결

이번 장에서 다룬 웹 애플리케이션 보안의 '입력값 비신뢰 및 안전한 컨텍스트 분리' 원칙은 최신 인공지능 엔지니어링 분야에서도 고스란히 계승됩니다. 다음 장에서는 사용자의 자연어 입력이 LLM 모델의 시스템 지시문(System Prompt)과 혼동되어 모델을 오작동하게 만드는 '프롬프트 인젝션(Prompt Injection)과 탈옥(Jailbreaking)'의 원리와 그 방어 대책에 대해 학습할 예정입니다.
