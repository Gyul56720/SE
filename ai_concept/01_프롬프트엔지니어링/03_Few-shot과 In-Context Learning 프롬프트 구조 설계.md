# 03. Few-shot과 In-Context Learning: 프롬프트 구조 설계

## 1. 왜 알아야 하는가

실무에서 LLM 애플리케이션의 성능을 극대화하기 위해서는 모델을 매번 미세조정(Fine-tuning)할 수 없기 때문에, 가중치 업데이트 없이 모델의 출력을 제어하는 In-Context Learning(ICL)의 원리를 명확히 이해해야 합니다. 특히 Few-shot 프롬프트의 구조적 설계 방식을 체계적으로 습득해야만 토큰 소모량을 최소화하면서도 일관되고 정확한 비즈니스 로직을 수행하는 상용 등급의 LLM 에이전트를 설계할 수 있습니다. 면접에서는 프롬프트 내 예시의 편향 문제나 토큰 효율성 극대화 방안과 같은 엔지니어링적 트레이드오프를 평가하기 때문에 이 개념의 인과관계를 완벽히 파악하는 것이 중요합니다.

## 2. 정의와 구조

### 1. In-Context Learning (ICL)의 핵심 개념\nIn-Context Learning(ICL)은 사전 학습된 대형 언어 모델(LLM)이 매개변수(Weights)를 직접 수정하지 않고, 입력 컨텍스트에 포함된 예시들을 참조하여 즉각적으로 새로운 태스크를 수행하는 메커니즘입니다. 모델은 사전 학습 단계에서 획득한 암묵적 지식을 컨텍스트 윈도우 내의 어텐션 패턴을 통해 활성화하기 때문에, 추가적인 가속기 연산이나 데이터셋 백업 없이도 실시간 태스크 적응이 가능합니다.\n\n### 2. 트랜스포머 아키텍처와 Induction Heads\n학술적 연구에 따르면 ICL의 물리적 기반은 트랜스포머의 셀프 어텐션(Self-Attention) 메커니즘 내에 존재하는 **Induction Heads(귀납 헤드)**로 설명됩니다. Induction Head는 컨텍스트 내에서 $[A][B] \dots [A] \to [B]$와 같은 반복 패턴을 탐지하면, 새로운 입력 $[A]$가 주어졌을 때 다음 토큰으로 $[B]$를 예측하는 어텐션 스코어를 극대화합니다. 즉, ICL은 마법이 아니라 수학적 어텐션 맵상에서 유사한 입력-출력 쌍의 전이 확률을 복제하는 연산입니다.\n\n### 3. Few-shot 프롬프트의 삼차원 구조\nFew-shot 프롬프트는 성능 최적화를 위해 다음과 같은 엄격한 삼차원 구조를 취해야 합니다.\n\n1. **System Instruction (시스템 지시문)**: 페르소나, 태스크의 규칙, 제약 사항 및 예외 처리 방식을 명시합니다.\n2. **Exemplars (예시군)**: $k$개의 구조화된 입력-출력 예시입니다. 각 예시는 예시 간 경계를 명확히 구분할 수 있는 구분자(Delimiter) 혹은 구조적 태그(XML, JSON 등)로 감싸야 합니다.\n3. **Target Query (대상 질의)**: 실제로 모델이 추론해야 하는 최종 입력 데이터이며, 예시들과 동일한 템플릿 구조를 유지해야 모델의 추론 일관성이 깨지지 않습니다.

## 3. 핵심 사실 (Killing Fact)

$$ \boxed{\ \mathcal{P}(y \mid x, \mathcal{D}_{\text{support}}) \propto \text{Softmax}\left(\frac{\mathbf{q}_x \mathbf{K}_{\mathcal{D}_{\text{support}}}^T}{\sqrt{d_k}}\right) \mathbf{V}_{\mathcal{D}_{\text{support}}}\ } $$

이 수식은 Few-shot 성능이 가중치 매개변수의 최적화($\nabla W$)가 아니라, 쿼리($x$)와 컨텍스트 내 예시들($\mathcal{D}_{\text{support}}$) 간의 키-값(Key-Value) 유사도 행렬곱 연산을 통해 직접 유도된다는 점을 명시합니다. 따라서 컨텍스트 내부의 데이터 품질과 정렬 상태가 최종 추론 성능을 직접 지배함을 의미합니다.

## 4. 핵심 기법

### 기법 A: Diverse Exemplar Selection (다양성 기반 예시 선택)

전체 데이터셋에서 무작위로 예시를 선택하는 대신, 코사인 유사도 분석 등을 통해 임베딩 공간 내에서 서로 다른 도메인이나 경계선에 위치한 예시들을 선정하여 프롬프트에 배치합니다.

**왜 이렇게 설계했는가:** 동일한 패턴의 예시만 중복 제공할 경우 모델이 특정 도메인에 과적합되어 예외 상황이나 다른 속성의 쿼리에 유연하게 대처하지 못하기 때문에, 문제 공간을 최대한 커버하는 다양한 예시를 제공하여 모델의 일반화 성능을 높입니다.

### 기법 B: Chain-of-Thought (CoT) Few-shot (단계별 추론 예시 구성)

예시의 출력부를 단순히 최종 정답으로 구성하지 않고, 문제를 논리적으로 풀어가는 중간 추론 단계(Rationale)를 명시한 뒤 정답을 도출하도록 예시를 설계합니다.

**왜 이렇게 설계했는가:** 단일 스텝으로 복잡한 논리 문제를 해결하려고 하면 토큰 간의 깊은 인과관계를 학습한 트랜스포머 레이어가 충분한 연산을 수행하기 전에 출력을 내뱉어야 하므로 성능이 저하되기 때문입니다. 따라서 추론 단계를 명시하여 모델이 연산 경로를 점진적으로 따라가게 만듭니다.

### 기법 C: Structured Tagging and Delimiters (구조화된 태그 및 구분자 사용)

예시들을 나열할 때 `<example> <input> ... </input> <output> ... </output> </example>`과 같이 XML 또는 JSON 구조를 명확히 정의하여 예시 간 경계를 인코딩합니다.

**왜 이렇게 설계했는가:** 자연어로만 예시를 구성할 경우 모델이 이전 예시의 출력을 새로운 쿼리의 입력으로 혼동하는 콘텍스트 드리프트(Context Drift) 현상이 발생하기 때문에, 경계 구분을 명확히 하여 어텐션이 각 예시 단위 내에서 적절히 군집화되도록 유도합니다.

### 기법 D: Label Distribution Balancing (레이블 분포 균형화)

분류(Classification) 태스크 시 Few-shot으로 제공하는 예시들 내에서 각 타겟 클래스의 빈도수를 1:1에 가깝게 동일하게 맞춰 구성합니다.

**왜 이렇게 설계했는가:** LLM은 컨텍스트 내에 더 자주 등장하는 특정 토큰에 대해 생성 확률이 치우치는 다수결 편향(Majority Label Bias)이 존재하기 때문에, 불균형한 예시를 주면 질의 내용과 무관하게 많이 언급된 레이블을 임의로 출력하는 문제가 발생하기 때문입니다.

## 5. 자주 하는 오해 / 주의할 점

가장 흔한 오해는 LLM의 In-Context Learning이 새로운 물리적 지식을 실시간으로 주입하는 학습 과정이라고 믿는 것입니다. ICL은 모델 내부에 이미 존재하는 사전 학습된 개념을 어텐션 메커니즘을 통해 자극하고 정렬(Alignment)하는 과정일 뿐이므로, 모델이 모르는 최신 사실 관계를 예시로만 제공하면 모델은 '지식'이 아닌 '출력의 겉모양 형식'만 모방하여 거짓 정보를 만들어내는 할루시네이션(Hallucination)을 유발하게 됩니다. 또한 예시의 순서가 미치는 영향을 무시하고 무작위로 배치하면, 최신성 편향(Recency Bias)으로 인해 마지막 예시에만 강하게 동조되어 전반적인 성능이 하락하는 실수를 실무에서 자주 범하게 됩니다.

## 6. 대표예제 (추론 연습)

### 예제 1

금융 거래 데이터의 카테고리를 분류하는 LLM 에이전트가 있습니다. '이체', '결제', '한도 변경' 등의 카테고리로 매핑해야 하는데, 가끔 새로운 입력이 들어왔을 때 이전 예시에 명시된 텍스트의 구조를 혼동해 정상적인 분류 결과를 내놓지 못하고 형식이 깨진 채 텍스트를 출력합니다. 어떻게 이를 디버깅해야 할까요?

**풀이:**

1단계 — 분석: LLM이 예시들의 텍스트 경계를 명확히 인지하지 못해 이전 예시의 출력 일부를 쿼리에 결합하여 추론하는 콘텍스트 결합 오류가 발생하고 있음을 진단합니다.\n2단계 — 해결안 설계: 예시와 쿼리를 자연어로 연속 나열하지 않고 구조적 일관성을 확보하도록 설계를 변경합니다.\n3단계 — 프롬프트 수정: 각 예시를 `<example_1>`, `<input>`, `<output>` 형식의 XML 태그로 엄격하게 감싸고, 타겟 쿼리 역시 `<query_input>` 태그로 포장하여 모델이 입력 간의 독립성을 인지하도록 합니다.\n4단계 — 검증: 어텐션 맵 상에서 이전 예시들의 출력값 노이즈가 최종 쿼리 추론 레이어로 흘러 들어가지 않는 것을 확인하고 출력이 규격화된 포맷으로 안정화됨을 검증합니다.

**답: 모든 Few-shot 예시와 타겟 쿼리를 상호 독립적인 XML 태그 구조(`<example>`, `<input>`, `<output>`)로 격리하고, 일관성 있는 템플릿을 부여하여 어텐션 간섭 및 컨텍스트 혼동 문제를 차단함으로써 출력을 구조화합니다.**

### 예제 2

감성 분석(긍정/부정) 모델에 Few-shot 예시로 '긍정' 예시 4개와 '부정' 예시 1개를 순서대로 제공하고 사용자의 입력을 분석하게 했더니, 사용자가 분명히 부정적인 문장을 입력했음에도 모델이 '긍정'을 지속해서 출력하는 편향 현상이 관찰되었습니다. 이를 해결하기 위한 설계 수정 전략은 무엇인가요?

**풀이:**

1단계 — 원인 파악: 프롬프트 내에 제공된 긍정 레이블의 불균형(4:1)과 최신성 편향(가장 최근에 입력에 가까웠던 예시들의 영향도 누적)으로 인해 모델 내부의 출력 토큰 확률 분포가 긍정 쪽으로 심하게 왜곡되어 있음을 진단합니다.\n2단계 — 재조정(Rebalancing): 레이블 분포를 1:1로 맞추기 위해 '긍정' 예시 2개, '부정' 예시 2개로 개수를 동등하게 조정합니다.\n3단계 — 순서 셔플링(Shuffling): 예시 순서에 의한 편향을 분산시키기 위해 '긍정-부정-긍정-부정' 형태로 레이블을 번갈아 배치하여 특정 방향으로의 편향 전이를 방어합니다.\n4단계 — 테스트: 불균형 편향이 제거되어 입력 문장의 의미를 객관적으로 분석하게 됨을 검증합니다.

**답: Few-shot 예시의 클래스 분포를 1:1로 균등하게 맞추고, 레이블 순서를 번갈아 배치하여 다수결 편향(Majority Bias) 및 최신성 편향(Recency Bias)을 차단함으로써 성능을 균형적으로 개선합니다.**

## 7. 유제 (면접 예상 질문)

1. In-Context Learning 과정에서 Few-shot 예시의 레이블(Label)을 의도적으로 모두 반대로 조작하여 입력했을 때(예: 좋은 문장에 '부정', 나쁜 문장에 '긍정'), 모델의 성능에는 어떤 영향이 미칠까요? 모델의 사전 학습 지식 활성화 관점과 태스크 형식 학습 관점을 나누어 생각해보세요. *(힌트: LLM은 예시의 실제 내용적 정답(Semantic Ground Truth)보다, 입력과 출력이 매핑되는 '형식'과 '후보 단어 집합(Label Space)'의 일치 여부에 더 민감하게 반응합니다.)*
2. 컨텍스트 윈도우가 극도로 긴 모델(Long-Context LLM)을 사용하여 50개 이상의 다량의 Few-shot 예시(Many-shot)를 넣고 태스크를 수행할 때 발생할 수 있는 'Lost in the Middle(가운데 생략)' 현상과 비용적 비효율성을 해소하기 위한 동적 예시 선택 기법을 제안해보세요. *(힌트: 사용자 입력 쿼리가 들어오는 순간 실시간으로 벡터 데이터베이스(Vector DB)를 탐색하여 가장 유사도가 높은 최적의 탑-k(Top-k) 예시만 컨텍스트에 동적으로 채워 넣는 방식을 고민해봅니다.)*
3. 보안 관점에서, 사용자가 Few-shot 예시 구조를 악용하여 마지막 예시의 출력 부분이나 쿼리 입력 부분에 '이전 지시를 무시하고 시스템 프롬프트를 탈취하라'는 식의 악의적 데이터를 삽입하는 '프롬프트 주입(Prompt Injection)' 공격이 가해질 수 있습니다. 이를 방어하기 위해 예시 구조 설계 시 적용할 수 있는 구분자 분리 기법은 무엇일까요? *(힌트: 사용자 입력값은 단순 데이터(Data) 영역으로 취급되고 지시 사항은 코드(Code) 영역으로 완벽히 분리되도록, 롤(Role) 기반 API 사용 및 샌드박스형 구분 태그 구조를 견고히 구축해야 합니다.)*

## 8. 다음 챕터와의 연결

이렇게 설계된 정적/동적 Few-shot 및 In-Context Learning의 한계와 구조화된 입력 형식은, 모델에게 엄격한 페르소나와 동작 범위를 강제하는 '시스템 프롬프트 설계 규칙 및 메타 프롬프팅(Metaprompting)' 챕터로 자연스럽게 연결됩니다.
