# 04. 고급 추론을 위한 프롬프트 최적화: Self-Consistency, ReAct, 구조화된 출력

## 1. 왜 알아야 하는가

LLM의 단순한 순방향 연산(Forward Pass)은 복잡한 다단계 추론이나 정교한 비즈니스 로직을 완벽하게 처리하지 못하기 때문에, 시스템의 신뢰성을 극대화하기 위해 고급 프롬프트 기법을 학습해야 합니다. 특히 실무에서는 일관되지 않은 추론 결과나 비구조화된 텍스트 응답이 시스템 통합의 치명적인 장애물이 되므로, 출력을 구조화하고 외부 도구와 협업하며 결과의 일관성을 확보하는 최적화 기법은 필수적입니다.

## 2. 정의와 구조

### 1. Self-Consistency (자기 일관성)\nSelf-Consistency는 Chain-of-Thought(CoT)의 한계를 극복하기 위해 제안된 기법입니다. 단일 추론 경로를 따라 답을 도출하는 대신, 모델의 Temperature를 0보다 크게 설정하여 다양한 추론 경로($r_i$)와 그에 따른 최종 답안($a_i$)을 생성하도록 유도합니다. 이후 다수결(Majority Voting)을 통해 가장 빈번하게 등장한 답안을 최종 선택합니다. 이는 복잡한 논리 문제에서 우연한 오답을 배제하고 수학적/공학적 일관성을 높이는 데 효과적입니다.\n\n### 2. ReAct (Reasoning and Acting)\nReAct 프레임워크는 LLM의 내부 추론(Thought)과 외부 환경과의 상호작용(Action 및 Observation)을 결합합니다. LLM은 문제를 해결하기 위해 현재 상황을 분석하고(Thought), 필요한 도구를 호출하며(Action), 그 실행 결과(Observation)를 다시 입력에 통합하는 루프를 반복합니다. 이 과정을 통해 할루시네이션(Hallucination)을 줄이고 실시간 정보 탐색이 가능해집니다.\n\n### 3. 구조화된 출력 (Structured Output)\n대규모 언어 모델의 응답을 외부 API나 내부 데이터베이스와 연동하려면 결정론적이고 신뢰할 수 있는 데이터 포맷(예: JSON, XML)이 필요합니다. 이를 위해 시스템 프롬프트에 JSON 스키마를 강제하거나, OpenAI의 Structured Outputs 기능처럼 스키마를 준수하는 토큰만 생성되도록 로짓 바이어스(Logit Bias) 또는 문법(Grammar) 제약을 적용하는 기법이 활용됩니다.

## 3. 핵심 사실 (Killing Fact)

$$ \boxed{\ \%hat{a} = \%arg\%max_{a} \%sum_{i=1}^{N} \%mathbb{I}(a_i = a) \%quad \%text{where } a_i = \%text{ExtractAnswer}(r_i \%sim p_{\%theta}(r|x))\ } $$

이 수식은 Self-Consistency의 수학적 근간으로, 다양한 온도 설정 하에서 샘플링된 독립적인 추론 경로들($r_i$) 중 최종 도출된 결과($a_i$)의 최빈값을 구하는 과정을 의미합니다. 이는 단일 경로에 의존하는 일반 CoT에 비해 오답의 영향을 상쇄하고 최적의 일치 경로를 도출해 내는 핵심적인 신뢰성 보장 메커니즘입니다. (참고: JSON 포맷팅을 위해 수식 내부의 백슬래시는 유니코드 디코딩 시 유효하도록 더블 이스케이프 또는 JSON 가이드라인을 따릅니다.)

## 4. 핵심 기법

### 기법 A: Self-Consistency Sampling

API 호출 시 Temperature를 0.5에서 0.7 사이의 중간 값으로 설정한 후, 다중 출력 생성 파라미터(예: n=5 또는 n=10)를 사용하여 여러 추론 경로를 병렬로 도출하고 사후에 최빈값(Majority Vote)을 수집합니다.

**왜 이렇게 설계했는가:** 온도가 0이면 모델이 항상 하나의 탐욕적(Greedy) 추론 경로만 선택하여 오답에 한 번 빠졌을 때 극복하기 어려운 반면, 온도를 주어 생성하면 다양한 추론 궤적 중 정답으로 수렴하는 빈도가 통계적으로 높기 때문입니다.

### 기법 B: ReAct Loop Template

프롬프트 내에 'Thought: [추론]', 'Action: [도구명[파라미터]]', 'Observation: [도구 실행 결과]' 패턴을 차례대로 강제하는 Few-shot 예시를 배치하고, Stop Sequence를 'Observation:'으로 설정하여 실행을 통제합니다.

**왜 이렇게 설계했는가:** 모델이 행동을 개시하기 전에 먼저 이유(Thought)를 숙고하게 함으로써 도구 오용을 방지하고, 외부 실행 결과(Observation)를 다음 생각에 결합하여 정보 업데이트를 가능하게 하기 때문입니다.

### 기법 C: Schema-Guided Structured Generation

JSON Schema로 정의된 구조를 시스템 프롬프트에 직접 정의하거나 API 수준의 'response_format'에 주입하고, Pydantic 등의 라이브러리로 전달된 출력을 최종 유효성 검증합니다.

**왜 이렇게 설계했는가:** 일반 자연어 프롬프트 지시만으로는 모델이 간혹 부연 설명을 붙이거나 예외 토큰을 출력하여 백엔드 프로그램의 구문 분석(Parsing) 오류를 일으키는 현상을 기계적으로 확실히 배제하기 위함입니다.

## 5. 자주 하는 오해 / 주의할 점

가장 흔한 실수는 Self-Consistency를 적용하면서 정작 API 파라미터의 Temperature를 0으로 고정하는 것입니다. 이 경우 생성된 N개의 답변이 모두 똑같아져 다수결 연산의 의미가 상실됩니다. 또한 ReAct 기법을 설계할 때 무한 루프(Infinite Loop) 방지 안전장치를 생략하여, 도구 실행 실패 시 동일한 Action을 무한정 반복하며 상상할 수 없을 만큼 많은 비용을 소모하고 서버가 뻗는 일이 빈번하게 발생합니다. 마지막으로 구조화된 출력을 구성할 때 JSON의 파싱 적합성만 검사하고 각 필드의 세부 유효성 범위(예: 나이가 음수이거나 특정 값이 Null로 채워지는 현상)를 놓치는 논리 오류도 주의해야 합니다.

## 6. 대표예제 (추론 연습)

### 예제 1

사용자의 총 지출 이력을 분석하여 세금 감면 대상이 되는 항목을 정확히 추출하고 합산해야 하는 재무 관리 시스템을 개발 중입니다. 단일 추론 방식으로는 계산 실수가 자주 발생하여 정확도가 떨어집니다. 이 시스템에 Self-Consistency를 적용하는 구현 로직을 단계별로 설명하시오.

**풀이:**

1단계 - 사용자의 지출 데이터와 감면 세부 법령을 프롬프트에 제공하고, 각 단계별 연산과 최종 합산액을 명시하도록 CoT 포맷을 유도합니다.\n2단계 - API 호출 시 Temperature를 0.7로 주입하고 파라미터 n=5를 설정하여 동시에 5개의 서로 다른 추론 답변을 가져옵니다.\n3단계 - 백엔드 파이썬 코드에서 각 답변 내의 최종 연산 금액을 정규표현식(Regex)을 이용해 추출합니다.\n4단계 - 추출한 금액들 중 가장 빈번하게 등장한 값(최빈값)을 탐색하여 최종 검증된 세금 감면액으로 시스템에 출력합니다.

**답: 동일 요청에 대해 5개의 독립된 추론 결과의 최빈값을 탐색하여, 단일 디코딩 단계에서 발생할 수 있는 계산적 편향 및 단일 실패점(SPOF)을 제거합니다.**

### 예제 2

사내 데이터베이스 검색 도구를 활용하여 사용자가 질문한 장비의 정비 이력을 알려주는 CS 봇을 제작해야 합니다. 모델이 잘못된 정비 매뉴얼을 스스로 상상하지 않고 정비 이력 데이터베이스(DB_Search API)를 정확하게 활용하여 답변을 작성하도록 유도하는 ReAct 아키텍처를 설계하시오.

**풀이:**

1단계 - 사용 가능한 도구를 'DB_Search[장비명]'으로 프롬프트 상단에 선언합니다.\n2단계 - 'Thought: 현재 질문에 대응하기 위해 어떤 장비의 정보가 필요한지 파악한다. Action: DB_Search[장비명]. Observation: 검색 결과'의 템플릿 예제를 추가합니다.\n3단계 - 모델이 'Action' 줄을 출력하면 API 클라이언트에서 Stop 토큰을 작동시켜 출력을 일시중지합니다.\n4단계 - 정비 DB에 실제로 검색 쿼리를 실행해 결과를 얻은 후, 이를 'Observation: [정비 이력 결과]' 메시지로 결합하여 모델에게 이어서 생성하게 만듭니다.

**답: Thought로 장비를 식별한 후 DB_Search 액션을 발생시켜 실행 결과를 관측하고, 이로부터 도출된 팩트만을 답변하도록 설계된 ReAct 에이전트 루프 구조입니다.**

## 7. 유제 (면접 예상 질문)

1. Self-Consistency 기법에서 최빈값을 정하는 기준(Voting Strategy)을 설계할 때, 단순히 '정답 문자열'의 일치 여부만 비교하는 대신 가중치를 주는 진보된 다수결 계산 아이디어는 무엇이 있는가? *(힌트: 각 경로가 생성될 때 계산되는 토큰 확률(Token Probability) 혹은 로그 우도(Log Likelihood)의 합산값이나 평균값을 가중치로 활용하는 방안을 고려해보세요.)*
2. ReAct 루프가 끊이지 않고 무한정 외부 API를 호출하며 과금이 발생하는 현상을 방어하기 위해 애플리케이션 레벨에서 구현해야 할 핵심 방어 수치는 무엇인가? *(힌트: 에이전트가 반복할 수 있는 최대 횟수(Max Iterations)를 환경 변수로 하드코딩하고, 횟수 초과 시 안전하게 폴백(Fallback) 답변을 출력하도록 예외 처리를 구성해야 합니다.)*
3. Structured Output을 사용할 때 Schema에 명시된 필수 필드(Required Field)가 유실되거나 'Null' 값으로 채워져 들어오는 스키마 부적합 오류를 해결하기 위해 프롬프트 지침에 심어둘 수 있는 방어 장치는 무엇인가? *(힌트: '설명(description)' 필드에 반드시 값이 존재해야 하는 세부 조건이나 값이 없을 때 채워넣을 기본 폴백 값(Default Value)을 상세히 가이드하는 방법을 검토하세요.)*

## 8. 다음 챕터와의 연결

안정적인 추론과 강건한 구조화 출력 기법을 터득했다면, 이제 이를 시스템에 연동하는 과정에서 악의적인 사용자 입력을 만나게 됩니다. 다음 장에서는 프롬프트 인젝션(Injection)과 탈옥(Jailbreaking)의 위협 모델을 다루고 이를 방어하는 핵심 보안 전략을 살펴봅니다.
