# 01. LLM의 정보 처리 방식: 토큰화, 임베딩, 어텐션과 컨텍스트 윈도우

## 1. 왜 알아야 하는가

LLM을 활용한 프롬프트 엔지니어링과 보안 위협 대응의 출발점은 모델이 텍스트를 물리적으로 어떻게 이해하고 처리하는지 명확히 아는 것입니다. 토큰화, 임베딩, 어텐션 메커니즘은 LLM이 입력을 해석하고 맥락을 압축하는 핵심 파이프라인이기 때문에, 이를 모르면 비효율적인 프롬프트 작성으로 비용이 낭비되거나 컨텍스트 윈도우 초과로 인한 정보 누락을 방어할 수 없습니다. 따라서 이 원리를 이해해야만 모델의 한계를 예측하고 최적의 입출력 제어가 가능해집니다.

## 2. 정의와 구조

### 1. 토큰화 (Tokenization)\nLLM은 원시 텍스트를 직접 처리하지 않고, 이를 의미 있는 최소 단위인 '토큰(Token)'으로 분할하여 처리합니다. 주로 Byte-Pair Encoding(BPE) 알고리즘이 사용되며, 이는 자주 등장하는 문자열 조합을 하나의 토큰으로 병합하는 방식을 취합니다. 이 때문에 한국어나 특수문자는 영어에 비해 더 많은 토큰을 소비하게 되며, 이는 프롬프트 설계 시 비용과 컨텍스트 제한에 직접적인 영향을 미칩니다.\n\n### 2. 임베딩 (Embedding)\n토큰화된 각 토큰은 고차원 벡터 공간의 점으로 변환되는 '임베딩' 과정을 거칩니다. 임베딩 벡터는 단어의 시맨틱(의미론적) 관계를 수학적 거리로 표현하므로, 유사한 의미를 지닌 토큰들은 벡터 공간상에서 가깝게 위치하게 됩니다.\n\n### 3. 셀프 어텐션 (Self-Attention)\n트랜스포머 아키텍처의 핵심인 셀프 어텐션은 문장 내의 모든 토큰 쌍 간의 관계성을 계산합니다. 각 토큰은 Query, Key, Value 벡터로 변환되며, 가중치합을 통해 현재 맥락에서 가장 중요한 토큰 정보를 집중해서 받아옵니다. 수학적으로는 $\\text{Attention}(Q, K, V) = \\text{softmax}\\left(\\frac{QK^T}{\\sqrt{d_k}}\\right)V$로 정의됩니다.\n\n### 4. 컨텍스트 윈도우 (Context Window)\n컨텍스트 윈도우는 모델이 한 번에 처리할 수 있는 최대 토큰 수의 한계를 의미합니다. 어텐션 연산의 시간 복잡도가 토큰 길이의 제곱($\\mathcal{O}(N^2)$)에 비례하기 때문에, 컨텍스트 윈도우는 하드웨어와 알고리즘적 제약으로 인해 물리적으로 제한됩니다. 이 제한을 초과하면 이전 정보가 유실되거나 모델이 오동작을 일으킬 수 있습니다.

## 3. 핵심 사실 (Killing Fact)

$$ \boxed{\ \\text{Attention}(Q, K, V) = \\text{softmax}\\left(\\frac{QK^T}{\\sqrt{d_k}}\\right)V \\quad \\text{and} \\quad \\mathcal{O}(N^2)\\text{ Complexity}\ } $$

셀프 어텐션 공식과 제곱 복잡도는 LLM이 문맥을 이해하는 원리와 컨텍스트 한계가 발생하는 물리적 이유를 동시에 보여줍니다. 입력 토큰 수($N$)가 증가할 때 연산량이 제곱으로 증가하기 때문에 컨텍스트 윈도우가 제한될 수밖에 없으며, 이 수학적 제약을 이해하는 것이 효율적인 프롬프트 압축과 설계의 근본적인 출발점이 됩니다.

## 4. 핵심 기법

### 기법 A: BPE 기반 토큰 수 계산 및 최적화

프롬프트 작성 시 한글의 자모 분리 현상이나 불필요한 다중 공백을 제거하고, 다국어 처리 시 영문 번역 후 입력하는 파이프라인을 구축합니다.

**왜 이렇게 설계했는가:** 한국어는 형태소 구조상 영어보다 동일 의미 대비 더 많은 토큰을 소모하므로, 토큰 수를 미연에 최적화해야 비용을 절감하고 컨텍스트 초과 오류를 방지할 수 있기 때문입니다.

### 기법 B: 슬라이딩 윈도우 및 대화 이력 압축

긴 대화 세션에서 전체 이력을 유지하는 대신 최신 $K$개의 토큰만 유지하는 슬라이딩 윈도우를 적용하거나, 이전 대화를 핵심 요약문(Summary)으로 대체하여 프롬프트에 주입합니다.

**왜 이렇게 설계했는가:** 어텐션 메커니즘의 토큰 제한 범위 내에서 핵심 맥락을 잃지 않으려면 정보 밀도를 높이고 불필요하게 늘어난 토큰을 주기적으로 정리해야 하기 때문입니다.

### 기법 C: 임베딩 벡터 유사도 분석 기반 RAG 필터링

사용자의 질문과 문서 데이터베이스의 문단들을 임베딩 공간으로 변환한 뒤 코사인 유사도를 계산하여 관련성이 높은 상위 $N$개의 정보만 선별하여 컨텍스트로 제공합니다.

**왜 이렇게 설계했는가:** 무관한 정보를 무작정 컨텍스트 윈도우에 주입하면 노이즈가 증가하고 어텐션 분산 현상(Lost in the Middle)이 발생하여 답변 정확도가 떨어지기 때문입니다.

### 기법 D: 어텐션 포커싱 유도 구조 설계

프롬프트의 시작 부분과 끝 부분에 핵심 지시사항을 배치하고, XML 태그 등의 명확한 구분자를 사용하여 데이터 영역을 격리합니다.

**왜 이렇게 설계했는가:** 모델이 가중치를 부여할 때 구조화된 태그와 물리적 위치에 따른 어텐션 바이어스를 활용해야 중요 지시 사항에 더 높은 소프트맥스 가중치를 배정하기 때문입니다.

## 5. 자주 하는 오해 / 주의할 점

가장 흔한 실수는 글자 수나 단어 수를 토큰 수와 동일하게 생각하는 것입니다. 한글은 초성/중성/종성이 분리되어 인코딩되거나 여러 토큰으로 쪼개지기 때문에 영문보다 훨씬 빠르게 컨텍스트 한계에 도달합니다. 또한, 무조건 많은 정보를 프롬프트에 집어넣으면 더 정확히 답변할 것이라는 오해를 합니다. 실제로는 'Lost in the Middle' 현상으로 인해 컨텍스트의 중간에 위치한 정보는 어텐션 가중치를 제대로 받지 못해 무시되기 쉬우며, 불필요한 노이즈 토큰이 늘어날수록 추론 성능이 급격히 저하됩니다.

## 6. 대표예제 (추론 연습)

### 예제 1

한글 문서 약 15,000자를 프롬프트로 입력하여 요약을 지시했으나, 모델이 컨텍스트 한계를 초과하여 요약문을 누락하거나 에러를 반환합니다. 이 문제를 토큰화 특성을 고려하여 해결하는 효율적인 절차를 제시하시오.

**풀이:**

1단계 - 사용 중인 LLM의 토큰나이저를 활용해 한글 텍스트의 실제 토큰 수를 측정하고, 한국어는 1글자당 평균 2~3토큰 이상을 소모함을 인지합니다.\n2단계 - 전체 문서를 의미 단위로 분할(Chunking)하여 각 청크가 단일 컨텍스트 한도를 넘지 않게 조정합니다.\n3단계 - 분할된 각 청크를 순차적으로 요약(Map)한 뒤, 생성된 요약본들을 다시 취합하여 최종 요약(Reduce)하는 Map-Reduce 기법을 적용합니다.

**답: 한글의 높은 토큰 확장률을 감안하여 텍스트를 청킹하고, 순차적으로 요약한 뒤 재통합하는 Map-Reduce 아키텍처를 적용하여 컨텍스트 초과 문제를 해결합니다.**

### 예제 2

보안 가이드라인 문서를 RAG 시스템에 적용했는데, 사용자가 '서버 보안 점검 항목'을 질문했을 때 무관한 '개인정보 처리 방침' 문서가 함께 프롬프트에 주입되어 답변이 왜곡됩니다. 어텐션과 임베딩 관점에서 원인을 규명하고 해결책을 제시하시오.

**풀이:**

1단계 - 단순 '보안' 키워드의 중복으로 인해 임베딩 공간에서 관련 없는 문서의 벡터가 인접하게 산출되었음을 진단합니다.\n2단계 - 어텐션 메커니즘이 무관한 토큰들에도 가중치를 배분하여 최종 Value 출력을 왜곡시켰음을 분석합니다.\n3단계 - 유사도 임계값(Threshold)을 상향 조정하고, 키워드 검색을 혼합한 하이브리드 검색을 도입하여 프롬프트 주입 단계에서 노이즈 문서를 제거합니다.

**답: 유사도 기준 강화 및 하이브리드 검색을 통해 컨텍스트 노이즈를 차단함으로써, 모델의 셀프 어텐션 리소스가 유효한 서버 보안 정보에만 포커싱되도록 제어합니다.**

## 7. 유제 (면접 예상 질문)

1. 영문 텍스트 1,000단어와 국문 텍스트 1,000단어가 실제 LLM API에서 소비하는 토큰 수와 과금 비용에 차이가 발생하는 근본 원인은 무엇인가? *(힌트: Byte-Pair Encoding(BPE) 알고리즘이 한국어와 같이 사전 정의가 부족한 비영어권 문자를 처리할 때 바이트 단위로 쪼개어 표현하는 방식을 고려해 보세요.)*
2. 긴 프롬프트의 중앙에 위치한 핵심 지침이 모델에 의해 지속적으로 무시되는 현상을 해결하기 위해, 시스템 프롬프트의 배치 구조를 어떻게 수정해야 하는가? *(힌트: 입력 문맥의 시작과 끝부분에 위치한 토큰이 소프트맥스 가중치를 높게 부여받는 'Primacy/Recency Effect'를 활용해 보세요.)*
3. 다회차 대화 세션에서 이전 대화 흐름을 전부 전송하는 방식의 문제점을 해결하기 위해, 임베딩 벡터 데이터베이스와 요약 모델을 복합적으로 연계하는 아키텍처를 설계한다면 어떻게 구성해야 하는가? *(힌트: 매 대화 단계에서 중요도가 낮은 일상적 토큰은 RAG 유사도 검색에서 필터링하고, 장기 기억은 주기적으로 서머리 노드로 압축하여 컨텍스트 윈도우에 배치하는 방식을 고민해 보세요.)*

## 8. 다음 챕터와의 연결

이렇게 LLM이 정보를 토큰 단위로 쪼개어 어텐션 가중치로 처리하는 물리적 한계를 파악했다면, 이를 활용해 입력값의 형태를 가공하는 실전 기법으로 나아가야 합니다. 다음 장에서는 이 정보 처리 구조를 바탕으로 모델의 답변 정확도를 극대화하는 '명확한 지시어 설계 및 역할 지정(System Prompt) 기법'을 상세히 다루겠습니다.
